# 為什麼要先考雜湊，才信任它

<!-- SPDX-License-Identifier: Apache-2.0 -->

這份文件寫給學生，說明 vk26-alice-2 想回答的問題、為什麼往這個方向走，以及這樣做的好處與代價。實驗本身的細節在 [README.md](./README.md)（英文）。建議先讀 vk26-alice-1 的 [WHY.zh-TW.md](../vk26-alice-1-the-run-across-the-seam/WHY.zh-TW.md)，這個實驗沿用它的健康測試區塊。

## 1. 先弄清楚：kernel 為什麼需要雜湊

亂數產生器從雜訊源取出的樣本，就算通過健康測試，也不是均勻的亂數：每個樣本帶的熵不到 1 位元。所以通過測試的樣本要先經過**條件化（conditioning）**，例如把 4096 位元組的樣本用 SHA-256 壓成 32 位元組，才拿去用。

在這個 repo 裡，kernel 沒有自己的 SHA-256 時，就用 `ecall` 呼叫外部的 `HASH`：

- 在 Pico 2 上，`HASH` 由 shell 交給 RP2350 的 **SHA-256 硬體區塊**計算（exp210）；
- 在 Lean 的證明裡，`HASH` 是 `env.hash`，**任何**從位元組到 32 位元組的函數都可以。

定理對任何雜湊函數都成立，聽起來很強，其實也是一個缺口：**證明不管 `HASH` 算得對不對**。如果硬體區塊壞了，kernel 照樣把它的答案當成輸出寫出去。

## 2. 兩條路：自己算，或先考它

這個 repo 已經走過第一條路。exp223 把 exp208 證明過的 RV32IM SHA-256 放進 kernel，雜湊在 kernel 裡算、在證明裡驗：一個視窗要 **334284 條指令**（見 [exp223 的 capture](../../../../experiments/exp223-the-digest-the-kernel-withholds/capture.txt) 的 `the model after 334284`）。

vk26-alice-1 和這個實驗走第二條路：呼叫硬體，整個 kernel（兩個視窗、兩次 `HASH`）只要 **34885 條指令**。代價是要信任硬體。vk26-alice-1 把檢查交給外面：shell 拿 Python 的 hashlib、網頁拿瀏覽器的 WebCrypto，事後比對每一個雜湊。

這個實驗多做一件事：**在 kernel 裡、在讀第一個樣本之前，先考 `HASH` 一題答案已知的題目**。

```
題目：一則固定的 64 位元組訊息（放在映像檔 0x300）
答案：它的 SHA-256（由 gen.py 用 hashlib 算好，放在 0x340）
作答：kernel 呼叫 HASH，答案寫到 0x360
批改：kernel 逐字比對 0x360 和 0x340 的 32 位元組，不提早結束
```

答錯，kernel 立刻以停止碼 2 停下，一個樣本都不讀。這叫**已知答案測試（Known-Answer Test，KAT）**。

## 3. 標準怎麼說

NIST SP 800-90B 沒有要求 KAT：全文找不到「known answer」，它的健康測試是針對雜訊源的樣本，「在任何條件化之前」做（§4.3 第 6 項）。所以 **KAT 是這個實驗自己的選擇**，不是標準的要求。

啟動測試（start-up test）則是標準的要求，§4.3 第 4 項：

> 熵源的啟動測試應對**至少 1024 個連續樣本**執行持續健康測試。……受啟動測試的樣本，可以在啟動測試通過後釋出使用，**也可以在任何時候丟棄**。

這個實驗選了「丟棄」：第一個視窗（1024 個樣本）只拿來做啟動測試，**永遠不雜湊**。第二個視窗通過才雜湊、輸出。

## 4. vk26-alice-2 做了什麼

整個 kernel 有 112 條指令，依序：

1. **KAT**：`HASH`（64 位元組 → 0x360），再逐字比對 32 位元組。不符 → 停止碼 **2**。
2. **啟動測試**：對第一個視窗跑 vk26-alice-1 的 `win` 區塊。失敗 → 停止碼 **1**。
3. **第二個視窗**：重複次數（RCT）從第一個視窗**帶過來**繼續數。失敗 → 停止碼 **3**。
4. **輸出**：`HASH` 第二個視窗的 4096 位元組，寫到 0x2400。停止碼 **0**。

這裡有一個容易漏掉的細節：RCT 跨窗連續計數，所以第一個視窗的樣本會影響「**有沒有輸出**」（例如縫兩側 11+10 個 1，會讓第二個視窗失敗），但**輸出的每一個位元組都只取決於第二個視窗**。

## 5. 證明了什麼

主要定理是 `Trust.from_boot` 和 `Trust.trusts_after_kat`，白話是：

> 不管樣本是什麼、不管 `HASH` 是什麼函數：
> - 如果 `HASH` 對 KAT 的答案和映像檔裡的預期答案不同，kernel 在**恰好 43 條指令**後以 2 停下，記憶體只多了 `HASH` 寫在 0x360 的那 32 位元組；
> - 如果 kernel 以 0 停下，那麼 `HASH` 一定通過了 KAT，而且 0x2400 的 32 位元組就是 `HASH`（第二個視窗）。

其他情況的指令數也是確定的：啟動失敗 17462、第二窗失敗 34878、全部通過 34885。

規劃時寫的是「KAT 不符就停下，**記憶體不變**」。實作時發現做不到：`HASH` 一定先把答案寫進記憶體，kernel 才能比對。定理寫出的是精確的差別：只有那 32 位元組。這是把規劃寫成定理時才會發現的事。

另外有 11 個故意寫錯的版本（`proof/mutants.txt`），例如 KAT 的分支方向相反、比對時用 `and` 而不是 `or`、輸出成啟動視窗的雜湊、宣稱「答案等於它自己寫進去的地方就算通過」（這對任何雜湊都成立，等於沒考）。Lean 全部拒絕。

## 6. 怎麼知道 KAT 真的會擋

exp114 的 README 有一句話：「**從來沒被觀察到觸發過的檢查，和根本不會觸發的檢查，無法區分。**」

所以 shell 每一輪都故意弄壞一次：在 fair 這條樣本流上，把 `HASH` 對 KAT 的答案的第一個位元組翻轉一個位元。kernel 必須在讀任何樣本之前以 2 停下。LED 每一輪都會閃這一次（兩下）。

更有意思的是兩個「壞掉的 shell」：

- `HASH` 把雜湊寫到晚一個字（4 位元組）的位置；
- `HASH` 少算了 64 位元組。

這兩種錯誤**不是 shell 的檢查抓到的，是 kernel 的 KAT 抓到的**：KAT 的答案錯了，kernel 在 TRNG 那條（沒有被故意弄壞的）樣本流上以 2 停下，shell 的第 2 項檢查才報錯。KAT 在這裡做了它該做的事。

## 7. 誰在檢查誰

| 誰 | 怎麼寫的 | 檢查什麼 |
| --- | --- | --- |
| `trust.py` | 照規劃的順序，一個樣本一個樣本，用 alice 共用的 `health.py` | 14 條樣本流加 3 個錯的預期答案 |
| Lean 模型與 Hazard3 RTL | 同一個 `kernel.bin` | 停止碼、指令數、整個 64 KiB 區域都和 `trust.py` 加 hashlib 一致 |
| 網頁 `trust.html` | JavaScript；健康測試用 alice 共用的 `health.js`（和 vk26-alice-1 的網頁同一份） | 用 WebCrypto 重算 KAT 的答案、重判兩個視窗、驗輸出 |

## 8. 好處

- **信任的條件寫進了定理**：有輸出，就代表 `HASH` 答對了那一題。
- **快**：34885 條指令，比 exp223 自己算 SHA-256 的 334284 條少一個數量級。
- **KAT 在每一輪都被觀察到觸發**，不只是寫在程式裡。上板的紀錄裡，故意弄壞的答案出現 4 次，kernel 4 次都在第 43 條指令停下、沒有輸出；硬體區塊被老實地問了 14 次，14 次都答對。
- **晶片和 RTL 的指令數一致**：停止碼 0、1、2、3 分別是 34897、17470、51、34885，連「多 1 條」的那幾個也一樣。所以多出來的那條在處理器或共用的 harness，不在模擬器。

## 9. 代價與限制

- **只上過一次板**：一塊 Pico 2、一支手機、一份紀錄（`board/round1.txt`），18 條完整樣本流、三次 TRNG 取樣。
- **KAT 只考一題**：64 位元組、一個區塊。一個「一個區塊算對、64 個區塊算錯」的雜湊會通過 KAT；輸出是 4096 位元組，正好是 64 個區塊。這要靠 shell 和網頁事後比對。
- **預期答案是映像檔給的**：`Trusted` 比對的是 0x340 的 32 位元組，不管它們是什麼。它們是不是 SHA-256 的答案，是 gen.py 和 shell 的事，不是定理的事。
- **故意弄壞的是 shell 翻的一個位元，不是硬體真的壞掉**。它證明 KAT 會擋；它不告訴我們硬體會怎麼壞。
- **RTL 多算的一條指令**：停止碼 0、1、2 都比「每次 `HASH` 多 4 條、加 3」再多 1，停止碼 3 沒有。兩個實驗合起來的九個數字裡，多 1 恰好出現在「停下的那個 `ecall` 後面還有別的指令」的時候。這是觀察到的規律，不是解釋。

## 10. 這個實驗在試跑裡的角色

做這個實驗時找到的徵集設定問題：

- **J3 看不到同一份提案前面的實驗**：裁判判「有沒有新東西」時，只列 `experiments/` 的實驗。這個實驗沿用 vk26-alice-1 的跨窗計數，J3 看不到 vk26-alice-1，就可能把它算成這個實驗的新東西。**已修**（獨立 commit）：提案自己編號較小的索引列，現在也列進 J3 的資料。
- **第二份就抽出**：第二個網頁、第二個 fixtures.py、第二個 RTL 檢查，原本都會複製 vk26-alice-1 的程式。在複製之前，判定程式移到 `pages/health.js`，node 的載入器、瀏覽器測試、輸出行的讀寫也各自移到 alice 的共用目錄。

## 11. 給學生的思考題

1. 為什麼比對 32 位元組時「不提早結束」？如果發現第一個字不同就停，會有什麼問題？（提示：指令數。）
2. 如果把 KAT 的訊息換成 4096 位元組，第 9 節的第二個限制會消失嗎？代價是什麼？
3. 定理說「以 0 停下 ⇒ `HASH` 通過了 KAT」。反過來，「`HASH` 通過了 KAT ⇒ 以 0 停下」成立嗎？為什麼？
4. §4.3 第 4 項允許啟動測試的樣本「通過後釋出使用」。如果改成這樣，輸出應該是哪些樣本的雜湊？定理要怎麼改？
