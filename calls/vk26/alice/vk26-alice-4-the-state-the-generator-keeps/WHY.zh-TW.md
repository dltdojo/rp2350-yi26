# 產生器記住的那個狀態

<!-- SPDX-License-Identifier: Apache-2.0 -->

這份文件寫給學生，說明 vk26-alice-4 想回答的問題、為什麼往這個方向走，以及這樣做的好處與代價。實驗本身的細節在 [README.md](./README.md)（英文）。

## 1. 種子之後還有一段路

exp222、exp223 做到的事是：雜訊源的樣本通過健康測試之後，用 SHA-256 濃縮成 32 位元組的**種子**。但程式真正要用的亂數，通常不是直接拿種子，而是交給一個**確定性亂數產生器**（DRBG）：種子只放進去一次，之後每次要亂數，它都從自己記住的**狀態**算出一批輸出，再把狀態往前推。

NIST SP 800-90A 的 Hash_DRBG 就是這種產生器。它的狀態有三樣東西：

- **V**：55 位元組（440 位元）的數字，每次都會變；
- **C**：55 位元組，種子放進去時就決定，之後不變；
- **reseed_counter**：已經產生過幾次，到了上限就必須重新取種子（reseed）。

## 2. Generate 在做什麼

每要一次亂數（不帶 additional input 的版本，§10.1.1.4）：

1. 如果 reseed_counter 已經超過上限，拒絕，回報「需要 reseed」；
2. 輸出 Hash(V)、Hash(V+1)、Hash(V+2)……需要幾塊就算幾塊（Hashgen）；
3. 算 H = Hash(0x03 ‖ V)；
4. V = (V + H + C + reseed_counter) mod 2^440，然後 reseed_counter 加 1。

看起來只有四行。難的是第 4 步：**四個 55 位元組的大數相加，而且要模 2^440**。處理器一次只能加 32 位元，所以要一個位元組一個位元組地加，把進位一路往前帶。

## 3. 為什麼這裡最容易悄悄出錯

假設某個實作在第 20 個位元組忘了帶進位，或是把計數器加在 V 的「錯的那一端」（大端序和小端序搞反）。會發生什麼事？

**什麼事都不會發生。** 輸出仍然是 SHA-256 的結果，看起來一樣隨機，統計測試照樣通過。但這已經不是 SP 800-90A 的 Hash_DRBG 了：它的安全性論證不再適用，和其他正確實作產生的序列也對不起來。執行時沒有任何東西會發現。

這正是「證明」比「測試」有用的地方：錯誤不會自己冒出來，只能事先排除。

## 4. 證明了什麼

kernel 只有 70 條 RV32IM 指令。四次相加共用同一個 ADD 副程式：把 a1 指向的 55 位元組加到 a0 指向的 55 位元組上，從最後一個位元組往前加，進位放在 a3。H 和計數器都先擺成 55 位元組的欄位（前面補零），所以四次加法都是同一個 ADD。

主要定理 `Drbg.from_boot`，白話是：

> 映像檔裡放好 kernel 和一組狀態 (V, C, counter)，counter 沒超過上限。那麼 kernel 會在**恰好 2030 + 566m 條指令**後以 0 停下（m 是要的區塊數）。停下時記憶體恰好是：0x600 起是 Hashgen 的 m 個區塊，V 變成 V + H + C + counter，counter 加 1，計算用過的中間值留在它們的位置，其他一個位元組都沒變。

另外幾個定理：

- `after_out`：0x600 + 32j 起的第 d 個位元組，就是 Hash(V + j) 的第 d 個位元組。這是用「讀的人看到什麼」來寫 Hashgen；
- `reseed_boot`：counter 超過上限時，kernel 在 7 條指令後以 1 停下，一個位元組都不寫；
- `generate_twice`：在第一次留下的記憶體上再跑一次，第二次的輸出就是「新的 V」的 Hashgen。NIST 的測試向量正是這樣檢查的。

還有 12 個故意寫錯的版本，Lean 全部拒絕。例如：counter 等於上限時就拒絕（應該是超過才拒絕）、H 漏掉前面的 0x03、C 沒有加、計數器的位元組寫到別的位元組上、ADD 的進位右移 9 位而不是 8 位。

## 5. 「對任何雜湊函數都成立」，為什麼還要 NIST 的向量

定理裡的雜湊是 `env.hash`，**任何**函數都可以。這是刻意的：證明只管 kernel 有沒有照 SP 800-90A 的步驟做，不管雜湊本身。好處是證明不必碰 SHA-256 的六十四輪運算；代價是「雜湊就是 SHA-256」要另外確認。

所以這個實驗把同一件事從三個彼此無關的地方檢查：

1. **drbg.py**：照 SP 800-90A 的文字寫的 Python，對 NIST CAVP 的 120 組 SHA-256 向量，全部對；
2. **Lean 模型和 Hazard3 RTL**：kernel 在兩者上各跑完 120 組，每組連跑兩次，第二次的 1024 位元等於 NIST 的答案；
3. **網頁**：用瀏覽器自己的 SHA-256（WebCrypto）和 JavaScript 的 BigInt，從板子說的 V 和 C 重算每一次 Generate。

規劃時不確定雲端拿不拿得到 NIST 的向量（討論結果第 4 點）。結果拿得到，所以檔案連同來源和雜湊值一起放進 repo，之後不需要網路。

## 6. 板子上會跑什麼

每一組 NIST 向量，shell 讓 kernel 在同一塊記憶體上連跑三次：

- 第 1、2 次：Generate，都要以 0 停下；
- 第 3 次：counter 已經是 3，超過上限 2，**必須拒絕**，以 1 停下、什麼都不寫。

kernel 唯一的呼叫是 HASHB。晶片上由 RP2350 的 SHA-256 硬體區塊回答。但共用的 `sha_hw.h` 只接受 64 位元組整數倍、而且對齊的輸入，HASHB 的輸入卻是 55 和 56 位元組。所以 alice-4 自己寫了補位（padding）：0x80、補零到區塊的第 56 個位元組、最後是位元長度。寫的時候沒有任何機器能檢查它。如果寫錯，第一組就會在檢查 4 失敗：LED 先亮 2 秒，再閃 4 下。

**上板的結果**：Pico 2 跑了兩輪共 178 組，沒有任何 FAIL。手機存回的紀錄裡有 165 組完整，全部正確：
- 第二次 Generate 的 1024 位元都等於 NIST 的答案，所以補位是對的；
- 指令數都和 RTL 相同。

週期數也有發現：
- 第二次 Generate 在 165 組裡全是 15,078 個週期，不管 V 和 C 是什麼；
- 第一次 Generate 有 40 組多了 110 到 1,596 個週期，而且多半是同一批案例、兩輪都慢。

這指向案例資料在 flash 裡的位置，和 alice-3 找到的 XIP 快取現象一樣，不是狀態的值造成的。另有一段紀錄在送到手機的途中整行遺失，那幾組網頁標為不完整，不做判斷。

RTL 上 120 組全部通過：每次 Generate 4318 條指令，每次拒絕 11 條。

## 7. 證明不到的地方

- **Instantiate**：把熵變成 V 和 C 的 Hash_df 沒有證明，只透過 NIST 向量間接檢查。vk26-alice-5 才要證明它。
- **固定時間**：`lean/Rv32/Ct.lean` 的檢查器只認得 HASH 和 HALT，不認得 HASHB，也不接受 `jal`、`jalr`，所以根本問不了這個 kernel。這是試跑找到的設定問題（見下）。
- **計數器只有 32 位元**：所以上限要小於 2^32 − 1，標準允許到 2^48。
- **只能要整數個區塊**：每次 256 位元的倍數。

## 8. 好處與代價

**好處**：最容易悄悄出錯的地方（大數加法、進位、位元組順序、計數器擺在哪裡）由證明排除，而且對每一個狀態都成立，不是只對測過的那 120 組。NIST 向量則補上證明刻意不管的那一半：雜湊確實是 SHA-256。

**代價**：

- 證明的主要工作是 55 位元組大端序的加法。這個 repo 原有的 `lean/Rv32/Limbs.lean`（exp229）是小端序 32 位元字，用不上，要另寫。這些引理目前放在這個實驗自己的證明檔裡，因為還沒有第二個地方用到；vk26-alice-5 的 Hash_df 會是第二個。
- kernel 用副程式（`jal`/`jalr`）寫四次加法，程式短、證明也只要證一次 ADD；但固定時間檢查器因此問不了它。exp229 為了讓檢查器接受，把副程式全部展開。這裡選了另一邊。

## 9. 試跑在徵集設定裡找到的問題

- **NIST 的向量拿得到**：討論結果第 4 點的疑問解決了。
- **Ct.lean 問不了這種 kernel**：只認得 HASH 和 HALT、不接受 `jal`/`jalr`。檢查器在 `lean/`，S2 不讓提案修改，所以只記錄，不改。
- **SHA-256 硬體區塊的共用程式只接受整塊**：任意長度的補位放在 alice 自己的 `shell/hashb_chip.h`（最初寫在 alice-4 的 `board_chip.c`，alice-5 也用到後才抽出），和 alice-3 的 `trng_raw.h` 一樣，是 S2 讓 `tools/` 不能改的結果。若第二份提案也需要，它應該搬到 `sha_hw.h` 旁邊。
