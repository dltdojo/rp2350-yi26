# 熵的估計靠的那個數字

<!-- SPDX-License-Identifier: Apache-2.0 -->

這份文件寫給學生，說明 vk26-alice-3 想回答的問題、為什麼往這個方向走，以及這樣做的好處與代價。實驗本身的細節在 [README.md](./README.md)（英文）。

## 1. 先弄清楚：「熵」是在估什麼

亂數產生器的雜訊源每取一個樣本，到底帶來多少「不可預測性」？這就是**熵**。如果一個 8 位元的樣本永遠是同一個值，它帶來 0 位元的熵；如果 256 個值出現的機會完全一樣，它帶來 8 位元。

真正的雜訊源介於兩者之間，而且我們不知道確切的分布，只能從樣本**估計**。NIST SP 800-90B 第 6.3.1 節的「最常見值估計」（most common value，MCV）是最簡單的一種：

1. 數出最常出現的那個值出現了幾次，除以樣本總數，得到 p̂；
2. 算出 p̂ 的 99% 信賴區間上界：p_u = min(1, p̂ + 2.576 √(p̂(1 − p̂)/(L − 1)))；
3. 估計的最小熵是 H = −log2 p_u（每個樣本幾位元）。

直覺是：最常出現的值越常出現，攻擊者越容易猜中，熵就越低。

這個 repo 之前沒有做過這件事。exp114 的健康測試門檻是**假設**每位元 1 位元熵算出來的，exp222 也寫明「SP 800-90B 的熵評估不在這裡」。

## 2. 哪一部分可以證明

第 2、3 步需要開根號和取對數，這個 repo 的 Lean 沒有證明過做這兩件事的 RV32IM 程式。但第 1 步只是**數數**：數出 256 個值各出現幾次，找出最大的。

所以這個實驗只證明能證明的那一半：

- **kernel（有證明）**：數 4096 個樣本，寫出 256 個次數和最大的那個；
- **網頁和 Python（沒有證明）**：用最大次數算 p̂、p_u、H，兩邊各自寫、互相比對。

這條「證明到哪裡為止」的界線，README 寫得很清楚。這也是試跑想測的事：裁判看到「一半有證明、一半沒有」的宣稱時，會怎麼判斷。

## 3. 為什麼要數得這麼慢

最直覺的數法是 `counts[樣本] += 1`：每個樣本讀一次，把對應的格子加 1，大約 3 萬多條指令。

但這種寫法有一個問題：**它存取的記憶體位址由樣本決定**。在有快取的處理器上，攻擊者可以從時間差推測樣本的值；而這些樣本正是之後要當作亂數種子的東西。

這個 repo 有一個證明過的檢查器 `lean/Rv32/Ct.lean`（exp207），它會拒絕「分支或位址跟祕密有關」的程式。直接用索引的直方圖過不了，這件事本身也證明了（`naive_refused`）。

所以 kernel 換一種數法：**對每一個值，把所有樣本都看一遍**，看到相等就加 1，比較時不分支（`(樣本 xor 值) <u 1` 剛好是 1 或 0）。找最大值也不分支：

```
mask = −(目前最大 <u 這次的次數)      全 1 或全 0
目前最大 ^= (這次的次數 ^ 目前最大) & mask
```

代價是 256 × 4096 次比較，總共 6,294,284 條指令，是直接數法的大約 190 倍。換來的是：**不管樣本是什麼，每一步的 pc、每一個存取的位址都一模一樣**（`count_constant_time`）。

## 4. 證明了什麼

主要定理 `Count.from_boot`，白話是：

> 不管 4096 個樣本是什麼，kernel 都在**恰好 6,294,284 條指令**後以 0 停下。停下時，記憶體恰好是「原本的映像檔，加上 256 個次數和最大的那個」，其他一個位元組都沒變。

另外兩個關於規格本身的定理，用來確認「規格寫的就是我們想的」：

- `most_is_max`：沒有任何值的次數比「最大次數」多，而且確實有某個值剛好出現那麼多次；
- `hist_sum`：256 個次數加起來剛好是 4096，每個樣本都恰好被數了一次。

還有 12 個故意寫錯的版本，Lean 全部拒絕。例如：
- 用有號的 `lb` 讀樣本，128 以上的值會被當成別的值；
- 比較時用 `<u 2`，比某個值大 1 的樣本也會被算進來；
- 指標前進的量由比較結果決定，變成和樣本有關的位址；
- 最大值的遮罩只有 1，不是全 1。

## 5. 樣本從哪裡來：有沒有經過平衡器

RP2350 的 TRNG 預設開著自己的三個測試，其中一個是 **von Neumann 平衡器**：每兩個位元一組，`01` 輸出 0、`10` 輸出 1、`00` 和 `11` 丟掉。不管雜訊源本身多偏，平衡器的輸出幾乎都是 0 和 1 各半。

問題是：SP 800-90B 估的是**原始資料**（raw data），也就是雜訊源數位化之後、還沒經過任何處理的輸出。對平衡器的輸出做估計，估到的是平衡器，不是雜訊源。

所以 shell 每一輪取兩種樣本：

- **TRNG，測試開著**：和 vk26-alice-1、2 一樣，經過平衡器；
- **TRNG，原始**：設定 TRNG_DEBUG_CONTROL 的第 1 到 3 位元，把平衡器和另外兩個測試都旁路掉。

這個 repo 從來沒有旁路過平衡器，原始位元在這塊板子上長什麼樣子，要上板才知道。這是這個實驗**唯一沒有事先預測**的結果。

**上板的結果**：原始位元偏向 0。兩次各 32,768 個位元，是 1 的比例是 48.23% 和 48.41%；如果位元彼此獨立，分別離「一半一半」6.4 和 5.8 個標準差。每位元的 MCV 估計是 0.930 和 0.935；測試開著的三次是 0.962 到 0.980，1 的比例是 49.54%、50.00%、50.61%。

有趣的是，**以位元組為樣本時看不出差別**：五次 TRNG 的每位元組估計都在 6.50 到 6.71 之間。4096 個位元組太少，看不到這麼小的偏差；以位元為樣本才看得到。（這正是第 10 節第 4 題。）

## 6. 時間：證明說的與晶片量到的

證明說：樣本不會讓 kernel 多走或少走任何一步。在沒有快取的 Hazard3 上，這應該代表**每條樣本流花的週期數完全一樣**。

- **RTL**：12 條測試流、shell 的 5 條流，全部都是 7,343,633 個週期。
- **晶片**：exp212 在 Pico 2 上量過別的 kernel。發現種子不影響週期數，但開機後**第一次**計時會比較多（快取還是冷的），而且晶片的數字和 RTL 不同。

所以網頁的預測是：除了開機後第一條流，每條流的 `mcycle` 都是同一個數字。這個數字不一定等於 RTL 的。

**上板的結果：預測沒有成立。** 13 條流出現三個數字，比 RTL 多 64、164、184 個週期。關鍵是「位元三成為 1」這條固定樣本流，每一輪的 4096 個位元組完全一樣，卻花了 +164、+64、+184。

這反而是證明的旁證：同樣的樣本花不同的時間，所以差別**不是樣本造成的**，而是 kernel 執行軌跡以外的東西在變。最符合的解釋是 exp212 寫過的：計時範圍包含 harness 的 `mret` 和 trap 入口，晶片上這兩條指令從 flash 經 XIP 快取讀取；快取裡有沒有它們，取決於 shell 之前做了什麼，而這裡每條流之前做的事不一樣。但這次的資料**沒有辦法單獨證實**這個解釋。

下一版（還沒做）可以這樣分辨：每條流連續跑兩次 kernel，兩次都回報。如果第二次永遠是同一個數字、只有第一次在變，就是 shell 留下的快取狀態。

我們沒有把檢查改成「接受三個數字」，也沒有編一個容許範圍：預測錯了就寫錯了。check.sh 對板上紀錄只嚴格檢查計數，週期數照實印出來。

## 7. 誰在檢查誰

| 誰 | 怎麼寫的 | 檢查什麼 |
| --- | --- | --- |
| `count.py` | 照 §6.3.1 的文字 | 12 條測試流的次數、最大值、兩種 H |
| Lean 模型與 Hazard3 RTL | 同一個 `kernel.bin` | 停止碼、指令數、整個 64 KiB 區域、RTL 的週期數都一樣 |
| shell（C） | 自己再數一次 | 晶片上每條流的 256 個次數 |
| 網頁 `count.html` | JavaScript，再數一次 | 板子送來的次數；週期數是否一致；§6.3.1 自己的例子 |
| `fixtures.py --board` | count.py 再數一次 | 手機存回的紀錄裡每條流的次數；週期數與熵估計照實印出 |

順帶一提：§6.3.1 的例子（L = 20，p̂ = 0.4）先寫 p_u = 0.6895，下一行卻寫 log2(0.6822)。0.6895 才對，H = 0.5363 也對；標準的文字有個小筆誤。

## 8. 代價與限制

- **晶片的週期數為什麼會變**：證明排除了樣本，板子顯示同樣的樣本也會變；原因還只是假設。
- **一塊板子、兩次原始抽樣**不足以說這顆 TRNG 一般都偏向 0。
- **公式沒有證明**：count.py 和網頁算出一樣的答案，也都和 §6.3.1 的例子吻合，但那是兩份實作互相比對，不是證明。
- **4096 個樣本不是評估**：SP 800-90B §3.1.1 要求至少一百萬個原始樣本。這裡只是「看一眼」。
- **一個位元組不是這個雜訊源的樣本**：TRNG 是二元的，90B 的樣本是一個位元。網頁也算每位元的估計，但兩者都只是參考。
- **慢**：一次 630 萬條指令，晶片上大約 0.7 秒。
- **常數時間只對這顆處理器的觀察者成立**：沒有快取、沒有隨資料改變的延遲。證明說的是步驟，時間要靠 RTL 和晶片去量。

## 9. 這個實驗在試跑裡的角色

做這個實驗時找到的徵集設定問題：

- **原始 TRNG 沒有共用的地方可放**：共用的驅動程式沒有旁路選項，而 S2 不讓提案改 `tools/`。所以 `trng_raw.h` 放在 alice 自己的目錄，重用 `trng.h` 的設定和讀取函式，而不是整份複製。
- **函式名稱撞名**：`image` 已經有九份，這裡改名 `count_image`。
- **Lean 的三個新提醒**（已寫進徵集 README，獨立 commit）：
  - `lean.sh check` 只顯示錯誤的第一行，要看完整訊息得在套件目錄下直接執行 `lake env lean`；
  - Ct 檢查器知道 `lui` 的值，卻不知道位移的結果；
  - 在 `List.range 256` 上直接歸納會逾時，要先對一般的長度 K 證明。

## 10. 給學生的思考題

1. 如果樣本全都是同一個值，H 是多少？如果 256 個值各出現 16 次呢？為什麼後者算出來不是剛好 8？
2. 直接索引的直方圖在 Hazard3 上其實時間也是固定的，因為沒有快取。那為什麼還要證明常數時間？什麼情況下這個證明才有意義？
3. von Neumann 平衡器會讓輸出看起來很均勻。如果只看平衡器的輸出，你能不能分辨一個好的雜訊源和一個壞掉、但偶爾還會跳動的雜訊源？
4. 把 8 個位元合成一個位元組當作樣本，和把每個位元當作樣本，估出來的熵為什麼可能不同？哪一個比較保守？
