## 一、從神田明神「IT情報安全守護」與台灣「綠色乖乖」談起

在東亞的資訊工程文化中，有兩件極具代表性的實體「科技護身符」：

1. **日本東京神田神社（神田明神）的「IT情報安全守護（IT情報安全守護）」**：
   * **外觀與極客美學**：採用深綠色 PCB（印刷電路板）走線紋路與金色 IC 晶片圖騰設計，充滿硬體工程師熟悉的極客（Geek）氛圍。
   * **內容組合**：一份包含 **1 個卡片型御守**（放錢包或識別證套）與 **2 張專用貼紙**（一大一小，直接貼在筆記型電腦、機房伺服器機櫃或手機背蓋上）。
   * **祈求功效**：防止電腦中毒、系統當機、網路斷線、資料受干擾（Data Corruption）以及資訊外洩。
2. **台灣科技業與機房的「綠色乖乖」**：
   * **儀式規則**：必須是**綠色包裝**（椰子口味，代表系統指示燈長亮綠燈，忌用黃色或紅色），必須**不能過期**，且**絕不能拆封吃掉**。
   * **擺放位置**：直接壓在伺服器主機、交換器、提款機（ATM）或實驗室關鍵設備上方。

工程師比誰都清楚，貼紙裡沒有防火牆，玉米脆果也不會攔截封包。它們之所以存在，是因為複雜系統總有「測試涵蓋不到、規格沒寫清楚、硬體偶發異常」的未知邊界；在盡了人事之後，人們需要一個具象的物件來安頓心理焦慮。

## 二、形式化驗證何時會退化成「虛擬安全御守」？

形式化驗證（Formal Verification，如本專案使用的 Lean 4 與 TLA+）常被外界視為資訊安全的終極聖杯：「經過數學證明、絕對不會出錯的程式碼」。

但正如 `exp232`（[被證明的藥，和沒被證明的世界](../exp232-the-cure-the-proof-predicts/WHY.zh-TW.md)）所展示的：**「被 Lean 證明過」的意思永遠只是：那一句話（Theorem），在那個模型（Model）裡，對那些位元組（Bytes）成立。**

當開發者、審計人員或使用者把「通過 Lean 4 驗證、零 `sorryAx`」當成一張貼在韌體上的神田明神貼紙，而不再追問**「定理到底限制了什麼、漏掉了什麼」**時，形式化驗證就會退化成**「驗證劇場（Verification Theater）」**——也就是軟體工程裡的**虛擬安全御守**與**數位綠乖乖**。

更微妙的是，我們完全可以在韌體裡寫入一段**「形式化驗證過的無用位元組（Formally Verified Placebo Bytes）」**：

* 它**不是死碼（Dead Code / `nop`）**：CPU 每一輪都會取指、解碼、執行它，甚至為它付出真實的 `minstret` 指令週期。
* 它**有貨真價實的 Lean 4 定理背書**：定理沒有作弊、沒有 `sorryAx`、沒有偷加自訂公理（`#print axioms` 乾乾淨淨）。
* 它**有嚴格的突變測試（Mutant Ratchet）保護**：如果你把這幾個位元組改掉一個 bit，Lean 4 編譯器真的會報錯拒絕！
* **但它在真實系統中毫無安全作用**：移除它不會讓系統變危險，保留它也不會擋下任何一個真正的攻擊。它存在的唯一功能，就是在驗證報告裡多印出一行綠色的 `PASS`，給閱讀報告的人帶來心理安慰。

## 三、四種「證明加持過的安慰劑位元組」剖析

為了在實驗中具體呈現「形式化驗證的邊界」與「規格漏洞（Specification Bugs）」，`exp245` 在同一個 RISC-V M-mode 微監控器（Micro-Monitor）裡放入了四種不同型態的「數位御守位元組」，恰好對應「1 個主御守 + 3 張機櫃貼紙」的組合：

| 編號 | 御守名稱 | 機器碼實際做的事（皆被執行且被證明） | Lean 4 定理宣稱的事（100% 數學為真） | 為什麼它是「虛擬綠乖乖」（規格漏洞與邊界） |
| :--- | :--- | :--- | :--- | :--- |
| **Charm 1**<br>*(Literal 御守)* | **神田明神／綠乖乖封印**<br>`"OMAM"` / `"KUAI"` | 開機時在 M-mode 神龕區 `0x80008010` 寫入 8 bytes 守護常數 `0x4F4D414D` 與 `0x4B554149`；退場前逐字檢查，不符即報 Fault | `seal_intact_on_halt`：任何正常 `HALT` 退場的執行，其神聖守護封印必定完好無損 | **混淆「不相干的不變量」與「系統安全」**：神龕在 M-mode 區，U-mode 本來就碰不到（恆真）；而攻擊者把沙盒內的資料與代碼改得面目全非時，神龕依然完好、系統照常綠燈 PASS |
| **Charm 2**<br>*(硬體遮蔽)* | **壓在底下的 PMP 鐵壁**<br>`pmpaddr1` / `Entry 1` | 開機多花 12 bytes 設定 PMP `Entry 1` 為代碼區 `[0x80010000, +0x80)` 唯讀可執行（`R+X, !W`） | `entry1_forbids_code_store`：PMP 第 1 條目對代碼區的任何寫入請求一律回傳 `false`（拒絕） | **局部定理 vs 全域硬體語意**：RISC-V PMP 規則是「編號最小命中者決定」。因為 `Entry 0` 設了整塊 64 KiB `RWX`（如 `exp236`），硬體在 `Entry 0` 就放行了寫入，永遠不會問到 `Entry 1` |
| **Charm 3**<br>*(組件脫鉤)* | **只擦神桌的清零迴圈**<br>`Sacred Key Slot` | 退場時多花一個迴圈，將沙盒內「法定金鑰槽」`[+0x2180, +0x21a0)` 的 32 bytes 強制歸零 | `sacred_slot_zeroed`：無論正常退場或異常崩潰，法定金鑰槽的每一個 byte 停機時必為 `0` | **組件規格脫鉤（Compositional Gap）**：Monitor 擦了 `+0x2180`，但實際執行的簽章程式把私鑰放在頂部堆疊 `[+0xffc0, +0x10000)`。堆疊在定理裡被歸類為 `Frame`（保證不破壞區），私鑰原封不動外洩 |
| **Charm 4**<br>*(模型失真)* | **自我回音的驗章橡皮圖章**<br>`VERIFY_CHARM (t0 = 4)` | 新增非停機呼叫 `t0 = 4`，檢查緩衝區在沙盒內後，將請求碼 `4` 寫入服務埠 `0xc000001c` 並讀回 `a0` | `verify_charm_always_passes`：在模型中，任何位於沙盒內的守護檢查呼叫，回傳值 `a0` 必非零（通過） | **把 I/O 當成普通記憶體建模**：`PrivMachine` 把服務埠 `0xc000001c` 當成一般 RAM（見 `exp238` README 揭露）。寫入 `4` 再馬上讀同一個位址，讀回來的當然是剛寫進去的 `4`！定理證明了一顆永遠蓋「合格」的橡皮圖章 |

## 四、這四個案例揭示的形式化驗證四大邊界

透過這四段「被證明加持過的無用位元組」，讀者與審計者可以清楚看到形式化驗證無法自動替你守住的四道邊界：

### 1. 局部性質不等於全域生效（Local Property vs. Global Composition）
在 **Charm 2** 中，定理 `entry1_forbids_code_store` 單獨看是完全正確的：它問的是「`pmpEntryCheck` 這個函數對 `entry 1` 的輸出是什麼」。但它沒有問「整顆處理器的 `pmpCheck`（依序檢查 `entry 0..3`）最終輸出是什麼」。
* **教訓**：在閱讀任何形式化驗證報告時，看到「模組 X 的規則 Y 已被證明禁止寫入」毫無意義，除非有一條**端到端（End-to-End）定理**證明「在任何執行步數下，該記憶體位元組的值與初始值相同」（如 [`exp240`](../exp240-the-code-the-box-forbids-writing/README.md) 的 `wx_code_immutable`）。

### 2. 「Frame Condition（未修改保證）」的雙面刃（Preservation vs. Secrecy）
在形式化驗證中，為了讓呼叫者安心，定理通常會包含一條 `Frame` 條件：「除了工作區之外，其餘記憶體皆保持原樣（untouched）」。
在 **Charm 3** 中，`Sacred Key Slot` 被證明清零了，而其餘記憶體被證明「保持原樣」。對功能正確性而言，「保持原樣」是優點；對機密性（Secrecy / Zeroization）而言，**如果秘密放在 `Frame` 涵蓋的區域（例如 Stack），「保持原樣」就等於「保證洩密」**。
* **教訓**：清零證明（如 [`exp239`](../exp239-the-scratch-the-monitor-scrubs/README.md)）只有與 Payload 的「寫入足跡證明（Write Footprint）」接合，確保 Payload 從未把秘密寫到清零區以外的地方，清零定理才不會淪為擦神桌的儀式。

### 3. 環境與 I/O 建模的隱含假設（Environment Modeling Assumptions）
在 **Charm 4** 中，為什麼 Lean 可以證明「每次呼叫回傳的 `a0` 都等於 `4`（非零）」？因為為了簡化模型，MMIO 服務埠 `0xc0000010..0xc000001c` 被建模在同一個扁平記憶體函數 `mem : Nat → UInt8` 裡。
在 [`exp238`](../exp238-the-call-the-monitor-checks/README.md) 的 README 中，作者誠實地把這點列在 *What is not proved* 第二條；但如果有人故意或無意地利用這個模型特性，在規格裡宣稱「已證明驗證呼叫必定成功返回」，外行人只看定理名稱就會以為密碼學驗證已經被證明了。
* **教訓**：凡是跨過硬體邊界（MMIO、外部 Host、亂數源 TRNG、時脈）的讀寫，純記憶體模型的定理只證明了「寫出去的字」與「讀指令的位址」，**從未證明讀回來的值代表什麼意義**。

### 4. 突變測試（Mutants）只能測試「證明有沒有綁緊程式碼」，不能測試「規格有沒有用」
本倉庫從 `exp198` 起建立了嚴格的 `mutants.txt` 機制：故意改錯一行程式碼或一個常數，確認 Lean 會拒絕證明，防止證明寫出空洞的恆真式（Vacuous Truth）。
然而 **Charm 1–4** 展示了更深一層的陷阱：**就算變異體測試全數通過（改掉 `"OMAM"` 常數、改掉 `Entry 1`、改掉清零長度，Lean 全部拒絕），也只代表「定理與這些位元組緊密綁定」，不代表「這個定理對安全有用」**。
* **教訓**：要抓出「證明過的無用位元組」，單靠形式化驗證內部的突變測試是不夠的；必須搭配**「站在攻擊者視角的差分與雙重執行測試」**——直接把這段被證明的位元組整塊拔掉（或注入真實攻擊 Payload），看系統在攻擊下的表現有沒有任何差別。

## 五、給工程師與審計者的「除魅檢查表」

下次當你看到一份專案宣稱「核心位元組已經過 Lean / Coq / Isabelle 形式化驗證」時，請像檢視神田明神的 IT 御守一樣，問這四個問題：

1. **如果把這段被證明的位元組換成 `nop`，哪一個真實世界的安全測試會失敗？**
   * 如果只有 Lean 證明本身會壞掉，但沒有任何攻擊測試會因此打穿系統，那這段位元組就是 Charm 1 / Charm 2 式的數位綠乖乖。
2. **定理的結論是寫在「中間輔助函數（Helper）」上，還是寫在「最終可觀測狀態（Observable State）」上？**
   * 證明「設定了某個暫存器」或「某個檢查函數回傳 `false`」（Charm 2），不等於證明「記憶體不會被改寫」。
3. **定理裡的 `Frame`（不變區）裡，有沒有躺著不該留下的東西？**
   * 證明「A 區被清零」（Charm 3），必須同時證明「B 區從未被寫入秘密」。
4. **定理裡讀入外部世界的地方，模型是怎麼寫的？**
   * 如果模型把 MMIO 埠當成普通 RAM（Charm 4），那所有關於「從該埠讀回之值」的定理都只是在證明它自己剛寫進去的回音。
