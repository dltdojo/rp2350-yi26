## 一、從神田明神「IT情報安全守護」與台灣「綠色乖乖」談起

在東亞的資訊工程文化裡，有兩件很有代表性的「科技護身符」：

1. **東京神田明神的「IT情報安全守護」**：神田明神的氏子區域包含秋葉原電氣街與商業區，從平成 14 年（2002 年）
   起正式授與這款守護 IT 資訊的御守，祈求的是系統不出故障、資訊不外洩、病毒不入侵
   （[IT Leaders 報導](https://it.impress.co.jp/articles/-/27423)）。它的設計逐年更換：2003 年版是一張 IC 卡形狀的
   護符，加上一張長方形與一張小正方形的貼紙，共三件；2002 年版則是卡片加一張長方形貼紙
   （[PC Watch，2003 年](https://pc.watch.impress.co.jp/docs/2003/0401/uocchi/hothot.htm)）。
   本文只用到「一張卡、幾張貼在機器上的貼紙」這個結構；現行版本的外觀與價格，以神社公告為準。
2. **台灣科技業與機房的「綠色乖乖」**：
   * **儀式規則**：必須是**綠色包裝**（椰子口味，代表系統指示燈長亮綠燈，忌用黃色或紅色），必須**不能過期**，
     且**絕不能拆封吃掉**。
   * **擺放位置**：直接放在伺服器主機、交換器、提款機或實驗室的關鍵設備上。

工程師比誰都清楚，貼紙裡沒有防火牆，玉米脆果也不會攔截封包。它們之所以存在，是因為複雜系統總有「測試涵蓋不到、
規格沒寫清楚、硬體偶發異常」的未知邊界；盡了人事之後，人需要一個具體的東西來安頓焦慮。

## 二、形式化驗證何時會退化成「虛擬安全御守」？

形式化驗證常被當成資訊安全的終極答案：「經過數學證明、絕對不會出錯的程式碼」。

但正如 `exp232`（[被證明的藥，和沒被證明的世界](../exp232-the-cure-the-proof-predicts/WHY.zh-TW.md)）所說：
**「被 Lean 證明過」的意思永遠只是：那一句話，在那個模型裡，對那些位元組成立。**

當開發者、審計人員或使用者把「通過 Lean 4 驗證、零 `sorryAx`」當成一張貼在韌體上的御守貼紙，不再追問
**「定理到底限制了什麼、漏掉了什麼」**時，形式化驗證就退化成**驗證劇場（Verification Theater）**。

更微妙的是，我們可以在韌體裡寫入一段**形式化驗證過的無用位元組**：

* 它**不是死碼**：CPU 每一回合都取指、解碼、執行它，為它付出真實的指令週期。
* 它**有真正的 Lean 4 定理背書**：沒有 `sorryAx`，沒有自訂公理。
* 它**受突變測試保護**：改掉其中一個常數或一條指令，Lean 就拒絕。
* **但它對 payload 能做的事毫無影響**——而且這一點**也能在 Lean 裡證明**。

最後一點是 exp245 想讓讀者帶走的東西：要揭穿一段被證明的位元組，不一定要走出證明。換一條定理來問，常常就夠了。

## 三、三種「被證明加持過的安慰劑位元組」

exp245 以 [exp240](../exp240-the-code-the-box-forbids-writing/) 的 W^X monitor 為基底，放入三組御守。這三組對應
御守的結構：一張卡（Charm 1，名字本身就是御守），兩張貼紙（Charm 2、3，貼在機器真正的部位上）。

| 編號 | 名稱 | 機器碼做的事（被執行、被證明） | 御守定理說的事（為真） | 揭穿定理說的事（也為真） |
| :--- | :--- | :--- | :--- | :--- |
| **Charm 1**<br>卡片 | **神龕封印**<br>`"OMAM"` / `"KUAI"` | 開機在 M-mode 的 `0x80008010` 寫入兩個字組；HALT 前逐字檢查，不符就報 FAULT | `halt_requires_shrine`：任何以 HALT 退場的執行，封印必定完好 | `shrine_always_intact`：從 reset 可達的每一回合，封印都完好。U-mode 本來就寫不到那裡，所以檢查永遠通過 |
| **Charm 2**<br>貼紙 | **被遮蔽的 PMP 條目**<br>entry 3 | 開機把 seed 視窗 `[+0x100, +0x200)` 設成 entry 3、只讀 | `entry3_forbids_seed_store`：entry 3 對 seed 視窗的任何寫入都說「不准」 | `pmpCheck_shadowed`：entry 3 整個落在 entry 1 裡，而 PMP 由編號最小且命中的條目決定，所以 entry 3 永遠輪不到說話 |
| **Charm 3**<br>貼紙 | **擦錯神桌的清零**<br>神聖金鑰槽 | 每次退場清零 data 裡的 32 bytes `[+0xe00, +0xe20)` | `slot_zeroed_on_exit`：每次停機槽都是零，其餘記憶體保持原樣 | `stack_reaches_next_round`：payload 放在堆疊上的私鑰被「保持原樣」，下一回合讀得到 |

三組裡有兩組，前作早就以別的形式寫下了：條目順序決定一切，是 exp240 的 `entries_swapped` 與
`pmp_entries_tried_backwards`；frame 條件留下秘密，則是 exp236 的註解 "memory the payload wrote stays where it
is"，以及 exp239 `monitor_scrub` 的定理形狀。exp245 的工作是把它們放在一起，各自配上一條揭穿定理。

## 四、第四個御守，為什麼沒有放進 monitor

最初的設計還有一組 Charm 4：一個 `VERIFY_CHARM` 系統呼叫，把請求碼寫到服務埠、從同一個字組讀回答案，答案非零就算
「驗證通過」。在模型裡，服務埠就是記憶體，讀回來的就是剛寫進去的請求碼，所以 Lean 能證明「這個驗證永遠通過」。
這正是 [exp238](../exp238-the-call-the-monitor-checks/README.md) 在 *What is not proved* 裡自己寫下的一條：
"the model reads back the request it just wrote"。

它沒有放進 exp245，原因有三個：

1. **exp240 只服務 HALT。** 要加一個不停機的呼叫，就要把 exp238 的呼叫機制（存 t0..t3、`trap_return`、範圍檢查）
   合進 exp240，monitor 和證明都會大很多，換來的卻只是一個 exp238 已經揭露過的事實。
2. **在模擬器上，這些位元組其實有作用。** `tools/monitor/emulator.py` 只模擬 `0x80000000` 起的 256 KiB；
   對 `0xc000001c` 的寫入是匯流排錯誤，會走進 fault。exp238 的 `ServiceEmulator` 則把讀和寫分開，讀回的是 host 的
   答案；對垃圾資料，答案是 0，`beqz` 就拒絕了。所以安慰劑是**定理**，不是**位元組**，這和 Charm 1–3 是不同的一課。
3. **它真正的教訓是協定設計。** 答案和請求放在同一個字組時，「沒有 host 回應」就等於「讀回請求碼」，而請求碼不是零。
   只要有人把「非零」當成「通過」，沒有 host 的時候就會放行（fail-open）。修法是讓「通過」的值與任何請求碼都不同，
   例如只認 `a0 == 1`。exp238 的 `CHECKSIG` 有同樣的形狀（請求碼 3，答案 1 或 0，同一個字組）；**exp238 的呼叫者
   是怎麼解讀 `a0` 的，本實驗沒有查**，留作回頭檢查 exp238 的待辦。

## 五、這幾組案例揭示的邊界

### 1. 局部性質不等於全域生效
**Charm 2** 的 `entry3_forbids_seed_store` 單獨看完全正確：它問的是「entry 3 對這個存取說什麼」。它沒有問「整個
`pmpCheck` 依序問過 entry 0..3 之後說什麼」。
* **教訓**：「某條規則禁止寫入」沒有意義，除非有一條端到端定理說「這些 byte 在任何步數之後都沒變」，例如 exp240 的
  `wx_code_immutable`。

### 2. Frame 條件是雙面刃
**Charm 3** 的槽被證明清零了，其餘記憶體被證明「保持原樣」。對功能正確性，這是優點；對機密性，**秘密若放在 frame
涵蓋的地方，「保持原樣」就等於「保證留下」**。
* **教訓**：清零定理要和「U-mode 能寫到哪裡」接起來才有意義。exp240 讓這個集合可以逐一列出（`wx_store_ok`），所以
  「每一個 U-mode 能寫的 byte 停機時都是零」是一條寫得出來的定理。那才是修法。

### 3. 環境與 I/O 建模的假設
見第四節。凡是跨過硬體邊界的讀取（MMIO、外部 host、亂數源、時脈），純記憶體模型只證明了「寫出去的字」和「讀的
位址」，**從未證明讀回來的值代表什麼**。

### 4. 突變測試抓不到沒用的位元組——只要突變只對著御守自己的定理跑
本倉庫從 `exp198` 起用 `mutants.txt`：改錯一行程式碼，確認 Lean 拒絕，防止證明變成空洞的恆真式。exp245 的突變
全部會被拒絕。但要注意**為什麼**會被拒絕：

`shrine_check_skipped`（把驗印的 `bne` 換成 `nop`）被拒，是因為 `halt_requires_shrine` 是從**任意**陷阱狀態出發寫的，
包括封印已經被改掉、而現實中到不了的狀態。把同一個突變拿去對照從 reset 出發的定理（`shrine_always_intact`、
`monitor_end_to_end`），結論不會變：在可達的狀態裡，那個 `bne` 本來就不會跳。

* **教訓**：突變測試量的是「定理和位元組綁得多緊」。要知道位元組有沒有用，就要問一條**從 reset 出發、講可觀測
  結果**的定理：拿掉這些位元組，它還成不成立？成立，就是一段被證明的安慰劑。

### 5. 「沒有作用」本身也是相對於模型的主張
PMP 只約束一顆核心。在 RP2350 上，DMA、另一顆核心、故障注入都可能改到 `0x80008010`；在那裡，Charm 1 的 18 個字組
是一個 canary，會把 HALT 變成 FAULT。DESIGN 的 Act 1b 在模擬器上量這件事。
* **教訓**：「這段位元組沒用」和「這段位元組被證明了」是同一種句子，都要說出是在哪個模型、哪個威脅模型下。批評驗證
  劇場的人，自己也會演出同一齣戲。

## 六、給工程師與審計者的除魅檢查表

下次看到「核心位元組已經過 Lean / Coq / Isabelle 形式化驗證」，請像看待一張 IT 御守那樣問：

1. **這條定理是從 reset 出發的，還是從某個中間狀態出發的？**
   * 從任意中間狀態出發的定理，可能在描述一個永遠到不了的情況（Charm 1）。
2. **結論寫在輔助函數上，還是寫在最終可觀測的狀態上？**
   * 證明「某個檢查函數回傳 `false`」（Charm 2），不等於證明「記憶體不會被改寫」。
3. **定理的 frame 裡，有沒有躺著不該留下的東西？**
   * 證明「A 區被清零」（Charm 3），還要證明「秘密只會寫在 A 區」。
4. **定理讀入外部世界的地方，模型是怎麼寫的？**
   * 模型若把 MMIO 當成普通記憶體（第四節），所有關於「從那裡讀回的值」的定理，證明的都只是回音。
5. **把這段位元組拿掉，哪一條從 reset 出發的定理、哪一個攻擊測試會有不同結果？是在什麼威脅模型下？**
   * 兩邊都沒有不同，才可以說它在**那個模型下**沒有作用；說的時候也要把模型講出來（第五節第 5 點）。
