# 接下來：B 與 C 的規劃

<!-- SPDX-License-Identifier: Apache-2.0 -->

exp225 是在台中市立美術館真鍋大度「關係時態——超越模擬的生命形式」展場裡完成的。當時腦力激盪了五個實驗方向，現場做完的是 A（人工生命的心跳）。這份文件記下 **B** 和 **C** 的規劃，下次有機會可以直接接著做。

開工前仍要照 [experiments/README.md](../README.md#how-this-repository-is-developed) 的流程：先讀前例，再問 2 到 4 個問題，不要直接照這份文件動手。這裡寫的是當時的想法和已經查到的事實，不是定案。

## 當時的五個方向

| 代號 | 名稱 | 對應展間 | 狀態 |
| --- | --- | --- | --- |
| A | 人工生命的心跳：Rule 30 | A 展覽室：人工生命的對話 | **完成（exp225）**，板子上不規則閃爍 |
| B | 因你而改變的生命：按鈕播種 | B 展覽室：因你而改變的共享生態系 | 本文件 |
| C | 果蠅的動作偵測：Reichardt 偵測器 | C 展覽室：果蠅視覺模型 | 本文件 |
| D | 被證明的時間：LED 的拍長就是指令數 | 展名「關係時態」 | 已經併進 A：每段生命都核對 `minstret` |
| E | 共享生態系：兩個物種互不干擾 | B 展覽室 | 證明最重，約 3 小時以上，暫不排入 |

## 從 exp225 學到、下次可以直接用的事

- **手機燒錄可行。** 在展場用 Pixel 9a（Android）的檔案管理員，把 UF2 複製到 `RP2350` 磁碟就成功了，不需要 `pflash.html` 或 WebUSB。iPhone 還沒試過。
- **進 BOOTSEL 後要馬上複製。** 手機螢幕休眠時板子會離開燒錄模式（[docs/debugging-on-a-phone.md](../../docs/debugging-on-a-phone.md)）。
- **證明的骨架可以照抄 exp225 的結構。** 具體做法：
  - 用 `setup` / `body` / `stepLine` / `finishLine` 等具名片段組成 kernel；
  - 迴圈用 `Inv` 加 `iter`，再用 `loop` 做歸納；
  - 寫入記憶體用 `overlay` 和 `overlay_step`；
  - 停下用 `halts_at`。

  exp225 的證明在一個工作階段內就完成了。
- **LED 的協定已經有了。** 正常時是生命的節奏；檢查失敗是「閃 N 下後停頓」；shell 自己出錯是常亮；沒跑起來是全暗。
- **錄製擷取很快。** `run.sh` 用 `capture_tee` 和 `LEAN_VERDICTS`，exp225 錄一次只要 40 秒。

## B｜因你而改變的生命：觀眾按 BOOTSEL 播種

### 想法

觀眾按 BOOTSEL 按鈕。shell 記下按鍵的時間點，算成一個 32 位元的種子，從這個種子長出一段 Rule 30 生命，在 LED 上播放。每個人按的節奏不同，長出的生命就不同。

### 一個關鍵發現：證明的部分其實已經做完了

exp225 的 `lives` 定理對**任何種子**都成立：不管種子是什麼，kernel 都正好跑 3079 個指令停下，寫出那個種子的 256 代生命，其他記憶體一個位元組都不動。所以觀眾的輸入**不可能**讓 kernel 跑出圍牆、跑更久，或寫到不該寫的地方。這正是 B 想展示的事，而且已經被證明了。

B 真正的新工作在 shell，不在證明：

1. **讀 BOOTSEL 按鈕（風險最高）。**
   - BOOTSEL 不是一般 GPIO，它接在 QSPI flash 的片選線（CS）上。要讀它，得暫時讓那條線浮接、取樣再還原；這段期間 flash 不能讀取。
   - 偏偏 shell 本身就是直接在 flash 上執行的（XIP），所以取樣程式**必須放在 SRAM 裡執行**。
   - 前例：
     - [exp106](../exp106-bootsel-button/) 用 `crates/bootsel` 做過，但那是 ARM（cortex-m）的 Rust 版，RISC-V 的 C shell 不能直接用。
     - [exp211](../exp211-the-leaf-signed-once/) 的 shell 已經示範過「把一小段組合語言（`flash_rom.S`）複製到 SRAM 再呼叫」，可以照這個模式寫取樣程式。
     - `tools/hazard3/shell/link_chip.ld` 規定 shell 不能有需要從 flash 複製的 `.data`，所以要用 exp211 那種「執行時自己複製」的做法。
2. **把按鍵變成種子。** 有兩種做法：
   - 在 C 裡把按鍵間隔（`mcycle` 差值）摺疊成一個 word，不證明，屬於「蒐集事實」，就像 exp224 的 shell；
   - 另寫一個小的已驗證 kernel 做混合（例如每次按鍵做一次旋轉加 XOR），證明「種子正好是按鍵序列的這個函數」。工作量約多 1 小時。
3. **互動方式要讓人看得懂。** 例如：
   - 按下時 LED 快閃一下，表示收到了；
   - 停止按鍵 2 秒後，用這個種子開始新的一段生命；
   - 生命播放中再按，就重新播種。
4. **檢查要調整。** 觀眾播下的種子無法事先用 Python 算好，所以：
   - 開機時第一段生命仍用固定種子，對照 Python 的雜湊（和 exp225 一樣）；
   - 之後每段生命都核對 `minstret` = 3082；
   - 可以考慮讓 C 用逐格寫法自己算一份 Rule 30 來對照。但這是 C 在檢查已驗證的 kernel，要在 README 寫清楚它的角色。

### 備案：不用按鈕

如果讀 BOOTSEL 在 RISC-V shell 上卡住，可以改用晶片內建的溫度感測器（ADC 第 4 通道，[exp108](../exp108-adc-temperature/) 讀過）：觀眾用手指捂住晶片，溫度的變化就是輸入。缺點是反應慢（要幾十秒）、變化小，但完全不碰 flash，沒有讀按鈕的風險。

### 估計與風險

- **估計：** 按鈕取樣程式 1 到 2 小時（大多是 C 和組合語言），如果加上已驗證的混合 kernel 再 1 小時。
- **需要上板確認：** 取樣程式有沒有讓 flash 恢復正常，只能在板子上看到。照 AGENTS.md 的規定，**先把 LED 的除錯模式設計好**：在可能卡住的步驟前先點亮 LED，失敗時的閃法要帶步驟編號。這樣「死在第幾步」才看得出來。
- **待決定的問題：**
  - 種子混合要不要證明？
  - 按鍵結束的判斷用幾秒？
  - 一段生命播完後，要繼續延用最後一代，還是等下一個人？

## C｜果蠅的動作偵測：Reichardt 偵測器

### 想法

C 展覽室用果蠅視覺模型感知觀眾位置。果蠅視覺最經典的模型是 **Hassenstein–Reichardt 基本運動偵測器（EMD）**：

- 相鄰兩個感光點，一個訊號先延遲，再和另一個相乘；
- 兩個方向各算一次，相減；
- 正負號代表運動的方向。

做一個已驗證的 EMD kernel，證明它的輸出正好等於規格。

### 具體設計（1 位元版本，不需要乘法）

刺激是一列 32 格的明暗（一個 word），隨時間變化：s₀、s₁、…。在 1 位元時，「相乘」就是 AND：

- 往高位元的相關：`rotl(s_{t-1}, 1) & s_t`，即上一刻在 i、這一刻在 i+1；
- 往低位元的相關：`rotr(s_{t-1}, 1) & s_t`；
- 輸出：`R_t = popcount(往高位元) − popcount(往低位元)`，把整段時間的 R_t 加總。

為了不和 Rule 30 的「左、右鄰居」混淆，這裡一律說「往高位元、往低位元」。在 exp225 的定義裡，第 i 格的左鄰居是 i+1，所以「往高位元」就是 Rule 30 說的「往左」。

要證明的定理：
1. kernel 對任何刺激序列，輸出都等於規格的加總（和 exp225 的 `lives` 同一型）；
2. **語意性質：** 如果刺激每一刻都往高位元移一格（`s_t = rotl(s_{t-1}, 1)`，而且不是全 0 或全 1），輸出一定是正的；往低位元移則一定是負的。這一條才真正說出「它偵測運動方向」。

未知最大的是 **popcount**。用不需分支的 SWAR 寫法（`x - ((x >> 1) & 0x55555555)` 之類）可以算 popcount，但要證明它正確需要一些位元運算的引理。也可以改成逐位元迴圈，證明容易但指令數多。開工時先試 SWAR 的引理，卡住就換迴圈。

另一個版本是多位元的亮度（例如每格 8 位元），用 RV32M 的 `mul` 做真正的相乘。Lean 模型已經有 `mul`（`aluR` 的 `.mul`）。這比較貼近原始模型，但證明會牽涉乘法的溢位。

### 刺激從哪裡來

板子上沒有感光元件，所以刺激只能是內建的：

1. **內建的移動條紋**：往高位元移、往低位元移、閃爍（不動），各一段。LED 顯示判斷：例如快閃 = 往高位元、慢閃 = 往低位元、閃 N 下 = 看不出方向。用來確認偵測器在晶片上的行為和證明一致。
2. **讓果蠅看 Rule 30（把 A 和 C 接在一起）**：把 exp225 的生命一代代當作刺激餵給 EMD，讓「合成的果蠅」判斷這段人工生命在往哪邊動。這個方向最有展覽感：一個已驗證的生命，被一個已驗證的觀察者看著。

   離開展場後先用 Python 試算過，結果很明確：
   - 從 exp225 的種子 `0x10000` 起，256 代裡有 255 代的 R_t 為正，0 代為負；另外兩個種子分別是 254 代和 255 代為正，同樣沒有負的。
   - 再測 20 萬個隨機的 32 格狀態，每個只算一步：**沒有一個是負的**，有 209 個剛好是 0。

   這不是巧合，而是可以證明的事實，正好當作 C 的定理目標。

   > **猜想（看起來成立）：** 對任何 32 位元狀態 x，令 y 為 x 的下一代，則 `popcount(rotl(x,1) & y) ≥ popcount(rotr(x,1) & y)`。也就是說，果蠅看 Rule 30，永遠覺得它「往高位元走或不動」。
   >
   > **論證草稿：** y_i = x_{i+1} XOR (x_i OR x_{i-1})。
   > - 若 x_{i-1} = 1，則 y_i = NOT x_{i+1}：往高位元那一項 = NOT x_{i+1}，往低位元那一項 = 0。
   > - 若 x_{i-1} = 0：往高位元那一項 = 0，往低位元那一項 = x_{i+1} AND NOT x_i。
   >
   > 所以「往高位元」的總數 = 間隔 2 的 (1, 0) 配對數，「往低位元」的總數 ≤ 間隔 2 的 (0, 1) 配對數。在圓環上沿間隔 2 繞一圈，1→0 和 0→1 的次數一定相等，所以前者 ≥ 後者。
   >
   > 這個論證還沒寫成 Lean。
3. **真實的光**（未來）：需要外接光敏元件接 ADC，或用 LED 反向偏壓當感光器的技巧。都需要額外零件或未驗證的電路行為，不在這次範圍內。

### 估計與風險

- **估計：** 2 到 3 小時，其中 popcount 的證明是最大的未知。
- **風險低：** 輸出只用 LED，輸入是內建的，不碰 flash，也不需要新的硬體驅動。
- **待決定的問題：**
  - 1 位元版本還是 8 位元加乘法？
  - 刺激用內建條紋、Rule 30，還是兩者都要？
  - LED 怎麼呈現方向：快慢閃，還是閃的次數？

## 如果下次只有一點時間

建議的順序：

1. **先做 C 的 1 位元版本，刺激用 exp225 的 Rule 30。** 不碰 flash，風險最低，而且能把 A 和 C 串成一件作品。
2. **再做 B。** 先在桌上（不是展場）把 BOOTSEL 取樣程式上板驗證一次，確認沒問題再帶去現場。B 需要的上板次數最難預估，不適合在現場第一次嘗試。
