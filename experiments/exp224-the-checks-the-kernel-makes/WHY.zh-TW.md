# 為什麼要把 shell 的檢查搬進已驗證的位元組

<!-- SPDX-License-Identifier: Apache-2.0 -->

這份文件寫給學生，說明 exp224 想回答的問題、為什麼往這個方向走，以及這樣做的好處與代價。實驗本身的細節在 [README.md](./README.md)（英文）。

## 1. 先弄清楚：shell 和已驗證的位元組怎麼接在一起

可以把它想成兩個角色：

- **已驗證的位元組（kernel）**：關在密室裡工作的專家。它的每個位元組都有 Lean 定理保證行為。
- **shell（用 C 寫）**：密室外的管理員。它負責準備材料、把專家送進去、等專家按鈴出來，再檢查成果。

兩者之間只靠三個約定接在一起，而這三個約定在 Lean 和 C 兩邊寫的是同一件事：

| 約定 | Lean 裡 | 晶片上 |
| --- | --- | --- |
| 開場狀態 | `boot`：pc 指向區域起點，暫存器除 sp 外全為 0，記憶體就是映像檔 | `harness.S` 的 `enter_payload` 把晶片擺成這個樣子，再用 `mret` 跳進去 |
| 圍牆 | `env.region`：區域外的讀、寫、執行都是 fault | PMP 讓 User 模式只能碰這塊記憶體 |
| 出口 | `ecall`，t0 = 1 代表 HALT，代碼在 a0 | trap 回到 Machine 模式，shell 的 `handle()` 讀出代碼與 `minstret` |

定理只保證一件事：**如果晶片的行為符合 Lean 的機器模型，kernel 就會這樣做**。所以 shell 跑完之後，要在真的晶片上重新檢查定理承諾的每一項，確認這個「如果」真的成立。

## 2. 一個自然的問題：shell 也能用位元組寫嗎？

可以，但**用位元組寫本身並不會讓 shell 變可信，可信要靠證明**。不經過編譯器，只是把「信任編譯器」換成「信任寫位元組的人」。如果那些位元組沒有證明，手寫的出錯機率通常比編譯器還高。

而且這個 repo 的 kernel 早就不經過編譯器了：它在 Lean 裡寫成一串指令，再由 Lean 的 `encode` 轉成位元組。這個編碼器在 exp201 有兩條定理證明 `encode` 和 `decode` 雙向一致，還拿 LLVM 比對了 3450 個指令。真正的價值是：**被證明的對象就是最終執行的那些位元組**，中間沒有任何翻譯可能出錯。

| | C（原本的做法） | 手寫位元組，不證明 | 位元組加上證明 |
| --- | --- | --- | --- |
| 要信任編譯器 | 要（但 UF2 綁定記錄的工具鏈，可重現） | 不用 | 不用 |
| 出錯的主要來源 | shell 本身的邏輯錯誤 | 邏輯錯誤加手工編碼錯誤，風險更高 | 只剩模型和規格本身 |
| 寫起來 | 好讀好改 | 難讀難改 | 還要再寫證明 |

編譯器出錯的機率，遠低於人寫的邏輯出錯。所以單純拿掉編譯器，換來的保證很小；有意義的是「被證明」。

## 3. 為什麼 shell 比 kernel 難證明

難的不在語言，而在 **shell 做的事超出了 Lean 機器模型能描述的範圍**。這個模型開宗明義寫著：一個核心、只有 User 模式、沒有中斷、沒有 CSR、只有一個記憶體區域。

| shell 做的事 | Lean 模型有沒有 |
| --- | --- |
| 在 Machine 模式下執行 | 沒有，只有 User 模式 |
| 設定 PMP、`mtvec`、`mstatus`，用 `mret` 跳進 kernel | 沒有 CSR，也沒有特權切換 |
| kernel 執行 `ecall` 後 trap 回來 | 只說「停下」，沒說「跳到哪裡、存了什麼」 |
| 讀 `minstret` | 沒有 |
| 操作 TRNG、SHA-256 硬體、LED 的暫存器 | 沒有任何周邊裝置 |
| 等 TRNG，逾時就放棄 | 沒有時間的概念 |

所以 shell 的工作要分成三類：

1. **純計算**：例如「這 32 個位元組是否等於那 32 個位元組」「指令數是否等於預期」「依結果決定判定碼」。這些都在現有模型能描述的範圍內，**可以直接搬進已驗證的位元組**。
2. **harness 的進出口**：大約 200 行組合語言，負責架牆、擺開場狀態、處理 trap。要驗證它，得先把模型擴充到 Machine 模式、CSR 和 PMP。工作量大，但範圍明確。
3. **周邊驅動程式**：TRNG、SHA 硬體、LED。這部分永遠只能「照 datasheet 寫，靠實測確認」。就算寫成位元組也證明了，也只是把信任從「C 的驅動」移到「照 datasheet 寫成的模型」，**沒辦法證明模型和真實晶片一致**。

最划算的順序是先做第 1 類。exp224 就是這一步。

## 4. exp224 做了什麼

exp223 的 shell 每跑完一個來源，就用 C 做這些事：

| exp223 的 shell 做的事 | 性質 | exp224 裡由誰做 |
| --- | --- | --- |
| 讀 trap 資訊（是否 HALT、a0）、讀 `minstret` | 要用 CSR、trap | **shell**（蒐集事實） |
| 用 SHA-256 硬體算樣本摘要、算 128KB region 的雜湊 | 周邊裝置 | **shell**（蒐集事實） |
| 用 sha256.c 算 kernel 的雜湊 | 純計算，但需要 SHA-256 程式 | **shell**（蒐集事實；見第 7 節） |
| 三組 32 位元組比對：kernel 雜湊、摘要、region 前後 | 純計算 | **裁判 kernel**（已驗證） |
| 是否為 HALT、代碼是否為 0 或 1 | 純計算 | **裁判 kernel** |
| 指令數是否等於該代碼對應的預期值 | 純計算 | **裁判 kernel** |
| 依來源決定判定碼（1、3、4） | 純計算 | **裁判 kernel** |

新的流程是：

```
 來源 0、1、2 各跑一次 exp223 的 kernel
   shell 只把「事實」寫進一份紀錄（mcause、t0、a0、minstret、各種雜湊……）
       ↓
 三份紀錄都齊了，放進記憶體
       ↓
 裁判 kernel（167 個指令，Lean 證明）讀這三份紀錄
   做 exp223 的五項檢查、找出第一個有問題的來源
   以 HALT 代碼回報：判定 | 來源 << 3 | 失敗的檢查 << 6
       ↓
 shell 只負責把代碼顯示在 LED 上
```

裁判的定理 `judges` 說：**不管紀錄裡寫什麼**，它都會停下，停下的代碼正好是規格 `verdict` 算出的值，而且記憶體一個位元組都沒動。

## 5. 好處

- **判定邏輯有了定理。** exp223 裡「哪一項失敗」「該回報 1、3 還是 4」「哪個來源優先」這些判斷都是 C，沒有證明。現在由 167 個已驗證的指令做，Lean 拒絕了 13 個刻意做錯的版本，例如：
  - 把 t0 = 3 也當成 HALT；
  - 讓代碼 2 也通過檢查 2；
  - 只檢查兩份紀錄；
  - 回報代碼時把來源放錯位元。
- **錯誤 shell 改由裁判抓。** check.sh 裡刻意做錯的 shell（kernel 雜湊不對、指令數多一、壞來源變公平……）不再由 C 自己發現，而是由裁判發現。裁判的代碼還會指出是哪個來源、哪一項檢查。
- **診斷資訊本身也有證明。** 代碼裡的「來源」和「失敗項目」位元，是規格的一部分，不是 C 隨手拼出來的。
- **可信的部分變大，要信任的部分變小。** 需要人讀懂才能信任的 C 判斷邏輯，從整段減少到「蒐集事實」。

## 6. 代價與限制

- **shell 說謊，裁判看不出來。** 裁判只能判斷別人交給它的事實。check.sh 裡有一個刻意的反例：shell 在 kernel 跑完後偷偷改一個位元組，然後把「執行前的雜湊」當成「執行後的雜湊」交給裁判。結果是**慢閃，沒被抓到**。這個反例的意思是：信任從「C 的判斷」移到了「C 的蒐集」，並沒有消失。
- **還有兩處留在 C。**
  - 裁判自己的位元組要和 `judge.sha256` 比對。總得有某個在裁判以外的東西來檢查裁判，否則就是自己審自己。
  - kernel 以代碼 0 停下時，shell 會先清除 SHA 的暫存區再算 region 雜湊。這是根據 a0 做的決定，和 exp223 一樣留在 C。
- **雜湊仍未證明。** kernel 雜湊、樣本摘要、region 雜湊還是由 sha256.c 或 SHA-256 硬體算。裁判只比對它們。
- **證明比程式長得多。** exp223 的 `handle()` 裡做檢查的 C 大約 35 行；裁判的 Lean 證明有大約 800 行。
- **行為有改變。** exp223 遇到第一個錯就停；exp224 把三個來源都跑完，才由裁判一次判定。多跑一次 kernel，也多存三份共 768 位元組的紀錄。

## 7. 接下來可以往哪裡走

1. **把事實的「計算」也搬進去。** 例如 kernel 的雜湊可以改由 exp208 已驗證的 SHA-256 kernel 計算，shell 就少一個要信任的計算。
2. **擴充模型，證明 harness。** 把 Machine 模式、CSR、PMP、trap 加進 Lean 模型，證明 `enter_payload` 真的擺出了 `boot` 狀態。
3. **周邊驅動。** TRNG、SHA 硬體、LED 永遠要靠 datasheet 和板子實測。能做的是縮小它們，不是消滅它們。

## 8. 給學生的思考題

1. 第 6 節的「說謊 shell」為什麼沒被抓到？如果要抓到它，事實要怎麼蒐集才行？
2. 為什麼裁判不能檢查自己的位元組？如果把這一步交給第二個裁判，會發生什麼事？
3. exp223 是遇到第一個錯就停，exp224 是三個都跑完才判定。兩種做法各有什麼好處？
4. 第 3 節的三類工作裡，哪一類你認為最值得先投入？為什麼？
