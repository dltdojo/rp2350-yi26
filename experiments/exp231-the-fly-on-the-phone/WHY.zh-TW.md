# 果蠅上板，再搬到手機上

<!-- SPDX-License-Identifier: Apache-2.0 -->

這份文件用白話說明 exp231 做了什麼。實驗本身的細節在 [README.md](./README.md)（英文）。

## 1. 前情提要

- **exp225**：一支 RISC-V 小程式（kernel）跑 Rule 30，一個 32 格的環，每一代算出下一代，共 256 代。Lean 證明它每一代都算對。
- **exp227**：把這 256 代透過 USB 送到手機，用 `life.html` 一列一列畫出來，網頁自己再算一次 Rule 30 對照。
- **exp230**：另一支小程式，模仿果蠅眼睛偵測移動的方式（Hassenstein–Reichardt 偵測器）。它看相鄰兩個畫面：現在亮著的格子，如果前一刻它下面那格亮著，就算「往上移了一格」；如果前一刻上面那格亮著，就算「往下移了一格」。Lean 證明了三件事：程式算的就是這個偵測器；整條往上平移的畫面一定被看成往上（四種週期為 2 的條紋除外）；而**果蠅看 Rule 30，永遠只會看到往上或不動，絕不會看到往下**。

exp230 只在電腦裡跑（Lean 的模型和 Hazard3 處理器的硬體模擬），沒有上板子。

## 2. exp231 做了什麼

**把果蠅放到真的晶片上，看著真的 Rule 30，再把它看到的東西畫在手機上。**

板子上每一輪做兩件事，用的都是已經證明過的那兩支程式，一個位元組都沒改：

1. 先跑 exp225 的 Rule 30 程式，從一個種子算出 256 代。
2. 再跑 exp230 的果蠅程式，讓它看「種子＋這 256 代」共 257 個畫面，數出每一步往上和往下移動的格子數。

跑完之後，板子上的外殼程式（shell，C 寫的，沒有證明）檢查它看得到的部分：

| 檢查 | 內容 |
| --- | --- |
| 10 | 果蠅程式的位元組和 exp230 記錄的雜湊值一樣 |
| 11 | 它正常結束，回傳 0 |
| 12 | 它剛好執行了 70927 條指令（證明說 70924，加上外殼進出的 3 條） |
| 13 | 第一輪 256 步的每一個計數，都和 Python 算的一模一樣 |
| 14 | **沒有任何一步被看成往下移** |

第 14 項就是 exp230 的定理 `watches_life` 在真的晶片上被檢查：定理說不會發生，板子每一輪都確認一次。

## 3. LED 就是果蠅

每一步一拍（約 0.36 秒）：

- **閃一下**：果蠅看到這一步在往上移。
- **暗一拍**：果蠅看到沒有移動（往上和往下一樣多）。
- **往下**：不會出現在 LED 上——如果真的發生，檢查 14 會先把程式停下來，改成錯誤燈號（亮 2 秒，再閃 14 下）。

所以正常的樣子是**很均勻的節拍**。從一顆亮點開始的第一輪，只有第一步是暗的（一格長成三格，往左往右各算一格，打平）；之後連續十幾輪都沒有任何暗拍。

這和 exp227 的 LED 不一樣：exp227 閃的是 Rule 30 中間那一格，節奏是亂的；exp231 閃的是果蠅的判斷，節奏是穩的。光看 LED 就分得出板子上跑的是哪一個。

## 4. 手機上的網頁 `fly.html`

用 Chrome 打開，按 **Connect** 選板子，之後每一拍出現一列：

- **左邊**是這一代 Rule 30 的 32 格（第 31 位元在最左邊）。
- **中間**是果蠅的「方向表」：往左的藍色長條是往左移（往第 31 位元，也就是 exp230 說的「上」）的格子數，往右的橘色長條是往右移的格子數。看一陣子就會發現：**藍色永遠不比橘色短**——這就是 exp230 證明的定理，畫在你眼前。
- **最右邊的小方塊**是網頁自己的檢查：網頁裡另外寫了一份 Rule 30 和一份果蠅（一格一格照定義寫，不抄任何程式），每一列都重算一次。綠色是對得上，紅色是對不上，灰色是沒有上一列可以對照。
- **Copy** 把網頁的判斷和收到的每一行文字複製起來，可以貼回來給我們。

### 沒有板子也能展示

按 **Demo, no board**，網頁會自己從一顆亮點開始算，用和板子一樣的速度一列一列畫出來。拿來給別人看「果蠅怎麼看 Rule 30」很方便。

但要說清楚：**Demo 是網頁自己算、自己對照自己，所以什麼都沒有檢查到。** 網頁的狀態列、判斷列和 Copy 出來的第一行都會寫明「DEMO, no board」，不會和真的板子資料混在一起。

## 5. 每一層各自保證什麼

| 哪一段 | 誰保證 |
| --- | --- |
| Rule 30 算對 | exp225 的 Lean 證明 |
| 果蠅算對、看 Rule 30 不會看到往下 | exp230 的 Lean 證明 |
| 晶片上跑的就是那些位元組、結果符合預期 | 外殼程式的檢查 1–4、10–14 |
| 從晶片到手機的 C 程式、USB、線材、手機都沒弄錯 | 網頁自己重算的檢查 |

網頁**抓不到程式本身算錯**——如果程式錯了，送出來的資料從一開始就是錯的。那一段由證明和外殼的檢查負責。網頁負責的是「之後的每一段」。

## 6. 目前的狀態

- 在 Hazard3 的硬體模擬上，同一個外殼程式跑了兩輪，每個數字都和 Python 算的一樣；七個故意改錯的外殼，每一個都被它該觸發的那項檢查抓到。
- 網頁在無頭瀏覽器裡、對著一個假的 USB 裝置測過：連線、畫圖、判斷、Copy、Demo 都正常；六個故意改錯的網頁都被測試抓到。

### 第一次上板（round 1）

Pico 2 加一支 Android 手機。網頁連上時，板子開機後的第一輪已經跑到第 63 步，網頁接著收了 100 步（第 63 到 162 步）：

- **100 步全部被看成往上，沒有一步不動，沒有一步往下。**
- 網頁自己重算：99 步對得上，0 步錯，1 步沒得對照（就是收到的第一步）。
- 回到電腦上再用 `rule30.py` 和 `fly.py` 從開機的種子一路算到那 100 步的位置，**每一步的那一代和兩個計數都一模一樣**。
- 狀態列裡 `minstret=70927`：果蠅程式在真的晶片上執行的指令數，和硬體模擬的一條不差。
- 外殼程式要五項檢查都過才會開始播放，所以能收到這些步驟，就表示第一輪在晶片上通過了檢查 13，也就是那一輪所有的計數都和 Python 一樣。

這一輪也抓到網頁的一個問題。畫面下方寫著「this round so far: left 222 · right 111 over 28 steps」。數字本身是對的，`fly.py` 算第 63 到 90 步剛好就是 222 和 111；但網頁是中途加入的，那 28 步只是它看到的部分，不是「這一輪到目前為止」。網頁第 2 版（p2）改成中途加入時寫「steps 64–91 of this round, as this page saw them」，並加了重現這個情況的測試。

還不知道的：一整輪從第 0 步開始的總數和接縫（這次是中途加入，沒收到 LIFE、FLY、SEED 那幾行）——第二次上板補上了。

### 第二次上板（round 2）

同一塊板子（從第一次一路跑下來）、同一支手機，網頁第 2 版。

- **LED 均勻地閃**——就是「果蠅每一步都看到往上移」該有的樣子。
- 網頁在開機後第一輪的第 233 步連上，收到第 233 到 241 步之後，**大約九分鐘什麼都沒收到**，下一行已經是第 6 輪的第 243 步。狀態列寫著 `dropped=208096`：這段時間板子照常計算、照常閃燈，只是沒有人讀 USB，它就把整行整行的資料丟掉，而不是卡住等人——`usbdev.c` 本來就是這樣設計的。20 萬位元組大約就是六輪的 SEES 行加上每秒一行的狀態列。為什麼網頁停了九分鐘，貼回來的資料沒有說；手機螢幕休眠或 Chrome 被切到背景，看起來都會是這樣。
- 網頁把這段記成**一個缺口**，缺口後的第一步標成「沒得對照」，沒有誤判成錯誤。
- 接著第 7 輪開始，LIFE、FLY、SEED 三行完整收到。網頁確認了**接縫**：第 7 輪的種子 `2733d53c` 正是第 6 輪的最後一代。
- 全部 57 步：55 步對得上、0 步錯、2 步沒得對照（第一步和缺口後的第一步），**57 步全部往上**。
- 第 7 輪的 FLY 行說，果蠅整輪看到**往上 1988、往下 990**。網頁只看到這一輪的前 35 步，自己加不出總數；但回到電腦上用 `fly.py` 從開機種子算到第 7 輪，總數一模一樣。也就是說，**一整輪 256 步在真的晶片上的結果，和 Python 完全一致**。
