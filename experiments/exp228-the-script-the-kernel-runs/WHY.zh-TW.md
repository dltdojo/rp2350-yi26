# 經過證明的腳本解譯器，和直接用 Rust 或 C 寫有什麼不同

<!-- SPDX-License-Identifier: Apache-2.0 -->

這份文件用白話說明 exp228 做了什麼，並比較它和直接用 Rust 或 C 寫一支同樣功能的程式差在哪裡：各自保證了什麼、還得信任什麼、要付出什麼代價。實驗本身的細節在 [README.md](./README.md)（英文）。

## 1. 這個實驗做了什麼

比特幣的每筆交易都附帶一小段程式，叫做 **Script**，用來決定「這筆錢能不能花」。節點執行這段腳本，最後得到「接受」或「拒絕」。這個判決一旦錯了，就是共識錯誤，代價可能是真金白銀。

exp228 寫了一個 Script 的**解譯器**，也就是讀腳本、下判決的那支程式，然後用數學證明它判得對。可以把它想成四個角色：

| 角色 | 在這個實驗裡是什麼 |
| --- | --- |
| 規則書 | `proof/Script.lean` 裡的規格 `verdict`：每個操作碼該怎麼做、什麼情況算失敗、失敗代碼是幾號 |
| 裁判 | `kernel.bin`，881 條 RISC-V（RV32IM）機器指令組成的解譯器，在 Pico 2 的 RISC-V 核心上執行 |
| 助理 | 用 C 寫的殼層（`shell/`）。裁判遇到 `OP_SHA256` 或 `OP_CHECKSIG` 時用 `ecall` 問它，由它計算 SHA-256 和驗證 BIP340 簽章 |
| 數學證明 | 定理 `kernel_verdict`：只要腳本不超過 1020 位元組、堆疊不超過 32 個元素、每個元素不超過 80 位元組，裁判對**每一個**這樣的輸入都會停下來，而且停下來時的判決和規則書一字不差 |

### 證明不管助理答得對不對

這是最特別的設計。定理裡，殼層的兩個回答（雜湊值、簽章有效與否）是兩個**完全沒有假設**的函式：不論殼層回報什麼，裁判都會照規則書處理這個答案。

所以證明裡完全不需要 SHA-256 或橢圓曲線的數學，這兩件事交給殼層負責。殼層的 BIP340 驗證器用官方的 19 組測試向量，加上 200 組參考實作產生、其中一半翻轉了一個位元的簽章來檢查，結果全部正確；但它**沒有被證明**。

### 範圍刻意收窄

為了讓證明做得出來，這裡只實作 tapscript 的一個子集：堆疊操作、4 位元組整數的加減、`OP_SHA256`、每個腳本最多一次 `OP_CHECKSIG`。沒有 `OP_IF`，也沒有交易的簽章雜湊（訊息是殼層的一個常數）。而且凡是 tapscript 寬鬆的地方，這個子集都從嚴：子集接受的腳本，tapscript 也會接受；反過來則不一定。**這不是共識實作**，不能拿來取代 Bitcoin Core。

## 2. 證明抓到了測試抓不到的錯

寫 `ENCODE`（把計算結果寫回位元組）的證明時，證明卡住了。往回追才發現：遇到需要獨立符號位元組的數字時，解譯器先寫入符號位元組，再寫入整個 4 位元組的數值字，結果數值字把符號位元組蓋成 0。

- −128 被寫成 `80 00`，那其實是 +128。
- −129…−255、−32768…−65535、−0x800000…−0xffffff 都有同樣的問題。

在那之前，3000 個隨機腳本在 Lean 模型和 Hazard3 RTL 上都和 Python 參考實作一致，沒有一個觸發這個錯，因為隨機產生的腳本幾乎不會拿這種計算結果去和常數比較。

這就是測試和證明的差別：

- **測試**說的是：「我試過的那些都對。」
- **證明**說的是：「範圍內的全部都對。」

錯誤修好之後，`cases.arith()` 補上了本來就該先有的邊界測試，共 672 個腳本。舊的解譯器在模型上錯了其中 110 個，新的一個都沒錯。舊版本也留在 `proof/mutants.txt` 裡，每次檢查都確認證明會擋下它。

## 3. 和直接用 Rust 或 C 寫的差別

### 3.1 保證的東西不同

| | C | Rust | exp228 |
| --- | --- | --- | --- |
| 記憶體安全（不越界、不懸空） | 沒有保證 | safe Rust 有保證 | 證明了：範圍內的輸入不會碰到區域外的記憶體，也不會出錯陷入 |
| 邏輯正確（判決符合規則） | 靠測試 | 靠測試 | **數學證明** |
| 一定會停下來 | 靠測試 | 靠測試 | 證明了 |

關鍵在於：**ENCODE 那個錯不是記憶體錯誤，而是邏輯錯誤。**

用 Rust 寫成「先寫 `buf[4 + n]`，再把 4 位元組寫到 `buf[4..8]`」，編譯會過，執行不會 panic，索引也都在範圍內，就這樣安安靜靜地給出錯的答案。Rust 的型別系統和借用檢查管的是「會不會亂碰記憶體」，管不到「−128 應該編碼成什麼」。

公平地說，這個錯有一部分是低階寫法自己招來的：一次寫一整個字是組合語言層級的最佳化。照 Bitcoin Core 的寫法，用 Rust 一個位元組一個位元組地 push 到 `Vec`，大概不會犯這個錯。低階程式碼製造了更多出錯的機會，而證明把這些機會全部堵上。

### 3.2 證明的對象是真正執行的位元組

用 Rust 或 C 時，就算證明了原始碼，原始碼和晶片上執行的東西之間還隔著**編譯器**。編譯器本身的錯，或者 C 的未定義行為被最佳化器利用，都不在原始碼證明的涵蓋範圍內。

exp228 證明的是 `kernel.bin` 本身，也就是板子上實際執行的那 881 條指令和一張 256 字的分派表：

- 解譯器在 Lean 裡寫成一串指令（由 `kernel.py` 從標籤產生），再由 Lean 的 `encode` 轉成位元組。`encode` 和 `decode` 雙向一致，在 exp201 已經證明過。
- `check.sh` 確認 Lean 產生的位元組和提交的 `kernel.bin` 完全相同。
- 殼層每次執行前都核對 `kernel.bin` 的 SHA-256。

中間沒有任何編譯器或翻譯步驟可以出錯。

### 3.3 信任沒有消失，只是換了位置

證明成立的前提有這幾項，每一項都是「信任」，只是比較少、比較集中：

| 前提 | 怎麼支撐它 | 有沒有證明 |
| --- | --- | --- |
| Lean 的 RISC-V 模型和真正的晶片行為一樣 | 拿模型和 Hazard3 RTL 跑同樣的 3705 個腳本互相對照（需要簽章的只在模型上跑）；上板是下一步 | 沒有，靠對照 |
| 規則書本身寫對了 | 和 Python 參考實作 `script.py` 對照全部 3705 個腳本；`mutants.txt` 故意放進錯的規格，確認證明會擋下來 | 沒有，靠對照 |
| C 殼層：載入腳本、SHA-256、BIP340 | 官方測試向量、隨機簽章、在 RTL 上跑完整個殼層，以及七個故意做錯的殼層版本，確認每個都被抓到 | 沒有，靠測試 |
| Lean 本身 | 只用 Lean 的三個基本公理，不用 Mathlib、`native_decide`、`sorry` | Lean 的核心是整個信任的根 |

如果規則書寫錯，證明只會忠實地證明一個錯的東西。所以這不是「零信任」，而是把信任從「整支程式的每一行」縮小到「幾個小而穩定、可以反覆對照的地方」。

### 3.4 代價

| | Rust / C | exp228 |
| --- | --- | --- |
| 寫一個完整解譯器 | 幾天 | 一個大幅收窄的子集，就要大量工時 |
| 改一行程式 | 重新編譯 | 證明往往要跟著改；光是檢查證明就要約 3 分鐘，七個變異體約 13 分鐘，`check.sh` 全部約半小時 |
| 功能範圍 | 完整 tapscript | 沒有 `OP_IF`、只有 4 位元組算術、只能一次簽章 |
| 誰看得懂 | 一般工程師 | 要同時看得懂 RISC-V 組合語言和 Lean |
| 時間性質 | 不保證 | 同樣不保證：定理只說會停，不說多快；也沒有常數時間的主張 |

### 3.5 中間路線

想要比測試更強、又不想寫組合語言，還有幾種中間做法，例如：

- **Rust**：Kani（有界模型檢查）、Verus、Creusot，或者用 Aeneas 把 Rust 轉成 Lean 再證明。
- **C**：Frama-C、VST，搭配 CompCert 這類經過驗證的編譯器，把保證延伸到機器碼。

這些做法落在「純 Rust」和本實驗之間：寫起來輕鬆得多，但通常保證的是原始碼，除非搭配 CompCert 這類工具，否則編譯器仍在信任範圍內。

## 4. 什麼時候值得這樣做

**適合**：程式小、規則穩定、錯一次代價極高的地方，例如共識規則的判決、開機載入器、簽章驗證的最後一關。

**不適合**：大部分的應用程式。規則常改、功能多、錯誤的代價承擔得起時，用 Rust 加上好的測試，CP 值高得多。

一句話總結：

> Rust 保證程式「不會亂碰記憶體」；exp228 保證這 881 條指令「對每一個輸入都給出規則書上的答案」。後者強得多，也貴得多。
