# 大規模的二進位證明，和本倉庫的 RV32 位元組證明

<!-- SPDX-License-Identifier: Apache-2.0 -->

2026-10-23 的分析。對象是 Anthropic 2026-10-22 發表的
[LLMs are making formal software verification feasible at a much larger scale](https://www.anthropic.com/research/formal-verification)
（以下稱「該研究」）及其[附錄](https://www-cdn.anthropic.com/files/4zrzovbb/website/6867eadf760258fa8b42a504600cd3c036d16358.pdf)，
以及合作者 Theorem 公開的語意庫
[`rocq-linux-process-semantics`](https://github.com/theorem-labs/rocq-linux-process-semantics)。問題有兩個：

- 該研究的形式化驗證是怎麼做的？
- 它和本倉庫從 exp201 起的做法——RV32 機器碼加上 Lean 4 證明——差在哪裡？

**結論：兩邊都證明「編譯出來的位元組」而不是原始碼，也都把信任集中在「指令集語意、定理陳述、證明檢查器」這三件事上；
差別在於取捨的方向相反。** 該研究把**涵蓋面**推到極限：123 個真實函式庫、整個 Linux 行程（含 libc 與 ASan 執行期），
證明的性質則刻意選得窄——「不會當掉」，以及兩個建置版本行為相同。本倉庫把**性質**推到極限：精確的輸出、精確的
指令週期數、常數時間、PMP 隔離、退場清零，換來的是只能處理幾百個字組、沒有作業系統的程式。

本倉庫最值得借用的是該研究處理環境的方式：**作業系統的每一種回應都被量化，沒有建模的行為一律算失敗。** 本倉庫目前
把 MMIO 服務埠當成普通記憶體，這正是 exp238 自己揭露、exp245 拿來當反例的缺口。

這份分析沒有用到板子，也沒有新的實測。關於該研究的數字都取自上面三個來源；Theorem 語意庫的內容只讀了它的 README，
沒有讀原始碼，凡是 README 沒寫的部分，本文都標成「未說明」。

## 一、該研究做了什麼

### 1. 起點：把模糊測試變成規格

形式化驗證向來昂貴。該研究引用 seL4：實作約 2 人年，驗證約 20 人年。

它的切入點是 Google OSS-Fuzz 裡已有的模糊測試進入點（fuzz entry point）。每個進入點本來就是一個「把任意位元組餵給
函式庫」的小程式，搭配 AddressSanitizer（ASan）偵測記憶體錯誤。該研究把它直接變成規格：

> 對任何小於 64 MB 的輸入，這個進入點都正常結束，不觸發記憶體安全錯誤，也不觸發失敗的 assert。

於是規格不必由人寫：維護者寫過的 fuzz harness 與 assert 就是規格。附錄舉的 LZO 例子說明這有多強：它的 harness 會先壓縮
再解壓縮，並 assert 解出來的長度等於原長度。要證明那個 assert 永遠不會觸發，Claude 必須證明 LZO 的壓縮與解壓縮
**能互相還原**，這已經是一條關於「函式庫算出什麼」的正確性定理，而不只是「它寫到哪裡」。

### 2. 證明的是編譯後的 RISC-V 二進位

附錄說明了為什麼不翻譯原始碼：把 fuzz 測試翻成 Rocq 有翻譯錯誤的風險，直譯原始碼則有「直譯器與實際編譯結果不一致」
的風險。所以它**直接解讀編譯後的二進位**，使用 RISC-V 指令語意與 Linux 行程語意。

Theorem 的語意庫 README 寫明了範圍：

- 指令集是 **RV64GC**，`theories/Riscv/` 放解碼器與指令語意。README 沒有逐一列出模型涵蓋哪些擴充指令。
- 二進位透過 `tools/elf_snapshot.py` 變成記憶體映像。
- 系統呼叫的規格放在 `Sys/`，目錄結構仿照 Linux 核心原始碼（例如 `Sys/Fs/ReadWrite.v` 對應 `fs/read_write.c`）。
  每一條規格都附一個可執行的檢查器（`Checks/`），並證明檢查器與規格一致。
- **規格是「允許的結果集合」，不是單一結果**：`read` 可以回傳可用輸入的任何非空前綴，`mmap` 可以失敗並回傳
  `ENOMEM`。程式必須對每一種允許的回應都正確。
- 每次啟動的記憶體佈局（堆疊位址、program break、mmap 基址、`AT_RANDOM` 位元組）都被量化，而且兩個二進位的佈局
  **各自獨立**量化，證明不能假設它們共用位址。
- 有一個 `Unmodeled` 結果，標記模型不解釋的情況。

### 3. 「當掉」的定義，和三條定理

附錄給的定義：**當掉 = 錯誤（例如存取未對映的記憶體）、中止（例如 assert 失敗），或任何沒有建模的行為（例如語意裡
沒有定義的系統呼叫）。**

最後一項是關鍵。模型沒涵蓋到的地方不會被默默當成「沒事」，而是直接算成失敗。

接著是三條定理，各自補上前一條的漏洞：

1. **ASan 版本不會當掉。** 這條成立，OSS-Fuzz 就不必再對這個二進位做模糊測試。但使用者跑的不是 ASan 版本。
2. **ASan 版本與一般版本行為相同。**「行為」只看四件事：從 stdin 讀到的位元組、寫到 stdout/stderr 的位元組、結束碼
   或終止它的訊號、檔案系統的最終狀態。兩個程式等價，是指對每一種輸入、每一對記憶體佈局，讀寫事件序列與結束狀態都相同。
3. **一般版本也不會當掉。** 因為當掉的程式，它的事件序列只是「停在那裡」，無限迴圈也一樣。所以第 2 條無法區分
   「一個當掉、一個進入無窮迴圈」。第 3 條補上這個洞。

合起來，在 RISC-V Linux 上，對兩個二進位、所有小於 64 MiB 的輸入、所有記憶體佈局：兩者都不出錯、不中止、不碰到
沒建模的行為；而且讀寫事件相同、結束方式相同、留下的檔案系統相同。

語意庫的頂層陳述是 `strong_universal_T`（`theories/EquivalenceDefinition/Equivalence.v`），它是一條**兩個二進位之間的
等價**陳述，並要求「涵蓋」：沒有任何來源端的執行會走到 `Unmodeled`。

### 4. 規模與樣貌

| 項目 | 數字（取自該研究與附錄） |
| :--- | :--- |
| 函式庫與進入點 | 123 個函式庫、239 個進入點 |
| 通過檢查的證明 | 約 1.8 億行 Rocq；Claude 總共寫了約 10 億行，其餘沒有通過 |
| 一個典型的證明 | 約 60 萬行、約 1,400 個檔案（各函式庫介於約 33 萬到 90 萬行） |
| 二進位大小 | 中位數約 18,000 條 RISC-V 指令；函式庫自己的部分常只有約 2,000 條 |
| 證明裡真正關於函式庫的比例 | 以 cJSON 為例，約十分之一；其餘是 C 啟動碼、配置器、`printf`、ASan 執行期、fuzz driver |
| 機器產生的部分 | 一半以上是 Claude 自己寫的工具產生的（指令編碼、查表） |
| 檢查一個證明的時間 | 30 分鐘到數小時 CPU 時間 |
| 規格長度 | 中位數約 110 行，對比中位數約 86 KB 的程式碼 |

附錄有一段專家觀察很值得記下：代理寫的證明**非常冗長**。它們反覆寫出暫存器內容、整數轉換、一長串位址彼此相異、
堆疊每一格的內容、每一個分支。人類證明工程師會立刻抽象出呼叫慣例、互斥指標集合、配置器的行為等概念。代理也自己發明了
一些熟悉的構造，例如類似分離邏輯（separation logic）的 frame 規則、與程式碼位置無關的推理、配置器的抽象，但抽象帶來的
縮減有限。附錄提出的開放問題是：這種冗長風格能不能擴展到更複雜的程式。MachCSL 的經驗顯示可能不行。

另外，目前每個證明都要從頭重證 libc 與 ASan 執行期，無法匯入。該研究也觀察到重用的效果：多個代理共用工作區時，
token 用量少 17%；OSS-Fuzz 的團隊經常複製並改寫已完成的證明。

### 5. 找到的錯誤，與防作弊

驗證過程找到數百個錯誤。Claude 修補程式碼，規格隨之重新產生，再重新證明。例子包括：

- 一個解壓縮器的計數器下溢，在約 20 MB 的罕見輸入上造成越界寫入。
- 一個影像解碼器的越界讀取，需要 64 MB 的輸入才會觸發。
- 一個檔案限制功能沒有在所有路徑上生效的邏輯錯誤。

修補程式碼本身就是作弊的入口：把會出錯的功能整個拿掉，定理也會成立。該研究的對策是**懲罰任何修補**，證明「這個修補
改變了哪些輸入的行為」的話則給額外分數，並記錄、稽核所有修補。

### 6. 其他案例

- **zlib**：Claude 從 RFC 1950 寫出規格，證明 Linux 核心的 zlib 在 **x86 二進位層級**實作了它，使用 Claude 自己產生的
  x86 語意。
- **Python 直譯器**：Claude 用安全的 Rust 寫了一個 Python 子集直譯器，用 Verus（Rust 加上 requires/ensures/迴圈不變式，
  以 Z3 證明）證明它符合以 λπ 為基礎的形式語意。這份語意與 CPython 的一致性則是**實測**的：170 萬個（多半隨機的）程式，
  99.95% 行為相同。附錄還做了一個對照：在早期版本刻意植入 7 個錯誤，隨機測試只抓到 2 個，證明 7 個全部抓到。

### 7. 該研究自己寫下的限制

- 「形式化驗證過」不等於「沒有錯誤」：錯誤可能在規格裡，也可能在建模的語意裡。
- 證明的是靜態連結 musl 的 RISC-V 二進位；多數使用者跑的是動態連結 glibc 的 x86 或 ARM 版本。
- ASan 抓不到所有記憶體安全錯誤，也不是每個進入點都驗證了。
- 呼叫端可能誤用函式庫而破壞記憶體，這不在證明範圍內。
- 信任的元件：RISC-V 與 Linux 行程語意、確切的定理陳述、Rocq 證明檢查器，以及隱含的硬體、作業系統、Rocq 所依賴的
  OCaml 編譯器。

## 二、本倉庫的做法，用同一把尺量

本倉庫的驗證走過兩條路，兩條都證明位元組：

- **kernel 路線**（exp201–exp235）：User mode、一個 64 KiB（後來 128 KiB）的區域，`ecall` 交給殼層處理（HASH、HALT、
  HASHB、CHECKSIG）。代表作是 exp208 的 SHA-256 kernel：252 條指令，證明它停機時 `a0 = 0`，恰好跑了 `4990 + 4873·n`
  條指令，並寫出 `n` 個區塊訊息的 `sha256`。
- **monitor 路線**（exp236 起）：RV32I + Zicsr 的 M-mode 微監控器，在 `PrivMachine` 上證明 PMP 隔離、系統呼叫的範圍檢查、
  退場清零、W^X 與回合之間的重入。exp240 的 monitor 是 151 個字組。

| 環節 | 本倉庫 |
| :--- | :--- |
| 指令集 | [`lean/Rv32/Isa.lean`](../lean/Rv32/Isa.lean)：kernel 可用的 46 種 RV32IM 指令形式，`encode` 與 `decode` 兩個方向都證明了 |
| 位元組怎麼進入證明 | `monitor.bin` 的字組直接成為 Lean 裡的 `monitorCode`；`check.sh` 每次重新組譯 `monitor.S` 並核對，而且產生的證明檔必須與產生器的輸出完全相同 |
| 語意的校驗 | `Isa.lean` 對 LLVM 做差分（exp201）；`Machine.lean` 對 riscv-tests 與 Hazard3 RTL（exp202）；`Priv.lean` 是 Hazard3 文件的解讀，另由 `tools/monitor/emulator.py` 做第二份獨立解讀 |
| 證明檢查 | `tools/lean/lean.sh check`：每條定理的 `#print axioms` 只能出現 Lean 自己的公理，`sorryAx`、`native_decide`、`bv_decide` 一律拒絕 |
| 防空洞證明 | 每個實驗的 `proof/mutants.txt`：改錯一個字組、一條宣稱或一條模型規則，Lean 必須拒絕 |
| 證明規模 | exp240 的 `Wx.lean` 約 2,400 行（由 `gen.py` 依 `tools/monitor/chunks.py` 的表格產生），手寫部分 `defs.lean` 43 行加 `tail.lean` 215 行；共用的 `lean/Rv32/` 約 13,800 行 |

## 三、差異

### 1. 驗證對象：整個 Linux 行程 vs 沒有作業系統的幾百個字組

| | 該研究 | 本倉庫 |
| :--- | :--- | :--- |
| 指令集 | RV64GC（另有 x86 的 zlib 案例） | RV32IM 的 46 種形式；monitor 用 RV32I + Zicsr |
| 執行環境 | Linux user mode，單執行緒、靜態連結 musl、固定記憶體預算 | 裸機：User mode 的單一區域，或 M-mode 加上 PMP |
| 二進位大小 | 中位數約 18,000 條指令 | 數十到數百條（exp208 252 條，exp240 151 字組） |
| 二進位從哪來 | 現成的 C/C++ 專案，經過一般編譯流程 | 手寫組語，或刻意保持很小、指令形式受限的程式 |
| 特權層級、PMP、CSR | 不在模型裡 | monitor 路線的主題 |

該研究的規模能做到，是因為 Linux 替它處理了特權層級、記憶體保護與裝置。行程只需要面對系統呼叫介面，而這個介面有
清楚的規格可以抄（Linux 原始碼本身）。本倉庫要證明的東西，正好是作業系統那一層：誰能寫哪段記憶體、陷阱發生時
保存什麼、退場前清掉什麼。這一層在 Linux 的模型裡是「假設」，在這裡是「定理」。

反過來說，該研究的語意不涵蓋 RV32、M-mode、PMP、MMIO 與中斷，**不能直接拿來驗證 RP2350 上的韌體**。

### 2. 定理的形狀：窄而通用 vs 深而專門

該研究證明的性質，對每個程式都一樣：不當掉，加上兩個建置版本等價。規格可以自動產生，代價是性質淺。LZO 的
還原性是例外而不是常態：只有在 harness 的 assert 剛好要求時才會出現。

本倉庫證明的性質，每個實驗都不同，而且都是確切的值：

- **功能正確**：exp208 寫出的是 `sha256`，不只是「沒有越界」。
- **確切的指令數**：`4990 + 4873·n`；exp213 的簽章器是 `2284 + 3·Σdᵢ`。
- **常數時間**：`lean/Rv32/Ct.lean` 證明兩個在公開值上一致的狀態會步步同步，這是該研究的性質完全不談的資訊流。
- **隔離與清零**：exp240 的 `wx_code_immutable`、`monitor_reentry`；exp239 的 `monitor_scrub`。

代價是規格必須由人（或代理）為每個實驗手寫，而規格寫錯，證明救不了。exp245 整個實驗就在示範這一點。

### 3. 環境：量化每一種回應 vs 把介面當成記憶體

這是兩邊**最大**、也最值得本倉庫學的差別。

該研究的環境是**非決定性的**：系統呼叫的規格是「允許的結果集合」，`read` 可以只讀一部分、`mmap` 可以失敗，記憶體佈局
任意，證明必須對全部成立。**沒建模的行為算當掉**，所以模型的缺口會變成證明失敗，而不會變成一條空洞的定理。

本倉庫的環境有三種處理方式，嚴格程度不一：

- **殼層的 `ecall`**（kernel 路線）：`Machine.lean` 裡 HASH 的結果是 `env.hash`，CHECKSIG 的答案是 `env.sig`，兩者都是
  **參數**。證明從不看它們的內部，所以「呼叫 `CHECKSIG` 的 kernel，不論殼層回答什麼，定理都成立」。這和該研究的量化
  方式一致，只是量化的是一個函數，而不是每次呼叫各自的結果。
- **回合之間的 host 寫入**（exp240）：`HostWrite` 允許 host 在回合之間寫入 monitor 字組、code 區與鎖定位元以外的任何地方，
  而 `monitor_rounds` 對任意次數、任意內容的寫入都成立。這和該研究的量化方式一致。
- **MMIO 服務埠**（exp238）：`0xc0000010..0xc000001c` 被當成普通記憶體。exp238 的 README 寫明了後果：
  "the model reads back the request it just wrote"。exp245 的 WHY 第四節把它寫成反例：一個「讀回請求碼就算通過」的
  驗證呼叫，在模型裡能被證明永遠通過。

也就是說，**kernel 路線原本就量化了環境的答案，monitor 路線在服務埠上反而退了一步**。如果服務埠照 kernel 路線的
`env.sig`（或該研究）的方式建模，讀取答案時回傳「任意值」，定理就必須對每一種答案都成立，「永遠通過」就證不出來。
**這是本倉庫可以直接借用的做法，而且不需要新的工具**：本倉庫在 kernel 路線已經這樣做過，monitor 路線的回合定理也已經在
量化 host 的寫入，服務埠的讀取只是同一件事的另一個方向。

### 4. 信任基礎：同樣的三件事，不同的校驗方式

兩邊都不信任編譯器：證明的對象就是編譯（或組譯）之後的位元組。兩邊都信任三件事：指令與環境的語意、定理的陳述、
證明檢查器（Rocq 的核心，或 Lean 的核心）。

差別在於怎麼讓人相信語意是對的：

- **該研究**：系統呼叫的規格附可執行的檢查器並證明兩者一致；Python 案例的語意對 CPython 做了 170 萬個程式的實測。
  RISC-V 指令語意本身怎麼校驗，README 與附錄都沒有說明。
- **本倉庫**：每一層語意都有一個「另一份讀法」對照，並寫在 `lean/README.md` 的表格裡。`Isa.lean` 對 LLVM，`Machine.lean`
  對 riscv-tests 與 **Hazard3 的 RTL**，`Pio/Machine.lean` 對兩個 PIO 模擬器。弱點也寫明了：`Priv.lean` 只對文件與模擬器，
  沒有對 RTL，也沒有在晶片上量過 PMP 的條目順序（exp240 的 *What is not proved*）。

本倉庫的語意綁定的是**一顆具體的晶片**（例如 exp209 量到的 `PMP_GRAIN = 3` 讀回值），該研究綁定的是**一個作業系統的
介面**。前者能說「在這顆晶片上」，後者能說「在任何符合 Linux 行程語意的系統上」。

### 5. 證明的規模、風格與重用

一個典型的 OSS-Fuzz 證明約 60 萬行；exp240 整個 monitor 的證明約 2,400 行。差兩個多數量級，主要來自三件事：

1. **程式大小**：18,000 條指令對 151 個字組。
2. **要重證的東西**：該研究每個證明都從頭重證 libc、配置器與 ASan 執行期，cJSON 的證明只有約十分之一關於 cJSON。本倉庫
   的程式沒有 libc，共用的事實放在 `lean/`，一個事實只有一份。
3. **重複的抽象方式**：附錄觀察到代理會把暫存器、位址相異、每一個分支全部攤開寫。本倉庫的 monitor 證明也是攤開的，但攤開的
   工作交給產生器：`chunks.py` 把 monitor 切成固定形狀的短段，每一段的陳述與證明都一樣，由表格產生。這和附錄說的「一半以上
   是機器產生的查表」是同一種策略。不同的是，本倉庫把產生器本身納入檢查：產生的檔案必須與產生器的輸出完全相同。

該研究在重用上的觀察（共用工作區省 17% token、團隊互相複製證明、以 Mathlib 為類比），與本倉庫 AGENTS.md 的規則方向一致：
「第二份複製出現時就是抽取的時機」，並由 `experiments/duplication.sh --check` 強制。差別是本倉庫把它做成了**不能退步的棘輪**，
而該研究目前仍是每個證明各自重來。

### 6. 防作弊：修補的懲罰 vs 突變的棘輪

兩邊面對的作弊方式不同。

- **該研究**的代理可以**修改被驗證的程式**（修錯誤）。最便宜的作弊是把會當掉的功能拿掉，所以對策針對修補：懲罰修補、
  獎勵證明修補影響了哪些輸入、稽核。
- **本倉庫**的程式通常是固定的，作弊會發生在**證明與規格**。對策有三層：公理檢查拒絕 `sorryAx` 與以編譯程式碼證明的
  策略；`mutants.txt` 要求每一個錯誤版本都被 Lean 拒絕；產生的證明必須與產生器輸出一致。

附錄的 Verus 對照（植入 7 個錯誤，測試抓到 2 個、證明抓到 7 個）在精神上就是本倉庫的突變測試，只是方向相反：它證明
「證明比測試敏感」，`mutants.txt` 則證明「這份證明確實綁住了這些位元組」。

exp245 指出突變測試還有一層盲點：突變如果只對著某段位元組**自己的局部定理**跑，抓不到「這段位元組根本沒用」。該研究的
規格比較不容易掉進這個陷阱，因為它的頂層陳述從程式開始執行出發，講的是可觀測的讀寫事件。這正是 exp245 建議的
「揭穿定理」形狀：**從 reset 出發、講可觀測結果的定理**。

### 7. 「等價」這個工具，本倉庫還沒用過

該研究最有啟發性的一步，是用**兩個二進位的等價**來把「ASan 版本不當掉」轉移到使用者真正執行的版本。本倉庫的證明都是
關於**一個**二進位的。但至少有兩個地方，等價正是需要的陳述：

- **exp245 的消融**：「拿掉御守之後行為不變」最自然的寫法，就是御守版與 exp240 版在可觀測事件（回報字組、結束碼、回合結束
  時的記憶體）上等價。exp245 目前的設計是靠逐位元組相同加上模擬器比較，再分別為每個御守寫一條揭穿定理。
- **模型與量測的橋**：kernel 路線在 Hazard3 RTL 上跑同一份二進位並比較輸出（exp202 起），這是實測的等價。

附錄提到的那個細節也適用：**當掉的執行，事件序列只是停止，無窮迴圈也一樣**，所以等價定理一定要搭配「兩邊都不會卡住或
出錯」的定理。本倉庫的 monitor 定理以「跑 `n` 步，或在第一個陷阱停下」來陳述，若要寫等價，同樣要面對這個問題。

### 8. 落差各在哪裡

| | 該研究 | 本倉庫 |
| :--- | :--- | :--- |
| 模型與部署的落差 | musl 靜態 RISC-V vs 實際的 glibc 動態 x86/ARM | 模型 vs Hazard3 晶片；monitor 路線沒有任何晶片建置 |
| 偵測器的極限 | ASan 抓不到所有記憶體錯誤 | 沒有對應物：性質是直接寫出來的 |
| 不在模型裡 | 多執行緒、呼叫端誤用 | 中斷、另一顆核心、DMA、故障注入、側通道（常數時間除外） |
| 環境的建模 | 非決定性，沒建模的算失敗 | 殼層 `ecall` 的答案是參數（量化）；host 寫入有量化；MMIO 服務埠是記憶體 |

## 四、建議

1. **把服務埠的讀取改成參數**：像 kernel 路線的 `env.sig` 一樣，答案字的讀取回傳一個任意值，讓所有關於服務呼叫的定理對
   每一種答案都成立。這直接補上 exp238 揭露、exp245 示範的缺口。exp238 的 `ServiceEmulator` 已經把讀寫分開，模擬器那一側
   不需要改。
2. **讓模型與模擬器對「沒有記憶體的位址」說同一件事**：模擬器在沒有 RAM 的位址觸發匯流排錯誤；Lean 這一側，monitor 的定理
   假設 `env.region = monRegion = [0x80000000, 0xC0000100)`，區域內每個位址都讀得到值。該研究的作法是把沒建模的行為算成
   失敗（`Unmodeled`）；本倉庫可以讓這類存取在模型裡成為陷阱，或明確寫成一條假設。
3. **試寫一條等價定理**：以 exp245 的御守版與 exp240 版為第一個案例。規模小、兩份二進位的差別完全已知，適合用來確認
   「事件序列在當掉時停止」這類細節在 `PrivMachine` 上怎麼寫。
4. **不要追該研究的規模**：本倉庫的價值在性質的深度與晶片的綁定。把 Linux 行程語意搬進來，等於放棄 PMP、CSR 與 MMIO
   這些本倉庫要證明的東西。
5. **規格從測試來，這一點可以借**：本倉庫的模擬器套件（exp236 的 23 個惡意 payload、exp240 的回合測試）已經是規格的雛形。
   該研究的經驗是，把既有測試的判定條件原樣變成定理陳述，比另寫規格可靠，因為它繼承了維護者對「什麼算壞」的判斷。
