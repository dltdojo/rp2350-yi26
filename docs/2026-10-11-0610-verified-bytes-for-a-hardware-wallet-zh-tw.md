# 硬體錢包韌體：哪些部分值得做成「證明過的位元組」

<!-- SPDX-License-Identifier: Apache-2.0 -->

2026-10-11 的評估。起因是 exp228 完成之後的兩個問題：

- 從硬體錢包韌體的角度看，exp228 這種「RV32IM 機器碼加上 Lean 證明」的做法，優點和缺點各是什麼？
- 如果要往硬體錢包走，哪些功能應該繼續做實驗、納入形式化驗證的範圍？

**結論：只把錢包裡小而關鍵、規則穩定、輸入來自攻擊者的那幾個函式做成證明過的位元組，其餘的部分用測試。** 最值得投入的是「看到的就是簽的」：交易解析、BIP341 簽章雜湊、地址顯示，三者之間的一致性。順序上，先接著 [mathlib-for-checksig](./2026-10-10-1236-mathlib-for-checksig-zh-tw.md) 建議的 secp256k1 模 p 運算（已於 exp229 完成）。

exp228 的解譯器本身在錢包裡用處不大：執行 Script、判斷交易合不合法是節點的工作，不是錢包的。能帶到錢包的是它的方法：證明解析不會讀過頭、密碼學交給 `ecall`、規格與 Python 參考實作互相對照，以及 ENCODE 那個錯的教訓。

這份評估沒有用到板子，也沒有新的實測。文中引用的數字都來自已完成的實驗，連結在旁邊。

---

## 一、先定位：硬體錢包要守住什麼

硬體錢包說穿了只承諾兩件事：

1. **種子不離開裝置。** 不從記憶體殘留、時間、功耗漏出去，也不被裝置上別的程式讀到。
2. **只簽使用者在裝置上看到並確認過的那筆交易**，也就是「看到的就是簽的」。

攻擊者依可能性排序：

| 攻擊者 | 手上有什麼 | 主要針對 |
| --- | --- | --- |
| 被入侵的電腦或手機（主機） | 能送任何位元組給裝置 | 第 2 項：讓裝置簽一筆和顯示不同的交易 |
| 拿到裝置的人 | 實體接觸、時間 | 第 1 項：PIN 猜測、讀 flash、故障注入、側通道 |
| 供應鏈 | 韌體更新的管道 | 兩項都有：換掉韌體 |

評估形式化驗證的價值，就看它能把這兩項承諾守到什麼程度。

## 二、優點

| 優點 | 對錢包的意義 | 這個 repo 的證據 |
| --- | --- | --- |
| **抓得到邏輯錯誤** | 錢包最危險的錯，常是「沒當機、只是答案錯」：手續費算錯、找零判斷錯、顯示的位址和實際付款的腳本不一致。Rust 的型別系統管不到這些 | exp228 的 ENCODE 把 −128 寫成 +128，3000 個隨機腳本沒抓到，證明抓到了 |
| **證明的是實際執行的位元組** | 編譯器不在信任範圍內。對**常數時間**特別重要：最佳化器可能把無分支的程式碼改回有分支 | exp207 的 `lean/Rv32/Ct.lean` 在位元組層級證明：任兩個種子下，keygen 與 sign 每一步的 pc、存取位址都相同。exp212 在晶片上量到 16 個種子的週期數完全相同 |
| **攻擊者控制的輸入，正是證明的強項** | 主機送來的交易、PSBT 都不可信 | exp228：任何 1020 位元組以內的腳本，核心都不會讀過頭、不會出錯陷入 |
| **確切的指令數** | 每個核心都附帶一份時間規格 | exp203 起每個核心都證明停機時的指令數；exp228 在晶片上逐案相符 |
| **信任範圍小、可以反覆對照** | 規格、模型、RTL、Python 四方對照；變異體確認證明真的會擋 | exp228：3705 個腳本四方一致，七個錯誤版本都被擋下 |

## 三、缺點與限制

### 1. 殼層才是真正的信任基礎，而且是 C 寫的

這是最大的結構問題。目前的架構是：證明過的核心在 User 模式執行，受 PMP 限制；C 殼層在 Machine 模式執行，看得到整塊記憶體。證明說的是「核心不會越界」，沒有說「殼層不會洩漏」。

#### 為什麼 C 殼層目前必須在 Machine 模式，不能直接放進 User 模式？

安全設計的準則，本應是「特權區域（TCB）越小越好，且特權區域盡可能使用經過形式化驗證的機器碼」。但在 RISC-V（Hazard3）硬體架構下，C 殼層目前無法直接挪至 User 模式執行：

1. **開機預設為 Machine 模式**：晶片重置（從 Bootrom 或 Flash）啟動時，處理器硬體直接處於 Machine 模式。
2. **PMP 配置專屬 Machine 特權級**：User 模式要受到記憶體邊界限制，必須由 Machine 模式寫入特權 CSR（`pmpcfg*`、`pmpaddr*`）。User 模式存取這些 CSR 會直接觸發 Illegal Instruction 例外（`mcause = 2`）。
3. **Trap / ecall 攔截與降權切換**：核心以 `ecall` 發出服務請求或停機時，硬體跳轉至 `mtvec`（Machine Trap Vector）。只有 Machine 模式能讀取 `mcause`、`mepc`，並透過特權指令 `mret` 降權切換回 User 模式。
4. **特權 CSR 與受保護周邊存取**：特權控制暫存器（如中斷致能 `mie`、計數器凍結 `mcountinhibit`）以及未對 User 模式開放 PMP 授權的系統 MMIO（如時脈與硬體周邊）皆須由 Machine 模式管控。

因此，系統中**必然需要有程式碼留在 Machine 模式**。目前的 C 殼層把硬體初始化、USB 通訊、PMP 設定、Trap 處置全打包在一起，才使整個殼層都留在 Machine 模式。

#### 硬體錢包需要的架構 vs 目前過渡架構

| 層級 | 理想的安全終態 | 目前專案的過渡現況 |
| --- | --- | --- |
| **Machine 模式** | 極小的**形式化驗證監控程式（Micro-Monitor）**，僅負責 PMP 配置與 Trap 轉發 | 未經驗證的 **C 語言 / 組語大型殼層**（處理硬體初始化、USB、周邊驅動） |
| **User 模式 Domain 1** | **形式化驗證的密碼核心**（持有種子與私鑰，如 exp229, exp213） | **形式化驗證的密碼核心**（純計算，受 PMP 限制） |
| **User 模式 Domain 2** | **降權的驅動與通訊層**（USB、螢幕，被 PMP 隔離碰不到私鑰） | *(尚未分離，仍在 Machine 模式 C 殼層中)* |

錢包需要的方向剛好相反：持有秘密的程式要被圍起來，負責 USB、螢幕這類大量程式碼的部分要碰不到秘密。在 RISC-V 這一側要做到這點，Machine 模式裡只能留一個很小、本身也證明過的監控程式，USB 堆疊要和簽章核心一樣降到 User 模式。這個 repo 還沒做過。

#### 目前尚未實作「證明過的 M-mode 監控程式」的五大困境

1. **形式化模型的特權級狀態空間爆炸**：
   目前 `lean/Rv32` 僅對 User 模式的 RV32IM（通用暫存器 + 扁平記憶體陣列）建立語意。要驗證 Machine 模式程式，必須將整套特權架構建模進 Lean：特權 CSR（`mstatus`, `mtvec`, `mepc`, `mcause`, `mscratch`, `pmp*`）、硬體 Trap 自動保存與跳轉機制、`mret` 狀態還原，以及 PMP（RP2350 硬體支援 32-byte 粒度之 `NAPOT` 模式）在硬體匯流排上的過濾語意。如 [exp224 的 WHY.zh-TW.md](../experiments/exp224-the-checks-the-kernel-makes/WHY.zh-TW.md) 所指出，光是建模 200 行 harness，其複雜度就遠高於純演算法。
2. **晶片硬體實體與規格書的落差（Silicon Quirks）**：
   形式化證明的先決條件是「硬體真實行為完全吻合數學模型」。但實測顯示 Hazard3 在特權級與 CSR 存在未文件化或與預設模型出入的硬體行為：
   - **PMP 讀寫差異（exp209）**：Pico 2 晶片實測中，`pmpaddr0` 寫入後讀回值與寫入值不同（源於 RP2350 硬體固定 `PMP_GRAIN = 3`，使低位元依 `OFF` / `NAPOT` 模式強制讀回 `0` 或 `1`，而預設 RTL 模擬未開啟此粒度遮罩）。
   - **計數器特異行為（exp203、exp209）**：Hazard3 將規格明訂不計數的 `ecall` 計入 `minstret`，把 `mret` 算兩次，且計數還會受 `mret` 後方記憶體殘留指令影響。
   - **重置死鎖（exp214）**：Hazard3 在 reset 時凍結 `mcycle` 計數器（`mcountinhibit.cy` 重置預設為 `1`），導致殼層中的逾時邏輯死鎖。
   硬體在特權指令與 CSR 上的微架構特異性，隨時可能直接打破形式化證明的假設。
3. **RP2350 缺乏 S-mode，且 PMP 資源與對齊受限**：
   Hazard3 僅支援 Machine 與 User 兩層特權級，缺乏作業系統常見的 Supervisor 模式（S-mode）。若要將「不可信的 USB 堆疊」與「可信的簽章核心」同時降到 User 模式運行，Machine 模式監控程式必須承擔完整的多任務上下文切換（Context Switching）與動態 PMP 重置。而 RP2350 硬體僅配備 **8 個 PMP 區域**（單一 `pmpcfg0` 僅控管前 4 個條目，且不支援任意邊界的 `TOR` 模式、僅支援 2 的冪次對齊之 `NAPOT` 模式），要在有限條目與對齊限制內同時切分 Flash 程式碼、專屬 SRAM、MMIO 與共享緩衝區，硬體配置空間相當緊迫。
4. **週邊驅動程式龐大且難以數學形式化**：
   C 殼層除了排程，還涵蓋 USB 堆疊、Flash Bootrom 擦寫、TRNG 採樣、SHA 加速器控制。這些程式碼規模龐大且高度非同步（主機封包插拔、時脈雜訊、中斷觸發），極難用純函數式狀態轉移 $f(\text{state}) = \text{state}'$ 進行封閉系統定理證明，往往只能仰賴 TLA+ 模型檢查或模糊測試（Fuzzing）。
5. **投資報酬率（ROI）與工程路徑先後抉擇**：
   硬體錢包歷史上最常造成資產損失的，多半不是特權級提權，而是演算法與資料解析的致命邏輯錯誤：
   - 大數模運算溢位或邊界錯誤（如 exp228 抓出的 $-128$ 編碼正負顛倒、exp229 乘法第三次折疊進位處理）；
   - 常數時間被編譯器最佳化打破，形成時序旁通道洩漏金鑰；
   - 交易腳本與金額解析「看到的不等於簽的」（如 BIP143 未承諾全部輸入金額，或 BIP341 簽章雜湊與顯示金額不一致導致的手續費漏洞）。
   因此本專案採取實用主義路線：**優先將輸入面對攻擊者、出錯即致命的底層有限體演算法（exp229）與腳本解析（exp228）做成證明過的機器碼**；待核心演算法完備後，再來動 M-mode 的特權架構手術。

### 2. 這顆晶片守不住使用中的大型秘密

[can-this-chip-keep-a-secret.md](./can-this-chip-keep-a-secret.md) 已經把這件事量完了（Arm 這一側，`ACCESSCTRL`）：

- OTP 只能儲存，不能隱藏：4096 列沒有一列拒絕一般韌體讀取（exp154）。
- 小的秘密守得住：P-256 金鑰放在 4 KB 的 SRAM bank 8，簽章時也守得住（exp159）。
- 大的守不住：ML-DSA-65 使用中的金鑰有 65,696 位元組，落在開放的堆疊裡（exp160）。`ACCESSCTRL` 在主 SRAM 一次只能擋住連續 4 位元組（exp162）。
- 用完就清除是有效的，成本 2.3%（exp163）。

secp256k1 的工作集和 P-256 同一個量級，所以照 exp159 的做法放進 bank 8 是可行的方向。但 RISC-V 這一側（PMP、Machine 和 User 模式）能不能做到同樣的隔離，這個 repo 沒有量過。**形式化驗證補不了硬體上的缺口**；它能做的，是證明核心只在指定的區域裡碰秘密、結束時清乾淨。

### 3. 規格錯了，證明救不了

2020 年公開的 SegWit 手續費問題就是一例。BIP143 的簽章只承諾正在花用的那個輸入的金額，攻擊者可以讓錢包分兩次簽，誘使使用者付出大筆手續費。實作完全照規格，錯在規格本身，要到 BIP341 承諾所有輸入的金額才解決。

形式化驗證只能保證「照規格做」。所以每一份規格都要另外和獨立實作做差分測試（Bitcoin Core、libsecp256k1、BIP 的測試向量），就像 exp208 拿 hashlib 對照 SHA-256、exp228 拿 `script.py` 對照 Lean 規格。

### 4. 物理攻擊不在模型裡

- **故障注入**：定理的前提是 CPU 照模型執行，電壓或時脈 glitch 直接打破這個前提。[verified-kernel-road 簡報](./2026-10-02-0930-verified-kernel-road-briefing-zh-tw.md)已經明確把故障注入排除在範圍外。
- **功耗與電磁側通道**：exp207 的常數時間證明的是指令序列和存取位址，不涵蓋漢明重量這類資料相依的功耗。

### 5. 模型和晶片之間還有距離

Lean 模型對照的是 Hazard3 v1.1 的 RTL，晶片上是 v1.0-rc1。exp212 量到晶片週期數和 RTL 不同，而且不是每次 HASH 或每條指令的固定差值。指令層級的常數時間成立，微架構層級沒有證明。

### 6. 規模、更新與審查

- 一個完整的錢包韌體有數萬到數十萬行；exp228 的 881 條指令就花了大量工時，`check.sh` 跑一次約半小時。
- 每次韌體更新都可能要重做證明。
- 審計人員熟悉 C 和 Rust，同時看得懂 RISC-V 組合語言和 Lean 的人很少。

### 7. Pico 2 沒有可信的螢幕和按鈕

「看到的就是簽的」需要裝置自己的螢幕和確認鍵。Pico 2 只有一顆 LED 和 BOOTSEL 鍵。證明最多能做到「顯示緩衝區裡的內容正確」；像素和面板是硬體的事，也不在這個 repo 的範圍內。

## 四、哪些功能該繼續納入驗證

排序依據四個問題：錯了會不會損失資金或種子？規格是否小而穩定？輸入是否來自攻擊者？測試是否特別難涵蓋？

### 第一優先：直接決定「簽了什麼」

| 功能 | 要證明的性質 | 已有的基礎 |
| --- | --- | --- |
| **secp256k1 的模 p 運算** | 機器碼的 limb 運算等於 `Nat` 上的模運算 | [mathlib-for-checksig](./2026-10-10-1236-mathlib-for-checksig-zh-tw.md) 第五節建議的第一個實驗；不需要 Mathlib（已於 exp229 落地） |
| **BIP340 驗章核心** | 驗章結果等於規格；取代 exp228 殼層裡只經過測試的 `bip340.c` | exp228 的 `ecall` 介面不用改，換掉的只是回答 CHECKSIG 的那一方 |
| **BIP340 簽章與 nonce** | 簽章等於規格；nonce 是 (金鑰, 訊息, aux) 的規格函式，不會重用；常數時間 | exp207 的 `Ct.lean`；exp213 已經把 keygen、sign、verify 串成一條定理。nonce 重用等於金鑰外洩，是最致命的錯 |
| **交易解析與 BIP341 簽章雜湊** | **「看到的就是簽的」**：顯示緩衝區裡的輸出、金額、手續費，和送進簽章雜湊的位元組一一對應 | exp208 的 SHA-256 核心（BIP341 的 tagged hash 用得到），加上 exp228「解析不會讀過頭」的證明手法。**對錢包價值最高的一項** |
| **地址編碼（bech32/bech32m）與輸出腳本辨識** | 顯示的地址字串等於實際付款的 scriptPubKey；「這是找零」的判斷等於規格 | exp228 處理腳本的經驗最直接：辨識 P2WPKH、P2TR 範本，本質上是一個受限的腳本比對器 |

### 第二優先：守住種子與裝置狀態

| 功能 | 要證明的性質 | 已有的基礎 |
| --- | --- | --- |
| **金鑰衍生：BIP39 → PBKDF2-HMAC-SHA512 → BIP32** | 給定路徑，衍生出的金鑰等於規格；強化與一般衍生不混淆；常數時間 | 需要新的 SHA-512 與 HMAC 核心；點加法沿用第一優先的成果 |
| **PIN 錯誤計數與清除** | 失敗的嘗試永遠不會被還回來，即使在任何一條指令斷電；到上限就清除 | exp197 在四個韌體裡找到同樣的五個錯；exp198 在 Rust 證明了 `crates/client-pin` 的計數器；exp211 有 flash 斷電的 TLA+ 模型。下一步是位元組層級加上 flash 寫入模型 |
| **韌體更新驗證與防回滾** | 只接受簽章正確、版本號不倒退的映像 | Arm 這一側：exp166 驗 P-256 簽章、exp167 接上 exp143 的回滾，都是 Rust、沒有證明。驗證核心這一側：exp204 到 exp206 的 Lamport、WOTS、MSS 驗證器都已證明；exp211 的計數器只會掉位元。驗章只用公開資料，不需要常數時間，**最容易落地** |
| **種子產生** | 種子等於健康測試通過的樣本的雜湊；BIP39 助記詞的檢查碼正確 | exp222 到 exp224 的 TRNG 健康測試加 SHA-256 已經證明，exp224 連判決也搬進證明過的核心 |
| **秘密不殘留** | 核心停機時，暫存器與暫存區不留秘密；輸出只透過簽章依賴秘密 | exp207 的關係型證明可以延伸；exp204 已經證明「區域外什麼都不寫」；exp163 量過清除的成本 |

### 第三優先：模型檢查或測試就夠

| 功能 | 建議 |
| --- | --- |
| **簽章閘門與 UI 狀態機** | 「沒有使用者在裝置上確認，就不簽」用 TLA+ 驗證狀態機（exp211 已經用 TLA+ 找過反例）；最後的「可不可以簽」照 exp224 的模式，做成證明過的判決核心 |
| **USB 與 CTAP-HID 分框** | 只證明邊界上的分框與重組，exp199 已做；其餘用模糊測試 |
| **螢幕驅動、按鈕、多幣種、進階功能** | 測試即可。證明到「顯示緩衝區內容正確」為止 |

---

## 五、建議

1. **不要把整個錢包韌體當成驗證目標。** 用 exp224 的模式：證明過的核心做決定、C 殼層只負責搬資料。殼層越薄，沒有證明的部分就越少。
2. **每一份規格都要有獨立的對照。** BIP 的測試向量、Bitcoin Core、libsecp256k1。證明處理的是「照規格做」，差分測試處理的是「規格本身對不對」。
3. **先做驗證，再做簽章。** 驗章只用公開資料，不需要常數時間，也不受第三節第 2 點的晶片限制，可以先完整走一遍。簽章要等常數時間和秘密隔離都有答案再進行。
4. **殼層的特權要另外處理。** 在 RISC-V 這一側，要先有一個實驗回答「Machine 模式能不能縮到只剩一個證明過的監控程式」，簽章核心持有秘密才有意義。具體評估與「路徑 B 微模型」架構見 [Micro-Monitor 設計規劃文件](./micro-monitor/2026-10-14-0925-micro-monitor-in-lean4-design-zh-tw.md)。

### 建議的實驗順序

| 順序 | 內容 | Needs | 重用 |
| --- | --- | --- | --- |
| 1 | secp256k1 模 p 加法與乘法（exp229 已完成） | 0 | `lean/Rv32` |
| 2 | 純量乘法與 BIP340 驗章核心，取代 exp228 殼層裡的 `bip340.c` | 0（上板確認時 2） | exp228 的殼層與 `ecall` 介面 |
| 3 | 韌體更新驗證：exp206 的 MSS 驗證器接上 exp211 的計數器做防回滾 | 2 到 3 | exp206、exp211 |
| 4 | 交易解析、BIP341 簽章雜湊與「看到的就是簽的」定理 | 0 | exp208、exp228 |
| 5 | bech32m 地址與找零判斷 | 0 | 4 |
| 6 | BIP340 簽章、nonce 與常數時間，再照 exp212 的做法上板量時間 | 0，上板 2 | 2、exp207 |
| 7 | SHA-512、HMAC、PBKDF2，再到 BIP39 與 BIP32 | 0 | 1、exp208 |
| 8 | 位元組層級的 PIN 計數器加 flash 斷電模型 | 0，上板 3 | exp198、exp211 |

1、2、4、5、7 不需要板子，可以在雲端完成。3 與 8 需要 flash 和斷電，要有人在場。
