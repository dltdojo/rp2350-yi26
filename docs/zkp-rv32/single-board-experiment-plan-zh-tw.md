# 單板實驗計畫：一塊 RP2350 加一個靜態網頁的抗量子零知識隱私交易

<!-- SPDX-License-Identifier: Apache-2.0 -->

2026-10-16 規劃。**這份文件沒有用到板子，也沒有新的實測**；凡是數字都標明出處：實測（連到量過它的實驗）、估算（附算式），或待量。

密碼學模型、敘述、成本估算沿用審查修訂版計畫書 [pq-zk-payment-terminal-plan-zh-tw.md](./pq-zk-payment-terminal-plan-zh-tw.md)（下稱「計畫」）；背景知識見 [zk-background-notes-zh-tw.md](./zk-background-notes-zh-tw.md)。本文件只改一件事：**計畫第 2 節、第 5 節 Phase 3–4 與第 6 節原本要兩塊板子，這裡改成一塊板子，另一端由手機或電腦上的靜態網頁扮演**。理由是一個學生手上通常只有一塊板子，多板子的實驗設計與可用資源不符。

## 2. 單板配置：兩種模式

同一塊 Pico 2 經 USB 接到手機或電腦，網頁用 Web Serial／WebUSB 和它說話。兩種模式用**同一個證明格式**（第 4 節），所以兩邊的實作可以互相驗證。

| | 模式甲：板子證明、網頁驗證 | 模式乙：網頁證明、板子驗證 |
| --- | --- | --- |
| 場景 | 板子是硬體錢包，網頁是收銀機 | 網頁（手機）是錢包，板子是收銀機 |
| 私鑰 $sk$ 在哪 | **板子裡**，由 TRNG 產生，不出板子 | **瀏覽器裡**（網頁的儲存空間） |
| 證明方向 | 板子→網頁，MB 級 | 網頁→板子，MB 級 |
| 驗證方式 | 網頁邊收邊驗 | 板子串流驗證，不存整份證明 |
| 登錄層（作廢標記集合） | 網頁的儲存空間 | 板子的 flash，斷電中途不能壞（沿用 [exp211](../../experiments/exp211-the-leaf-signed-once/) 的寫入順序） |
| 收款人的代幣秘密（計畫 A7） | 經同一條 USB 線交給網頁 | 經同一條 USB 線交給板子 |

兩種模式要誠實寫出的差異：

- **「私鑰在誰手上」會跟著角色翻轉。** 模式乙的私鑰在瀏覽器裡，板子不再保護它；隱私性質（不洩漏 $sk$、金額、花的是哪一枚）兩種模式都一樣。
- **沒有獨立的登錄層。** 驗證的一方同時就是登錄層，所以防雙花只對這一個驗證端有效。這是單板的限制，不是設計的漏洞，文件和網頁都要寫明。
- **機密通道（計畫 A7）就是那條 USB 線。** 單板配置下，付款人和收款人的裝置是同一張桌上的兩台，這個前提要寫進每個實驗的「不證明什麼」。

## 3. 動手前要先確定的事實與矛盾

1. **網頁→板子還不能傳資料。** Hazard3 shell 的 [`usbdev.c`](../../tools/hazard3/shell/usbdev.c) 宣告了 bulk OUT（0x01），但只有送出佇列，沒有接收路徑。模式乙要板子收數 MB，所以這個方向是新工作，要放進 `tools/hazard3/shell/`，並在 `usbdev_test.py` 加主機端測試。Rust 韌體（`crates/cdc-console`）有雙向，但那是 Cortex-M33 路線。
2. **repo 裡沒有人量過 USB 吞吐量**，兩個方向都沒有，在手機上更沒有。證明是 MB 級：USB 全速 bulk 的理論上限約 1.2 MB/s，0.64 MB 至少 0.5 秒、3.1 MB 至少 2.6 秒（估算；實際要量）。
3. **網頁要算數百萬次 SHA-256 壓縮。** WebCrypto 是非同步、一次一個摘要，每次呼叫的額外開銷太大，所以網頁要用純 JS（或 WASM）的壓縮函數，速度在手機上也要量。
4. **三份實作要逐位元組一致。** Python 參考實作、網頁的 JS、Hazard3 的 C：同一個種子產生的證明要完全相同，而且彼此接受。這是兩種模式能互相檢查的根據，所以證明格式在 Z2 就要定死（第 4 節）。
5. **證明端的種子不能重用**（計畫 A5）。測試要有「給定種子」的確定性模式，才能比對三份實作；正式模式的種子＝PRF(TRNG ‖ $sk$ ‖ 公開敘述)。兩個模式要在程式裡分開，確定性模式不能被正式流程用到。
6. **網頁收到的 MB 級證明不能整份放進紀錄。** 照 [AGENTS.md](../../AGENTS.md) 與 vk26 的經驗，紀錄要以檔案存回、不能貼上；但存回的紀錄只放證明的 SHA-256 與逐輪的結果，不放證明本身。

## 4. 證明格式 v1（在 Z2 定死）

串流順序，讓驗證端可以邊收邊驗：

1. 標頭：格式版本、輪數 219、敘述代號（$pk=H(sk)$ 或交易）、公開輸入（交易時是 $rt$、$n$、$cid_{out}$、$cid_{change}$、$ctx$）、$salt$。
2. 挑戰值 $e$（放在最前面：驗證端先知道每輪要重算哪兩個玩家，計畫 3.6）。
3. 219 筆逐輪資料：兩個打開玩家的種子、未打開玩家的承諾、必要時第三個玩家的輸入分享、被打開玩家的 view。
4. 結尾：驗證端重算 $e$，和第 2 項比對。

每一項都有固定長度，或在標頭寫明長度；驗證端遇到任何不符，回報「第幾輪、哪一項檢查」。

## 5. 實驗序列：四個實驗、八個步驟

八個步驟 Z1–Z8 合成四個實驗。合併的原則：一個實驗仍然只有**一個主張**；同一個主張、同一份韌體、同一次燒錄的步驟放在一起。步驟只是實作的順序，不是各自的實驗，也不各自錄 capture。

| 實驗 | 主張 | 步驟 | 需要 |
| --- | --- | --- | --- |
| 實驗一 | SHA-256 原像的零知識知識證明：電路由 Lean 證明等於 SHA-256，Python 與網頁的證明逐位元組一致 | Z1、Z2 | 0 |
| 實驗二 | 一塊板子、兩種角色：同一份 $pk = H(sk)$ 證明格式，板子產生的網頁接受、網頁產生的板子接受；決定後續設計的常數在同一次燒錄量完 | Z3、Z4、Z5 | 2 |
| 實驗三 | 隱私交易與防雙花：同一個交易敘述，兩種角色各做一次，登錄層在驗證的一方 | Z6、Z7 | 2 |
| 實驗四 | 隱藏花的是哪一枚：Merkle 成員資格，量出證明隨深度的成長 | Z8 | 2 |

合併的代價也要記住：實驗越大，`check.sh` 與 `run.sh` 越久，改一處要重錄的範圍也越大；README 的宣稱越多，J1 能找到的缺口也越多。實驗二用「網頁選角色、韌體逐角色逐步驟回報」來保住失敗時的定位：每個角色、每個步驟各有自己的結果行與 LED 步驟號碼。實驗四最容易撞牆（時間與證明大小），可以依實驗三的實測決定要不要做、深度做到多少。

### 實驗一：零知識知識證明（Z1＋Z2）

#### Z1 電路就是 SHA-256

- **這一步要做到**：一份只有 AND、XOR、NOT 的閘列表，計算的就是 SHA-256 單區塊壓縮；Lean 證明它對**所有**輸入等於 `Sha.lean` 的規格。
- **內容**：Python 產生閘列表（由 32 位元加法器、Ch、Maj、Σ0／Σ1、σ0／σ1 組成），用 `hashlib` 對照隨機與邊界輸入；印出實際的 AND 閘數，對照計畫 3.4 的估算 22,696，不一致就改計畫的表。Lean 依元件逐一證明（加法器等於 `BitVec` 加法、Ch、Maj 等於規格），再組起來證明整個壓縮函數。
- **mutant**：加法器少一個進位、Σ 的旋轉量錯一個、訊息排程少一輪，都要被 Lean 拒絕。
- **不證明**：ZKB++；任何上板的東西。

#### Z2 ZKB++ 證明 $pk = H(sk)$，在 Python 與網頁上

- **這一步要做到**：Python 證明器產生的證明被 Python 與 JS 驗證器接受；JS 證明器以相同種子產生**逐位元組相同**的證明；竄改任一位元組都被拒絕，並指出第幾輪、哪一項檢查。
- **內容**：Python 參考實作（ZKB++ 三玩家、Fiat–Shamir、拒絕取樣、計畫 3.6 的種子衍生）；網頁共用的純 JS SHA-256 壓縮函數與 ZKB++；node 測試，用 Python 產生的測試向量檔。定下第 4 節的格式 v1。印出成本模型：證明大小、證明端與驗證端的壓縮次數，對照計畫 3.5 的 0.64 MB。
- **mutant**：挑戰值少吸收一個公開輸入、拒絕取樣不丟 `11`、打開錯的玩家、種子重用，都要被測試抓到。
- **不證明**：板子上的任何數字。

### 實驗二：一塊板子、兩種角色（Z3＋Z4＋Z5）

同一份韌體、同一個網頁、一次燒錄。網頁連上之後先跑 Z3 的量測，再由使用者選角色（Z4 或 Z5）；兩個角色的結果各自寫進紀錄。

#### Z3 板子與手機的常數

- **這一步要做到**：決定後面設計的幾個常數，一次燒錄量完，全部是貼上的實測（照 [the-board-is-the-loop.md](../the-board-is-the-loop.md) 的槓桿 2：一次燒錄問完整個矩陣）。
- **量測項目**：
  - 硬體 SHA-256 每次壓縮的週期數（CPU 餵資料；DMA 若可行一併量）；
  - `SUM0..7` 能不能寫回並續算（計畫 4.3 第 2 點，決定承諾的做法）；
  - Hazard3 上軟體 SHA-256 的吞吐量；
  - TRNG 取 32 bytes 的時間（[exp109](../../experiments/exp109-hardware-trng/) 已有每 64 bit 5.0–6.3 ms，這裡在 Hazard3 上重量一次）；
  - USB 吞吐量，**兩個方向**，對手機上的網頁與電腦上的網頁各量一次；
  - 網頁上純 JS SHA-256 壓縮的速度（手機與電腦）。
- **新增的共用程式**：Hazard3 shell 的 bulk OUT 接收路徑（`tools/hazard3/shell/`），附 `usbdev_test.py` 的主機端測試；既有實驗的 UF2 要逐位元組不變（只新增、不改既有的程式）。
- **之後**：依實測重算計畫 3.5 的時間欄，回填本文件。

#### Z4 模式甲：板子證明 $pk = H(sk)$，網頁驗證

- **這一步要做到**：板子用 TRNG 產生 $sk$，算出 $pk$，產生證明並經 USB 串流給網頁；網頁邊收邊驗，顯示 ACCEPT，並列出實測的產生、傳輸、驗證時間。
- **竄改**：網頁有「在第 k 輪改一個位元組」的按鈕，改過的證明被拒絕，並指出第幾輪、哪一項檢查。
- **一致性**：板子在確定性模式下，以 Z2 的測試向量種子產生的證明，和 Python 的逐位元組相同（`check.sh` 在 RTL 上比對，板子上再比對一次）。
- **LED**：先亮起再做任何可能卡住的事；失敗時的閃法帶步驟號碼（[AGENTS.md](../../AGENTS.md)「LED 是除錯通道」）。

#### Z5 模式乙：網頁證明 $pk = H(sk)$，板子驗證

- **這一步要做到**：網頁產生證明，經 Z3 補上的接收路徑串流給板子；板子不存整份證明，逐輪驗證，結果經 USB 回報、同時用 LED 表示。
- **竄改**：網頁送出改過的證明，板子指出第幾輪、哪一項檢查失敗；送到一半斷線，板子回報「不完整」，不能判成 ACCEPT。
- **量測**：板子的驗證時間、SRAM 峰值。

### 實驗三：隱私交易與防雙花（Z6＋Z7）

同一個交易敘述、同一份韌體，網頁選角色；兩種角色各有自己的登錄層。

#### Z6 交易敘述（公開 $cid_{in}$），模式甲，網頁當登錄層

- **這一步要做到**：計畫 3.3 的第 1、3、4、5 項（所有權、作廢標記、輸出綁定、金額守恆），先公開 $cid_{in}$、不做 Merkle；Z1 的電路證明擴充到這個敘述用到的每一個閘列表。
- **登錄層**：網頁保存作廢標記集合與已登錄的代幣承諾，做計畫第 6 節的劇本：正常支付、沒有私鑰的偽造、竄改 $cid_{out}$、雙花。
- **量測**：證明大小（估算 3.1 MB）、產生時間（估算 22 秒，只算 SHA-256）、傳輸與驗證時間。
- **要寫明**：這個版本**不藏**花的是哪一枚代幣（背景筆記 1.1）。

#### Z7 交易敘述，模式乙，板子當登錄層

- **這一步要做到**：同一個敘述，角色互換；板子驗證並把作廢標記寫進 flash，斷電中途不會讓一筆已接受的交易遺失，也不會讓同一個作廢標記被接受兩次。
- **內容**：flash 上的只增日誌，沿用 exp211 的寫入順序與主機端的斷電模擬測試；雙花劇本在板子上重演。

### 實驗四：Merkle 成員資格（Z8）

#### Z8 隱藏花的是哪一枚：Merkle 成員資格

- **這一步要做到**：加上計畫 3.3 第 2 項，深度 $d$ 取小值開始（例如 4，再試 10），量出證明大小與時間隨 $d$ 的成長，對照計畫的每加一層約 0.63 MB、證明端約多 4.5 秒（估算）。
- **角色**：先做模式甲（板子證明的時間是最先撞牆的數字）。

## 6. 減少重做的規則（從 vk26-alice 學到的）

- **格式、測試向量檔先定**（Z2），後面的實驗只引用，不各自重寫。三份實作共用同一組向量檔，任何一份改了輸出，check 立刻知道。
- **先改程式、後改文件**，一次改完再錄 capture；只改 `.md` 不必重錄。
- **README 引用的每一個數字，都由 commit 進來的程式印出來**，進到 `capture.txt`；板子上的數字由參考實作的 `--board` 檢查印出。
- **紀錄說出是哪一版韌體**（每輪一行版本），網頁的 Save 在檔頭寫自己的版本與檔案的字元數。
- **改 `tools/` 時，既有實驗的 UF2 與 `kernel.bin` 要逐位元組不變**；只用新增的方式擴充共用程式。

## 7. 待決與之後的方向

1. Z3 的結果決定：承諾用硬體 SHA-256 輪流服務、軟體多份狀態，還是分段鏈式（計畫 4.3）；隨機帶要不要改用更快的 PRG。
2. 雙核分工（計畫 4.3 第 3 點）要不要在 Z4 就做，或等 Z6 證明端時間撞牆再做。
3. 證明太大或太慢時，評估 KKW 或 VOLE-in-the-head，另開實驗，不改既有階段的格式。
4. 證明過的 RV32IM 驗證核心（Lean 證明驗證核心等於驗證規格）：工作量遠大於 exp208，留到最後。
5. 側通道：證明端整個過程都在用 $sk$ 運算，見 [Can this chip keep a secret?](../can-this-chip-keep-a-secret.md)。
