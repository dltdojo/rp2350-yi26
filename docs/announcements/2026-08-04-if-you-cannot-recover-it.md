# 救不回來,就別做出來

- **日期:** 2026 年 8 月 4 日
- **語言:** 正體中文
- **對應進度:** exp139 重做、exp142,與 tools/partimg、yi26 的燒前檢查,共 42 個實驗

---

前一天結束在一個問題上:RP2350 的 ROM 裡藏著整套 A/B 韌體機器,而它是空的。今天要做的事很單純 — 放點東西進去,讓那套機器動起來。做完了,但路不是直的,而彎的地方比終點更值得寫。

## 一筆對不上的紀錄

起頭不是程式,是一筆對不上的紀錄。exp139 把一張 partition table 寫到 flash 的起點,它的 README 開頭寫著「尚未在硬體驗證」,而同一個 repo 的另外兩份文件卻記著:這張表**燒過**,把板子弄成拖拉燒錄拒絕任何 UF2 的狀態,最後靠 PICOBOOT 才救回來。同一件事,兩種說法,而其中一種是反事實的 — README 甚至叫人用「拖一個好的 UF2 上去」來復原,那正是當時被觀察到**行不通**的動作。

比對不上更麻煩的是:當初把不 boot 歸咎於「那張表哪個字寫錯了」。今天把那八個字拿去跟 embassy-rp 自己的 encoder 逐字比,結果一模一樣 — 那是一張**合法**的最小分割表,不缺任何 item。所以「表寫錯了」這個假設從一開始就是錯的。幸好先盤問再動手:一個猜錯的根因,會讓人往完全錯的方向燒好幾輪板子。

## 通電,無聲,連 BOOTSEL 都沒有

有了 `yi26 pflash`,可以用最乾淨的方式重測 — PICOBOOT 直接把表和 image 寫到它們該在的絕對位址,不經過那個會亂路由的拖拉磁碟。寫進去了,REBOOT2,然後 — 什麼都沒有。不是應用韌體的 `1209`,也不是 BOOTSEL 的 `2e8a:000f`。板子通電,無聲。

這一下推翻了一個一直被當成理所當然的假設。整條 PICOBOOT 的故事都建立在「軟體一定救得回來」上面:燒壞了,板子會自己掉進 BOOTSEL,PICOBOOT 就搆得到它。但這裡沒有。kernel 的紀錄很乾脆 — 重開機那一刻 BOOTSEL 裝置斷線,之後什麼都沒再出現。

而板子暗掉、**沒有**掉回 BOOTSEL,這件事本身就是診斷。找不到可開機 image 的板子會進 BOOTSEL;這一塊沒有,代表 ROM 認為它**找到了**可開機的 image、跳了進去、然後在 USB 起來之前就當掉。崩潰的 image 不是不存在的 image,所以 ROM 不會退回去。復原的代價,是這整條路一直想避免的那件事:一根手指按在 BOOTSEL 上。

## 差了一個 0x1000

去讀了平台的開機章節和幾份第一手回報,答案收斂得很一致。ROM 從某個分割開機時,會把那個分割的實體起點**重映射**到 XIP base `0x10000000` — 不管它挑的是 A 還是 B,都映到同一個執行位址。這正是同一份 binary 能從任一 slot 開機的原因。

於是 exp139 原本的做法就是那個 bug。它用 memory.x 把 image 搬去 `0x10001000` 原地執行;但 ROM 把分割起點映回 `0x10000000` 之後,一個綁在 `0x10001000` 的 image 實際在 `0x10000000` 跑,裡面每一個絕對位址都差了 `0x1000`,第一個就 fault。啟動、崩潰、暗掉。整個災難就是一個 `0x1000`。

修法不是搬 image,而是**別搬**。image 照常 link 在 `0x10000000`,像任何一份普通韌體;表放 sector 0,image 放 sector 1,由一個叫 `partimg` 的組裝步驟在燒錄前把兩者拼好。表和 image 是分開的兩個東西、最後才黏在一起 — 這才是平台真正保存它們的方式。改完再燒,板子回來了,ROM 從分割開了機,回報它有一個分割,而 stock 板回報零。

## 與其事後救,不如當場拒絕

那塊暗掉的板子留下的不只是一個修好的實驗,還有一個方向的轉變。

原本的思路是「燒壞了就救」。但今天證明了救不一定救得回來 — launch-then-crash 會暗掉,PICOBOOT 搆不到,只剩手指。既然如此,與其把力氣放在事後復原,不如放在**當場拒絕造出救不回來的東西**。

`partimg` 已經是這個樣子:你給它一個沒 link 在 `0x10000000` 的 image,它根本不產出 UF2,直接說明原因。今天把同一個模式推廣到燒錄端 — `yi26 flash` 和 `pflash` 在碰板子之前先做一次結構檢查:ROM 靠 flash 前 4 KiB 的一個 block loop 開機,所以一個最低位址不是 `0x10000000`、或前 4 KiB 根本沒有那個 block 的 UF2,會在寫入前被擋下,而不是燒完變成一塊暗板才發現。

這裡有一條必須守住的誠實界線。結構性的磚 — link 錯位址、沒有開機 block — 是工具**能證明**的,所以擋得掉。行為性的磚 — 跑起來 panic、well-formed 但語意錯的 descriptor 不 enumerate — 沒有任何靜態檢查事先知道。所以一個綠燈只代表「ROM 找得到東西開機」,**永遠不代表「安全」**。把這條界線寫進工具的訊息裡,比讓一個綠燈養出假信心重要。正確的形狀是:**造出 artifact 的工具自己拒絕壞的**,而不是另外做一個要記得去跑的掃描器 — 目錄擋不住重複,前一篇講過;而一個能跳過的掃描器擋不住磚。

還有一個小發現屬於同一類。那個「下一次燒需不需要手指」的問題,韌體原始碼看得出來、UF2 看不出來:帶 1200-baud 重開機看門狗的韌體,下次燒是免手的;沒帶的(exp103、exp104 故意沒帶),下次就得按鈕。這是這個 repo 裡最常見的「接近變磚」的性質,而它現在會在燒之前被讀出來、講出來,而不是燒完才驚訝。

## 選擇一直在 ROM 裡

分割能開機之後,A/B 幾乎是自己掉出來的。

版本號放在每一個 image 自己的 IMAGE_DEF 裡,不在表裡 — 這是先確認、沒有猜的一件事。embassy-rp 有一個 `imagedef-none` 開關,關掉它預設注入的 IMAGE_DEF,韌體就能自己提供一個帶 VERSION item 的;而那個 item 用它自己 encoder 的 API 拼出來,不需要 picotool。兩個 image 是同一份原始碼,build.rs 讀環境變數,只有一個 slot 字母和一個版本號不同。表裡兩個分割,B 連結到 A — 那個連結就是整個 A/B 關係,它讓 `get_b_partition(0)` 從 exp139 的 `-17` 變成 `1`。

然後就是那一下。A 是 1.0、B 是 2.0,燒進去,板子開了 **B**。接著把 A 重建成 3.0 — 高過 B 的 2.0 — 其他什麼都不動,重燒,板子開了 **A**。同樣兩個分割、同樣的連結、同樣結構的二進位,只有版本號動了,ROM 就開了另一個 slot。

一般的建議會說:你想開哪個 slot,ROM 管不了,自己寫個 bootloader 去挑吧。而這個實驗就是那句話的反例攤在桌上 — 那個選擇不在你要寫的 bootloader 裡,它一直在 ROM 裡,你只要把版本號告訴它。

## 一件沒藏起來的事

過程裡有一個瑕疵值得直說,因為這個 repo 的規矩是不藏。exp142 的 `check.sh` 在這台機器上,密集呼叫 `yi26` 加上重複建置之後,USB 的列舉會有幾秒鐘抓不到板子,於是那半段「板子在跑哪個實驗」的檢查會跳過。它是良性的 — 檢查整體仍然通過,板子毫髮無傷,而 A/B 本身在真板上驗過兩輪 — 但它是一個還沒解掉的 gremlin,記在該記的地方,等哪天有理由再回頭。

今天的主線,如果要用一句話收:一塊救不回來的板子,把整個專案從「事後把磚救回來」推向「當場拒絕把磚做出來」;而把那一個 `0x1000` 搞對之後,分割開了機,A/B 的選擇也顯出來 — 它從來就在 ROM 裡,只是沒被問過。
