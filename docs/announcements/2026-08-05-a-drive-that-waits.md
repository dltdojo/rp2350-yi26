# 一個等到有話說才出現的磁碟

- **日期:** 2026 年 8 月 5 日
- **語言:** 正體中文
- **對應進度:** exp151、exp152,與 crates/log-ring、crates/mdns,共 52 個實驗

---

這個 repo 有一個從第一個會印字的實驗就存在、而一直沒被說出口的假設:**你有 Chrome。**

所有的除錯都經過 CDC,而從瀏覽器碰到 CDC 就是 WebUSB,那是 Chromium 專屬的。沒有一支 iPhone 有;Android 上的 Firefox 和 Safari 也沒有。對一個唯一的電腦是那種手機的學生來說,這個 repo 從第一步就是不能用的。

今天那扇窗開了。

## 板子端出自己的日誌

exp150 已經證明板子可以服務網頁,而它刻意**沒有**服務日誌 — 因為那要給 `usb-log` 加第二個消費者,而那個 crate 是這裡唯一的儀器,不能隨便動。

exp151 做了,而且小心地做。`usb-log` 多一個 feature,關掉的時候編出來跟以前逐位元相同 — 送去序列埠的那個佇列兩種情況下都沒被碰過。

兩個消費者,兩套**相反**的規則,而那正是重點:

```
佇列    滿了丟最新的  ——  讀者本來就在那裡
保留區  滿了丟最舊的  ——  讀者是後來才到的
```

在插上板子兩分鐘後才打開頁面的人,要的是**剛剛發生了什麼**。盯著序列埠的人,要的是**不要錯過下一件事**。沒有一種政策對兩者都對,所以有兩種。

## 讀 log 這個動作,會把 log 抹掉

修之前量到的第一個數字:**64 行保留區裡有 58 行是讀者自己的腳步聲。**

每個 HTTP 請求寫三行,而頁面每三秒自動更新一次。`usb-log` 的文件本來就警告過觀察者效應,但那說的只是「改變時序」。這個更嚴重 — **讀取本身在抹掉歷史。**

後來同一件事又出現兩次:鏈路上其他名字的 mDNS 查詢,以及**打開板子自己的 USB 磁碟時那一百個 `READ(10)` 指令**。最後那一次讓規則變得無法迴避,因為那些噪音**就是讀者走過來的那條路** — 第一支跑這個韌體的手機,打開磁碟、點了連結,然後看到一份內容全是「磁碟被打開」的日誌。

> **任何只因為「有人正在讀 log」而存在的東西,都不屬於那份 log。**

修法不是少寫,是有兩個目的地並且知道誰該去哪裡。而**失敗要留下** — 這條守衛我寫了三個版本都太鈍,每一個都誤禁了一樣值得留的東西:一行啟動訊息、一個 bug 回報、另一個函式的迴圈。**分野不是重要性,是這行字屬於誰的 log。**

## 一個正確的實作,被別處的決定否決

日誌解決了,但「**找到**板子」還需要 WebUSB — 位址是從 CDC 讀出來的。所以給板子一個名字:`yi26.local`。

Android 從 2021 年起就在解析器層支援 `.local`(RFC 6762 §5.1 的 one-shot 查詢),Chrome 網址列從 Android 12 起走那條路。我這次先查證才寫,因為當天已經因為沒查證 Android 的行為走錯兩次。

`crates/mdns` 拒絕的比接受的多,包括**壓縮指標** — 那是合法的 DNS,但對一個單一問題的查詢毫無用處,而且正是 DNS parser 長出「讀自己尾巴的迴圈」的地方。有一個測試我寫錯了,解析器糾正我:**200 不是過長的標籤,是壓縮指標**,因為長度位元組的高兩位設起來就是指標的樣子。

在 Ubuntu 上它答得好好的。在手機上 `DNS_PROBE_FINISHED_NXDOMAIN`。

而板子自己的 log 證明它是無辜的:

```
mdns: listening as yi26.local
mdns: 318 bytes ignored: NotAQuery
```

多播**到得了**板子 — 那些是 mDNS 回應,手機上有東西在那條線上宣告服務。群組加入了、socket 活著、手機也在參與。**唯一沒到的,是一個問 `yi26.local` 的問題。**

一個否定的結果,值得跟正面結果一樣多:**一個實作可以是對的、測過的、正在跑的,然後因為別人在別處做的一個路由決定而完全沒用。**

## 名字不能打,只能點

就算解得出來也還有一關:Chrome 的網址列會把 `http://yi26.local/` **連 scheme 一起**拿去 Google 搜尋。截圖是一頁搜尋結果。

所以名字必須是**可以點的**,不是可以打的。而那需要一個頁面,而那個頁面要先到手機上 — 又繞回原點。

## 直到磁碟自己帶著答案出現

一個月前 exp137 量過:一台服務**已掛載**磁碟的主機,會用自己的快取回答檔案讀取。我拿這個結論把「磁碟帶連結」整條路否決掉了 — 位址是開機十秒後才到的,寫進去也沒人看得到。

**那個結論被我用得太寬了,而拿著手機的那個人推了回來。** exp137 同一段也量了另一半:

> **重新掛載就讀到新的了 — 那些位元組真的動了。**

**一個從來沒被掛載過的磁碟,沒有快取可以回答。**

所以 exp152 不去改一個已掛載的磁碟。它在知道位址之前回報 **NOT READY / MEDIUM NOT PRESENT** — 插著空讀卡機的樣子,而主機知道拿它怎麼辦:什麼都不做。位址到了,媒體才存在,而主機接下來做的是**第一次掛載**。

中間狀態看得見:位址之前,`/dev/sda` 存在而大小是 **0B**。之後,`sda 64K YI26 BOARD`。

## 於是這樣

```
插上 → 打開乙太網路分享 → 等 LED 快閃 → 檔案 app → 點 OPEN.HTM → 點連結 → 日誌
```

沒有 WebUSB、沒有打字、沒有書籤、**沒有任何檔案需要先傳到手機上**。

## 兩件我做錯而值得寫下來的事

**一個被切斷的頁面,長得像一個能用的頁面。** 連結顯示成 `http://10` — 一顆可以點、而且真的會通的按鈕,臉上寫著半個位址。頁面緩衝區是 640 byte 而渲染結果剛好填滿;`href` 在標記裡排前面所以活了下來,後面的顯示文字被切在位址中間。

證據在螢幕上放了一小時:一份目錄列表寫著 `OPEN.HTM 640`,對著一個宣告成 `[0u8; 640]` 的緩衝區。**沒有人把那兩個數字放在一起看。** 一個會靜靜截斷的緩衝區,需要有東西在它截斷時出聲。

**而順序比那個重要。** 重開機之後乙太網路分享是關的,而那個開關**在插上東西之前是灰的** — 所以順序只有一種可能,而在第 2 步拖太久就是會失敗的地方:板子那邊永遠不會放棄,但一台被告知「沒有媒體」夠久的主機可能會停止查看。

那三個步驟現在寫在磁碟自己的 README 第一段,給任何走到那一步的人看。而等待中的日誌現在講的是**要做什麼**,不是狀態 — 「還在要位址」沒告訴任何人該怎麼辦。
