# 有線,但沒有位址

- **日期:** 2026 年 8 月 5 日
- **語言:** 正體中文
- **對應進度:** exp148、exp149,與 crates/dhcp,共 49 個實驗

---

Pico 2 沒有網路介面。但它有 USB,而 USB 上可以宣告自己是一張**虛擬網路卡** — CDC-NCM — 於是接上去的那台機器就成了線的另一端。那台機器可以是筆電,也可以是手機,而後者才是這條路值得走的理由。

## 兩件事,一直被當成一件

「網路通了」其實是兩個獨立的成就,而它們平常被壓成一句話:

**第一,主機上有個驅動程式認領了這個介面。** 在那之前,板子只是一個沒人搭理的裝置。NCM 讓這件事變得**看得見**:一個 CDC-NCM 的資料介面宣告了兩組設定,而主機只有在某個驅動決定要擁有它的時候,才會去選那個帶端點的那一組。所以韌體自己知道有沒有人認領它。

**第二,有人發位址。** DHCP 是一場**對話**,而對話需要另一邊願意當伺服器。那是主機的性質,不是韌體的。

exp148 把這兩件事拆開,用一顆 LED 報告:不亮是沒人認領,慢閃是有人認領但沒有位址,快閃是拿到位址了。在 Ubuntu 上,核心在開機後 **400 毫秒到 1.4 秒**之間綁上驅動 — 板子什麼都沒做,是核心做的,而板子知道。

## 死結不是手機的毛病

原本的預測是:**手機**會讓板子停在「有線、沒位址」,因為 Android 對 USB 乙太網路跑的是 DHCP **客戶端**,而板子也是客戶端 — 兩個客戶端互相等待。

結果這台 Ubuntu 一模一樣。NetworkManager 對一個新的有線介面,預設就是當客戶端。

所以那句話要反過來說:**這個死結不是手機的性質,是「沒有被特別交代過的主機」的性質。** 而筆電可以被交代(一行 `nmcli`),手機沒有那個設定。

這讓下一步從「補救手機」變成「**從每一台主機手上拿掉一個手動步驟**」。

## 於是板子自己發位址

`embassy-net` 只有 DHCP 客戶端。所以 exp149 開一個 UDP socket 在 67 埠,自己講那四個封包:

```
客戶端 ──DISCOVER──▶  「有人在嗎?」        廣播,因為它還沒有位址
       ◀──OFFER────   「你可以用 192.168.7.2」
       ──REQUEST──▶   「我要了」            還是廣播,還沒正式
       ◀──ACK──────   「是你的了,一小時」
```

四個封包。DHCP 其他的能力 — 中繼、位址池、拒絕、續租記帳、衝突偵測 — 全部是因為真實網路上有很多客戶端、好幾台伺服器和一個路由器才存在的。**一條 USB 線的另一端只有一台主機。**

協定放在 `crates/dhcp`,裡面**沒有 socket**。這樣 `cargo test` 才能做板子做不到的事:把一個封包**在每一個長度上切開**,餵給解析器三萬次,在你正在讀這段文字的這台機器上。

## 兩個測試,解析器糾正了我兩次

我先寫了「每一個截斷都該被拒絕」。243 byte 的時候它說不對 — 那是 header、magic cookie 加上一個完整的訊息型別選項,**一個合法的最小 DISCOVER**。我換了個斷言,244 byte 它又說不對 — 那一刀切進了下一個選項的中間。

真正的規則是這個,而且它不明顯:

> **切在選項邊界,是一個比較小的合法封包。只有切在選項中間才是壞的。**

因為 DHCP 的選項自帶長度,而結束標記只有在後面還有東西的時候才需要。這條規則現在寫在測試的名字裡,因為它就是「拒絕真實客戶端」和「讀過緩衝區尾端」之間的那條線。

## 三個刻意的決定,每一個都是一個測試

**位址池裡只有一個位址。** 線的另一端只有一台主機。沒有租約表、沒有池的算術、沒有到期記帳。

**每一個回覆都廣播到 255.255.255.255。** 直覺的做法 — 單播到那個要給出去的位址 — 做不到,因為客戶端還不擁有那個位址,不會回應對它的 ARP。真正的伺服器靠「注入一筆沒人告訴它的 ARP 紀錄」解決;廣播讓這個問題直接消失。

**不給 router option,不給 DNS。** 兩個都是慣例,而兩個都是假話:這塊板子是一條線的一端,什麼都不路由。而主機被這樣告知之後**會照做** — 一支認定 USB 線是自己上網路徑的手機,是一支失去上網路徑的手機。

這個決定的證據在主機的路由表裡:它只裝了一條通往那個子網的路由,**其他什麼都沒有**,預設路由原封不動。

## 一個彎路,而答案就在三個資料夾外

exp149 大約三次開機會壞一次:USB 列舉正常、1200-baud 的重開機監聽正常,而 TRNG 讀取之後才啟動的每一樣東西都沒跑。

我去讀了 embassy-rp 的 TRNG driver,找到一個看起來很像的 waker race,判定是永久卡死,改用不碰中斷的阻塞版本 — 結果變成**每次都壞**,而且板子直接離開 USB 匯流排,因為 busy-wait 擋在列舉前面。

答案一直在這個 repo 裡。`exp109-hardware-trng` 就是為這件事做的實驗,而我留在預設值的那個常數就是它的標題:

> embassy-rp 的預設是 25 個時脈週期。在這塊板子上那太快了 — 健康測試會退回整個區塊然後重來。連續三次取 64 bits:**0.38 秒、31.4 秒、14.5 秒**。設成 1000 是 5–6 ms。
>
> 「總是能成功、但有時要花半分鐘」比壞掉更難診斷。

沒有任何東西卡住。我在一次花了三十秒的開機之後**七秒**去讀 log。

`experiments/README.md` 的第 2 步就是「先問這個問題是不是已經被回答過」。我對外部的 driver 原始碼查得很仔細,對自己 repo 裡以此為題的實驗反而沒查。而它換來的那條規則現在寫在兩份韌體的程式碼裡:**在 USB 起來之前,不准有任何東西擋住 executor。**
