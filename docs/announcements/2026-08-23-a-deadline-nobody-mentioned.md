# 一個沒人提過的期限

- **日期:** 2026 年 8 月 23 日
- **語言:** 正體中文
- **對應進度:** exp168 – exp174,與 crates/cbor,共 73 個實驗

---

簽章之路驗證了晶片的能力,而安全金鑰之路 (Authenticator road) 要打造的是一件真正的「器具」:**讓這塊板子成為一顆實體安全金鑰,在任何一台電腦的 Chrome 瀏覽器裡,直接在真實網站上完成 WebAuthn 註冊與無密碼登入。**

這條路不同於以往。CDC 序列埠寫得再簡陋,它依然會列舉並印出訊息;但安全金鑰只要有任何一個位元組不合瀏覽器的胃口,螢幕上就只會冷冷跳出一句「發生未知錯誤」。

為了不被黑箱困住,我們從最底層的封包一步一步手刻上去。

## 從一無所知的安全金鑰開始

exp168 打造了一顆「完全沒有任何密碼學功能」的安全金鑰。

它只實作了 USB HID 傳輸層、`CTAPHID_INIT` 與 `CTAPHID_PING`。透過精心編寫的 HID Report 描述元,它能直接被 Linux 系統的原生 udev 規則辨識為 FIDO 裝置,不需要使用者安裝任何自訂規則。

當 host 端的 `fido2-token -I` 向它查詢能力時,它回傳了 `caps: 0x08 (nowink, nocbor, nomsg)` —— 用 CTAP 協定本身的標準語言,誠實地宣告自己「什麼都不會」。

接著,exp169 與 exp170 打造了完全無動態記憶體配置的 `crates/cbor` 解析器與編碼器。它嚴格拒絕一切非規範 (non-canonical) 的 CBOR 位元組,並對每一個長度欄位進行邊界檢查,防範惡意建構的跨站請求。

## 不存金鑰的金鑰

exp171 與 exp172 實作了完整的憑證建立 (`makeCredential`) 與登入斷言 (`getAssertion`)。

這裡有一個漂亮的架構設計:**板子完全不需要維護任何金鑰資料庫,Flash 裡不存任何使用者的私鑰。**

```
Credential ID = 32 位元組隨機數 ‖ HMAC(裝置秘密, "id" ‖ 隨機數 ‖ 網站網域)[前 16 位元組]
私鑰          = HMAC(裝置秘密, "key" ‖ 計數器 ‖ 隨機數 ‖ 網站網域) 產生的 P-256 純量
```

當使用者要登入時,瀏覽器把 Credential ID 傳回給板子,板子以恆定時間 (constant-time) 比對 HMAC 標籤。只要標籤正確,代表這把金鑰當初確實是由本裝置為該網站所產生,板子便能當場重新衍生出私鑰並簽署斷言。

在這個過程中,我們也看清了協定的真相:**宣告「使用者是否在場 (User Presence)」的 UP 位元,完全是裝置自己的單方宣稱**,協定本身沒有任何機制能查核背後是否真的有人按下了按鈕。

exp173 將這套手刻韌體與官方的 `libfido2` 對接,順利通過了嚴格的命令列測試。

## 走進真實瀏覽器

exp174 是整條軌道的收官之作。我們打開真實的 Chrome 瀏覽器,在本地網頁與 `webauthn.io` 實測。

韌體第一次嘗試就成功完成了註冊與登入。但當我們開始測試各種邊界情況時,兩個隱藏極深的現象浮出水面。

### 一個跨越六十五個實驗的伏筆

在第一輪測試中,從按下按鈕到產生憑證,板子竟然要花上 **15 到 21 秒**。

衍生金鑰只需 44 毫秒,簽章只需 54 毫秒。那十幾秒究竟花在哪裡?

計時結果顯示,時間全部花在了一行看似人畜無害的呼叫上:向板載 TRNG 索取 32 位元組隨機數。

這是 **exp109** 在很久以前就寫下的警告:HAL 預設的 `sample_count = 25` 採樣過快,導致硬體自我健康檢查不斷判定隨機性不足而重試。exp109 當時特別寫道:「一個能動但有時要花半分鐘的東西,比直接壞掉的東西更難找,因為它沒有報錯、沒有崩潰,只有一段空白。」

從 exp171 到 exp174,所有的單元測試都亮綠燈,因為命令列工具願意無條件等待。直到真實瀏覽器站在對面,這個沉睡了六十多個實驗的瑕疵才被逮個正著。將採樣數改為 exp109 推薦的 1000 後,**採樣時間從 21 秒驟降至 10.5 毫秒 (提速 1400 倍)**。

### 沉默的代價與心跳封包

當我們把隨機數修快之後,另一個問題出現了:如果使用者遲疑了幾秒才按下按鈕,Chrome 會突然中斷流程,拋出 `NotAllowedError`。

瀏覽器不會永遠等下去。在沒有任何通訊的情況下,Chrome 的耐心極限大約是 **20 秒**。

解決方法是 CTAP 規格裡的 `CTAPHID_KEEPALIVE`。當板子處於等待使用者按鍵的狀態時,韌體每秒主動發送數次心跳狀態封包,告訴瀏覽器「我還活著,正在等待使用者互動」。

實測對比非常震撼:

```
關閉 Keepalive: 等待 25 秒後回傳 -> Chrome 拒絕 (NotAllowedError)
開啟 Keepalive: 等待 25 秒後回傳 (發送 249 次心跳) -> Chrome 順利接受並完成註冊!
```

心跳封包並不是讓金鑰能運作的本質,但它是讓金鑰在真實世界面對「動作不夠快的人類」時,依然能穩定運作的關鍵守衛。

此外,當使用者在瀏覽器端手動按下「取消」時,瀏覽器會送出 `CTAPHID_CANCEL`。過去的韌體會將其視為無效指令並繼續在背景簽章,現在韌體能在第一時間響應取消並立刻中止密碼學運算。
