# 誰還能敲門

- **日期:** 2026 年 8 月 6 日
- **語言:** 正體中文
- **對應進度:** exp153、exp155、exp161,與 crates/http-route,共 55 個實驗

---

這個 repo 在網路之路上曾經白紙黑字寫下一句武斷的結論:「桌機可以被告知做路由和 NAT,而手機不行 —— 因為手機沒有這種操作介面。」

這句話在今天被我們自己親手推翻了。

推翻它的不是什麼高深的黑魔法,而是我們終於把前面三個實驗已經在要大家開啟的開關看清楚了:Android 的「乙太網路分享 (Ethernet tethering)」。那個開關的名字寫著分享,而它實際做的事,就是把手機變成 DHCP 伺服器、預設閘道,以及一台扎扎實實的 NAT。

## 從手機連向網際網路

exp153 把先前架好的網路堆疊反過來指。板子不再只是等著別人連進來的伺服器,而是主動向外發問的客戶端。

插上 Pixel 9a,開啟乙太網路分享,板子在 30 秒內取得租約與閘道位址,然後向 `1.1.1.1` 發出 TCP 連線。9 毫秒連上,23 毫秒完成整個 HTTP 交換。

這趟交換量出兩件在現代網際網路上極具代表性的事實:

對 `http://1.1.1.1/` 的普通請求,收到了 `301 Moved Permanently`,被重定向到 `https://`。這是一塊沒有 TLS 堆疊的微控制器在 2026 年面對的現實 —— 網路上幾乎所有內容都已經對純文字 HTTP 關上大門。而第二個請求對 `http://cp.cloudflare.com/generate_204` 發出,收到的是乾淨的 `204 No Content`。強制入口 (Captive Portal) 探測端點之所以存在,正是因為它必須在網路建立信任前運作,因而成為純 HTTP 在網路上少數被允許通行的地方。

這不是警告,這是一組量測數據。板子沒有 TLS,而這就是不帶 TLS 的代價與邊界。

## 並行是免費的,直到遇到共享的週邊

既然板子能在網路上說話,下一步就是讓一個通訊埠承載多個任務。

exp161 在同一個 TCP 80 埠上開了四扇門:`/`、`/log`、`/status` 與 `/trng`。以往若要讓板子同時做兩件事,在 USB CDC 上得宣告兩組介面、生出兩個裝置節點,還得在 host 端小心分辨誰是誰;在 HTTP 抽象層上,增加一項服務只是一個 match 分支。

非同步執行器 (async executor) 的威力在這裡一覽無遺:四個客戶端在同一瞬間分別索取四個不同路徑,全部在 10 到 20 毫秒內平行處理完畢。

但當三個客戶端同時索取「同一件東西」—— 向板子上唯一的硬體亂數產生器 (TRNG) 各要 1 KiB 隨機位元組時,幻象結束了,物理世界的排隊開始了。

```
第一個客戶端: 採樣花費 220,899 µs, 等待鎖 9 µs
第二個客戶端: 採樣花費 225,514 µs, 等待鎖 221,259 µs
第三個客戶端: 採樣花費 224,486 µs, 等待鎖 450,273 µs
```

每個客戶端的採樣時間都是恆定的,但第二與第三個客戶端付出了成倍的等待時間。而在這三個請求塞車的同時,另一台客戶端發出的 `/status` 請求,卻在 3.7 毫秒內乾淨俐落地返回。

耗盡的從來不是 URL 空間,而是實體週邊。非同步框架能免費多工處理無狀態的邏輯,但無法憑空變出第二顆硬體。

為了把這四扇門做好,`crates/http-route` 還學到了一個底層教訓:TCP 讀取是分片的,一個沒送完的 `GET /sta` 絕不能被當作對 `/sta` 的 404 請求。解析器必須區分「資料不完整 (Incomplete)」與「明確拒絕 (Refused)」,並在封包斷片時乖乖等待下一筆位元組。

## 誰在敲門:危險來自你正開著的瀏覽器

前面所有的實驗,每個端點都只負責讀取資料。只要沒有任何端點會改變板子的狀態,安全性就還只是個理論問題。

exp155 是本專案第一個「只要發送 HTTP 請求就能改變硬體狀態」的實驗 —— 透過網址切換板子上的 LED 燈號。

許多人直覺認為,把控制介面放在 HTTP 上的風險是「同區域網路裡的其他人可能會來搞破壞」。但真機量測出來的威脅更加貼身,而且就在眼前:真正的威脅是裝置擁有者自己正在執行的瀏覽器。

我們把包含探測腳本的網頁放在另一個本機來源 (`http://127.0.0.1:8000`),並在 Chrome 中打開。結果如下:

```
<img src="http://10.42.0.250/led/fast">            -> 板子上的 LED 立即變成快閃
跨站表單 POST http://10.42.0.250/led/slow          -> 板子上的 LED 立即變成慢閃
fetch POST /control/led/off (帶 X-Yi26-Control)    -> 請求被拒絕,LED 完全沒動
```

這三行量測結果揭露了 Web 安全最容易被誤解的本質:

第一,**CORS 從來不阻止請求發送**。CORS 規範的是瀏覽器能不能讓網頁腳本「讀取」回應內容。一個 `<img>` 標籤根本不需要讀取任何回應,它只需要把請求打出去 —— 而只要請求抵達,板子上的 LED 就已經被改變了。

第二,在 `<img>` 的無 CORS GET 請求中,瀏覽器甚至**完全不附帶 `Origin` 標頭**。板子在日誌裡只能記下「被無來源的請求改變了狀態」,既無法拒絕,事後也無從追查是哪個惡意網頁所為。

第三,第三次敲門之所以被擋下,關鍵在於非簡單標頭 `X-Yi26-Control`。自訂標頭迫使瀏覽器在採取行動前,必須先發送一次 `OPTIONS` 預檢請求 (Preflight)。正是這次預檢,讓板子有機會在動作發生前審查來源,並用沉默 (不回傳 `Access-Control-Allow-Origin`) 表達拒絕,瀏覽器因而終止了後續真正的控制動作。

這條防線的邊界也必須講明:它防禦的是瀏覽器內未經授權的跨站分頁,而不是本機上的 `curl`。任何原生程式都能偽造 `Origin` 標頭,正如任何程式都能直接打開 USB CDC 序列埠一樣。

## 虛擬磁碟的最後一哩路

在完成這一連串網路控制的同時,我們也修正了一個重複出現三次的算術錯誤:過去文件一直將「CDC-ACM (2 介面) + CDC-NCM (2 介面) + Mass Storage」誤算為 6 個介面。`lsusb` 的真實輸出證明是大容量儲存裝置的兩個端點被誤當成了兩個介面,實際總數是 5 個。

這 5 個介面各司其職:CDC-ACM 守護著 1200-baud 免手動燒錄與命令列除錯日誌;CDC-NCM 提供了跨平台的無驅動乙太網路;而延續自 exp152 的虛擬 FAT12 磁碟,則在板子成功取得 IP 租約的那一刻才宣告掛載。

手機使用者不需要打字,不需要猜測 mDNS 解析,也不必擔心網址列把私有 IP 拿去 Google 搜尋。插上傳輸線、開啟乙太網路分享、點開手機檔案管理員裡的 `OPEN.HTM`,點擊連結 —— 網頁隨即在手機瀏覽器中呈現,硬體控制與日誌檢視在指尖完成。
