# 接縫是一個檔案

- **日期:** 2026 年 8 月 2 日
- **語言:** 正體中文
- **對應進度:** exp101 – exp116,加上 docs/platforms.md,尚無正式版本釋出

---

這個專案從第一天就有一個沒被檢查過的假設:你有一台 Linux 機器。所有腳本都是在 Ubuntu 上寫的,文件也照實說只在 Ubuntu 驗證過,聽起來很誠實,但誠實跟有用是兩回事。對一個買了板子卻沒有那台機器的人來說,「只在 Ubuntu 驗證過」跟「你做不了」沒有差別。

真正去看的時候才發現,問題被自己的敘述框住了。編譯韌體和燒錄韌體其實毫無關係。編譯需要工具鏈、幾百 MB 的磁碟,完全不需要硬體;燒錄需要板子和一個能把檔案拖進磁碟的檔案管理員,完全不需要編譯器。中間的接縫是一個 .uf2 檔案,而一個檔案是可以搬家的。那台 Linux 機器可以是租來的,按小時計費,編完把檔案下載回自己已經有的那台電腦,拖進板子的開機磁碟就好。而且那台雲端機器也剛好是讓 AI 代理幫忙改程式的好地方。

這件事沒有用推理帶過。從一個乾淨的 git clone 開始,在一個這個 repo 從沒去過的目錄裡,把當時的五個韌體實驗全部編過一輪,檢查 UF2 的家族識別碼正確,其中一個的檔案大小跟該實驗文件裡記錄的驗證值一模一樣;在完全看不到板子的情況下跑它的檢查腳本,五個通過、一個略過、狀態碼為零 —— 沒有板子不算失敗。最後把那個從乾淨 checkout 編出來的 .uf2 燒進真的板子,三個 task 的日誌都正常。順帶量到一件本來會被當成理所當然的事:兩次乾淨 clone 編出來的 .uf2 並不是位元組相同的,差異落在幾千個位元組。韌體行為一樣,檔案不一樣,這個專案裡沒有任何東西依賴它們相同,所以就照實寫進文件,而不是假裝沒看到。

不過這只解決了一半。從第四個實驗開始,板子做的每件事都是透過 USB 序列埠報告的,而在一台沒有工具鏈的機器上,讀那個序列埠就是唯一還需要安裝軟體的動作。桌機上這不算問題,隨便一個終端機程式都行。手機上就是死路。

所以後面兩個實驗是讓瀏覽器直接去讀。第一個只做描述元:開啟裝置、把它的介面和端點印成一棵樹,拿去跟 lsusb 的輸出對照。第二個真的把介面接管過來,親手送出 CDC 主機該送的兩個控制傳輸,然後讀那個端點,日誌就出現在網頁上。**這兩個實驗都沒有改動任何韌體。** 板子印的東西跟以前一模一樣,只是換了別的東西在聽。

會走這條路而不是別條,是被一個事實決定的:Android 上的 Chrome 有 WebUSB,但沒有 Web Serial。桌機上顯而易見的那個 API 在手機上不存在,而手機正是這整條路線的終點。另外也刻意不用本機的網頁伺服器。在桌機上跑一個 localhost 很方便,在手機上根本辦不到,而一個只在桌機成立的方案不能算解決了問題,所以網頁就是一個檔案,從檔案管理員直接打開。

代價講清楚。WebUSB 只有 Chromium 系的瀏覽器有,Firefox 和 Safari 都沒有,這是這個專案第一次在文件裡指名某一家的軟體,而買到的東西就是那支手機。Linux 上還要一條 udev 規則才能讓瀏覽器打得開裝置,所以工具多了一個子命令專門處理它,盡量不讓使用者去手打那些容易打錯的東西。過程中也量到一件沒有人會事先告訴你的事:Chrome 的 WebUSB **不會**幫你把核心的驅動程式移開,所以接管介面會失敗,而那個錯誤訊息裡沒有任何字指向這個原因。這件事是量出來的,不是猜的,現在寫在該實驗的文件裡。

還沒完成的部分也照說。手機那條路目前還是未完成狀態,文件裡標的就是未完成而不是推薦。第一個實驗確認板子、線、主機三者看得見彼此,那個實驗在一台沒有板子的機器上本來就跑不了,這是唯一真正的犧牲,無法補救。而所有這些仍然只在 Ubuntu 和一塊 Pico 2 上驗證過,其他平台的路徑寫了但沒有人跑過,文件寫的就是這句話。

回頭看,這次改的其實不是功能而是定位。原本是「教你用你的電腦寫韌體」,現在是「教你寫韌體,而那台電腦可以是租來的,而你手上那台可以只是拿來拖檔案和看日誌」。
