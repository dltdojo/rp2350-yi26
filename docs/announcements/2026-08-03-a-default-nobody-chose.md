# 從來沒有人選過的預設值

- **日期:** 2026 年 8 月 3 日
- **語言:** 正體中文
- **對應進度:** exp134、exp135 與 tools/pages,共 35 個實驗,尚無正式版本釋出

---

上一篇講的是一場抽獎怎麼被實測改了四次。這一篇講的東西更小也更難看見:**有些行為從來不是誰決定的,它只是某個容器的預設值,被沉默地接受下來,然後在三十三個實驗裡一路活著。**

起頭是一個很平凡的問題。開關 LED 是嵌入式最常見的入門任務,而 exp127 的 README 第十五行寫著 `No browser`。缺的是什麼?不是網頁 — 這個 repo 從 exp120 起就有一個能寫 OUT endpoint 的頁面。**缺的是一個輸入框的語法。** exp127 的 LED 要收 `0x01`,而那不是任何鍵盤打得出來的字元;在網頁裡打 `1`,送出去的是 `0x31`,韌體正確地拒絕它。

所以 CLI 能開關 LED,瀏覽器不能,而差別只是 `yi26 send` 有 `\xNN` 轉義而網頁沒有。這件事沒人決定過,它只是沒被問過。

## 兩個工具箱,和它們之間那條不會消失的線

補這個缺口逼出了一個更大的問題:網頁跟 `yi26` 其實是同一個工具箱的兩半,而只有一半被歸檔在工具區。日誌檢視器、燒錄模式頁、descriptor 檢查器 — 這些**對每一個韌體都能用**,它們是工具;而抽獎頁認得一個韌體的協定,它是**器具**。分界只有一個問題:這個頁面對每一個韌體都能用嗎?

重疊的地方只有四件事:讀日誌、送位元組、進燒錄模式、看 descriptor。其餘八件 `yi26` 做得到而網頁做不到 — 讀主機的 USB 樹、寫 udev 規則、掛載檔案系統、解 UF2 容器、從 kernel 手上搶介面 — 而原因全部是同一個:瀏覽器沙箱。**這條線不會因為誰努力而移動**,所以「盡量讓兩邊功能一致」是錯的目標。正確的目標是那四件重疊的必須語彙一致,而其餘的必須明顯不同、並且寫清楚為什麼。

語彙一致這件事是被檢查的,不是被承諾的。頁面的 escape 解析器會被 `check.sh` 抽出來,餵 `yi26` 自己單元測試用的那批案例,再比對兩邊接受的字母集合 — 因為只有一邊多加一種,前一項會毫無察覺地通過。

依照拷問流程去翻了內部舊專案,結果是警告而不是背書:它們早就有工具目錄放網頁,而同一個專案裡仍然長出第三個日誌檢視器,另一個專案更把整份工具複製進實驗目錄。**目錄擋不住重複,斷言才擋得住。**

還有一個決定不是我的。我原本打算把實驗裡的頁面換成連結,而使用者說那樣脈絡就消失了 — 實驗的意義就是知道之前做過什麼、後來變成什麼。於是四個原始頁面全部留在原地,標記凍結,指向維護版。exp120 是最清楚的例子:**它送不出 `\x01`,而那個缺陷正是新工具存在的理由。** 一個連結會把它藏起來。

## 十六行的佇列,和一個沒人選過的方向

抽獎那條線留下一個帳:每一份瀏覽器 capture 都被咬掉一塊。`(+50 lines lost)`、`(+64)`、`(+89)`。

顯而易見的診斷是佇列太小,而算術不同意。十六行、每秒一行,就是十六秒;六十四行是一分鐘。**而空窗是「沒有人在看」的那段時間,它沒有上界。** 四倍的 RAM 買到四倍一個本來就不夠的數字。

真正被跳過的是另一個問題。`usb-log` 自己的文件寫著「只有兩個選擇:等,或丟」。等確實出局 — exp104 量過,呼叫端被 `write_all` 卡住,兩個計數值相隔二十一秒才抵達。但「丟」藏了第二個問題:**丟哪一行?**

`Channel::try_send` 丟的是**新來的那一行**,所以滿了的佇列保留的是**最舊的十六行**。這從來不是誰做的決定,是容器的行為被當成了決定。而它的後果剛好最糟:缺口總是結束在讀者抵達的那一刻,所以你剛才花兩分鐘操作板子的那兩分鐘,正好是被丟掉的那批。

exp134 把它變成一個可以選的東西,三個政策,同一份韌體,同一次四十秒的沉默。丟最新的給你十七行舊的然後跳;保留最新的把缺口放在最前面,然後是最後十六秒;而第三種在沒有讀者的時候什麼都不排隊,只計數 — 它丟掉的是十行而不是七行,因為別人留下的那三行本來就不值得留,而它直說。

寫完才看得見的東西有兩個。**差值在會丟東西的佇列裡不安全**:`(+50 lines lost)` 是被渲染進某一行文字裡的,而保留最新的政策會主動丟掉已接受的行,計數就跟著沒了,而且無上界地少報。所以那個建置改報累計總數,它抗驅逐,因為後面每一行都會重印一次。實測的 capture 裡那個總數每秒加一,然後在讀者抵達的瞬間停住 — **計數器自己說出了驅逐速率**,沒有人設計這件事。

另一個是一個由兩個正確的半邊組成的死結。第三種政策需要知道有沒有讀者,而記錄函式是同步的,拿不到 USB sender,**它問不到,只能被告知**。如果旗標初值是假,就沒東西進佇列,寫出者永遠不醒,永遠不去看 DTR,旗標永遠不會變真。初值設真,代價正好是每個閒置區間漏一行 — 而那一行是沉默前說的最後一句話,對讀者反而合理。

決策獨立成一個沒有依賴的 crate,因為 `usb-log` 依賴 `embassy-rp`,**只能為板子編譯,從來沒有過一個測試**。而這裡每個問題都不需要硬體:板子上湊出一個狀態要四十秒刻意沉默,函式呼叫裡是一瞬間。

## 一行寫好六個實驗、今天才第一次跑起來的日誌

exp128 發現長度是 64 倍數的訊息永遠不會結束:沒有短封包收尾,接收端就一直等,而下一則訊息被黏上去。它指出了修法的名字 — 零長度封包 — 然後送不出來。

它的韌體裡一直有這一行:

```
msg #N: ... ended by a zero-length packet
```

寫好、驗過、推上去、寫進 README,而**在今天以前沒有任何量測產生過它**。接收端六個實驗前就完成了,缺的是任何一個講得出另一半的主機。

缺了六個實驗的原因,比修法本身有價值。`printf > /dev/ttyACM0` 把位元組交給驅動程式,由它決定怎麼分封包,而那條路徑上沒有任何地方能說「講完了」。零長度封包不是你能 echo 的位元組,它是**一個沒有位元組的傳輸**,只有握著介面的程式送得出來。所以 `yi26 send --end` 得長出第二條路:直接 claim 介面,做那兩個瀏覽器也會做的 control transfer。

這把慣常的故事翻過來了。工具區那張表列了八件 `yi26` 做得到而網頁做不到的事,而這是第一件反過來的 — **網頁一直都做得到**,因為 WebUSB 從來沒有 tty 擋在中間,反而是命令列工具得先交出自己的序列埠才追得上。

最尖的一格是「什麼都不送」。同一台機器上的舊專案量到零長度請求是零個封包,而 `nusb` 的原始碼白紙黑字寫著相反。實測 — 它有到。而 Chrome 也有到。所以那是**主機函式庫的性質,不是匯流排的**,兩邊都對自己的堆疊誠實,而「USB 會怎樣」和「我用的函式庫會怎樣」從來不是同一個宣稱。

結論不是「用零長度封包做分界」。舊專案為一個真實協定評估過這件事然後否決了,理由不在匯流排上:三個實作必須保持一致,傳輸相依的分界會讓它變成六個半套。**傳輸邊界真實、便宜,而且仍然不是放協定訊息邊界的地方。**

## 四個 bug,三個是同一天自己造成的

`run.sh` 在「請你抬頭看板子」那一步崩掉,因為 `pause` 沒給訊息而腳本跑在 `set -u` 下。`yi26` 不在使用者的 PATH 上,因為二十四個 README 叫他打這個指令而只有一個檔案說過怎麼讓它存在。然後修好第二件之後,腳本開始跑 `cargo install` 留下的舊快照,對著原始碼明明支援的旗標報錯,而錯誤訊息指向腳本。

三個都住在同一個地方:**只有人在場才會走到的那條路,沒有任何自動讀者。** `check.sh` 從不呼叫 `pause`,而 `check.sh` 才是無人自動跑的那個。presence 分級本來是要指出這種落差,結果落差落在工具自己身上。

## 現在

三十五個實驗,每一個都在真的板子上驗證過。工具箱分成兩半並且各自有斷言守著。日誌佇列從一個常數變成一個決定,而預設值一個位元都沒動 — 有測試釘住等價性。

還是沒有正式的版本釋出。
