### 量到的

十二個案例、七支韌體。**十個案例六支答案完全相同** —— 這條鏈從 110 行長到
959 行，行為幾乎沒漂，不是累積圖像會預測的結果。

兩個漂掉的都在鏈的頭部 exp189：

| | |
| --- | --- |
| `bad-cid` | 回 `ERR_INVALID_PAR`，規格寫 `ERR_INVALID_CHANNEL` |
| `busy-recovers` | 拒絕 broadcast INIT —— client 迷路後唯一的回頭路 |

第二個加了時鐘量：0.1 s 拒、1.0 s 拒、約 3 s 逾時、5 s 才給 channel。**不是
磚**，但那四秒裡裝置叫 client 走開又沒留路，而規格給的逾時是 750 ms。

移植 exp189 到 crate 時，在**另一條程式路徑**上找到同一個缺陷的第二處：等人
按按鈕的整段時間都拒絕 broadcast INIT，而預設 build 等 **30 秒**。

### 修好的（全部硬體驗證，無人在場）

| | 之前 | 之後 |
| --- | --- | --- |
| exp189 `bad-cid` | `ERR_INVALID_PAR` | `ERR_INVALID_CHANNEL` |
| exp189 `busy-recovers` | `ERR_CHANNEL_BUSY` | 給 channel |
| exp189 presence wait 期間的 broadcast INIT | 拒絕，0 回覆 | answered，1 回覆 |
| exp189 自己的 transaction timeout | 1500 ms | 750 ms（規格值） |
| `tools/ctaphid` 缺 `Link.drain()` | 沒有 | 有（見下） |

## 檢討

### 一、我的優先序表把我自己派去改二十份韌體

「`blink_task`/`heartbeat` 有 33 份複本，`lifeline::led` 已經存在，只差採用」
—— 這是上一輪那份表寫的，而且是錯的。把 33 份按**實際是什麼**分類之後：

| | |
| --- | --- |
| 1 | 真正符合條件 |
| 11 | LED 已經有別的意思（crate 自己的文件說這些保留自己的） |
| 20 | 要**加上** lifeline —— 裝上看門狗、換掉 panic handler |
| 1 | 根本不是 LED，它每兩秒 log 一行 |

第三列是決定性的：exp162/163/164 **故意殺掉 core 0 或當機**來量一面牆，一個
會把它們重開的看門狗改變的是它們量的東西。

而「33」是 grep **函式名字**得到的 —— 正是我在同一份文件下面兩節寫著的
`duplication.sh` 已知缺陷，只是這次從**規劃端**撞到，而且是在寫下它一小時
之後。

**下次怎麼不再犯**：一張建立在偵測器輸出上的優先序表，會繼承偵測器的盲點。
偵測器擅長找候選，它做不到的是告訴你這些候選是不是同一件事。**把候選分類，
是提出工作之前的最後一步，不是開工之後的第一步。**

### 二、我的共用工具缺了一個別人已經付過代價的修正

七份 host client 的傳輸層比對下來只有一處實質差異，而它是一個**從沒傳出去
的修正**：exp174 的 `Link.drain()`，丟掉上一次執行留在 kernel buffer 裡的
keepalive 封包。六份沒有，**`tools/ctaphid/` 也沒有** —— 而那是這個 session
自己寫的、一路拿去驅動七塊板子的 client。

exp194 找到韌體鏈**最新的成員帶著兩個缺陷**；host 鏈**最新的成員帶著唯一的
修正**。形狀一樣：一個改動落在一個分支上，其他分支永遠不會聽說。

**下次怎麼不再犯**：抽取一個東西的時候，**先把所有既有複本兩兩比對過**，
而不是挑一份看起來最乾淨的當範本。差異可能是 bug，也可能是修正，而後者比
前者更容易被丟掉 —— 因為它看起來像「多出來的東西」。

### 三、棘輪擋下我，而它是對的

exp194 的第一版韌體帶著 97 行的 `ctaphid_task`，已經比它取代的 959 行小十倍，
`duplication.sh` 還是把它擋下來：第十五個 `ctaphid_task` 就是第十五個。

我一度想改名繞過去。**擋下來是對的** —— 小到讓人覺得無害的迴圈正是會被複製
的那種。迴圈搬進 crate 的 `board.rs`，實驗剩下 17 行。

**下次怎麼不再犯**：檢查擋路的時候，先假設它是對的。這一輪三次被自己的檢查
擋下（`usb_check`、LED 順序的錨點、這一次），三次都是檢查對。

### 四、相容層是「避免編輯」的別名

host client 採用的第一版，我在每個檔案留了 `def init(link, ...)` 的 wrapper，
讓呼叫端不用改。結果：計數還是 7，而且三個檔案裡各多一個**只為了避免編輯而
存在的函式**。

**下次怎麼不再犯**：如果抽取之後數字沒有動，那就不是抽取。

### 五、一個錯的數字會讓整張表失去信用

多語言偵測器第一版，shell 函式的邊界用「欄位 0 的 `}`」找 —— 對 Rust 是對的，
但單行的 `say() { echo "$1"; }` 沒有那種括號，於是它一路跑到檔案裡下一個閉
括號，`sh:say` 被算成 **56 行，實際是一行**。

**下次怎麼不再犯**：跨語言重用一個規則之前，先問這個規則在新語言裡的前提還
成不成立。而且輸出裡任何一個「看起來不太對」的數字都要追到底 —— 這個是我在
看報表時覺得刺眼才發現的，沒有任何檢查會抓到它。

### 六、寫下「這件事不值得做」也是產出

C 那一輪最後**沒有改動任何實驗**，只把撤回的理由寫進設計文件。那不是空手：
那張表本來會把下一個人派去改二十份韌體。

## 這一輪做對的三件事，值得複製

1. **先量，再寫。** crate 不是 exp189 的傳輸層整理一下，是**五支韌體一致同意
   而且規格要求的行為** —— 這句話只有在那張表存在之後才寫得出來。要是照著
   最新的那份抄，就會把兩個缺陷一起抄進去。

2. **把時鐘接上去，句子才變成真的。** 第一次的讀法是「exp189 永遠卡死」。
   量了之後是「拒絕四秒然後恢復」。前者會變成一句永遠不會被更正的 README。

3. **兩份 capture 都留著。** 修好之後重跑套件會**抹掉曾經有問題的證據**。
   `capture-before-port.txt` 是量測，`capture.txt` 是現在的樹。
